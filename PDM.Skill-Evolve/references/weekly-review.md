# 综合评审（定时或回退）

本评审把所有 OPEN 观察条目与所有技能交叉核对，传播横切原则，
并把无需用户输入的改进应用到暂存副本——绝不动现行技能。两种模式：

- **定时自主评审（首选）：** 通过平台调度器注册的周期任务
  （例如周一/三/五早晨）运行。无需用户在场，只把未上报的观察条目
  应用到暂存副本；在用户安装捆绑包之前，任何内容都不上线
  （审批策略、「交付更新后的技能」）。
- **会话内 7 天回退：** 当以下两条同时成立时，在会话启动时挂起：
  没有注册定时评审（或已有 7 天以上没有任何定时评审写入过
  `last-review-date.txt`——调度器的 "succeeded" 只说明任务被启动过，
  从不说评审运行过），并且 `skill-observations/last-review-date.txt`
  的内容是 `never` 或一个距今 7 天或更久的日期——与 SKILL.md 步骤 3
  使用的同一条边界，刻意以同样方式表述：恰好七天时两个文件必须一致，
  否则评审是否运行取决于会话查阅的是哪一个（缺失的文件会以 `never`
  重建——见会话启动步骤 1 与步骤 3；文件中的值是权威的，一个日期
  意味着评审确实运行过）。在交互式会话中，挂起的回退以一行提议的形式
  浮出，仅在用户选择参与时才运行（SKILL.md，会话启动步骤 3）——
  它绝不阻塞用户的任务。其内容随积压条目的规模伸缩，其频率从不如此，
  因为一条永不清空的积压会以变得过于昂贵而无法清空的方式安静地失败：
  逐会话看正确的行为（绝不阻塞用户）累加起来，就是一场没人接受的
  评审。有界的切片让工作单元在积压增长时保持恒定。

本索引与审批策略之间的材料，是整个文件都依赖的序言：可达性态势、
离线工作区策略，以及如何界定一次跨多份观察日志的聚合评审的范围。

**可达性——定时工作实际运行在哪里？** 定时模式要求调度代理的执行
环境能够读写工作区文件夹。持久层与执行上下文是相互独立的轴：知道
状态住在哪里并不够——还要检查调度器是否运行在能够触及它的地方。
三种态势：

1. **共享文件系统**（例如 Cowork 的挂载文件夹）：定时模式按所述方式
   工作。
2. **仅本地文件系统加云端调度器**（例如运行在托管基础设施上的远程
   例程）：定时模式在物理上不成立——远程代理读不到
   `skill-observations/`，也无法把更新暂存到 `skill-updates/`。
   不要注册例程。建议改用周期性日历提醒，加本地会话中的手动
   "运行技能评审"触发器，或者把观察日志同步到调度器可达的存储
   （例如一个它能克隆的 git 仓库）。
3. **仅本地文件系统加本地调度器**（cron、Task Scheduler、常驻终端的
   循环）：可行，但用户必须保持本地代理可运行。

**针对定时运行的离线工作区策略。** 定时或自主会话可能在工作区的
持久层不可达时触发——日志可能位于触发时刻正在休眠或离线的机器上。
预先定义策略：(1) 先于一切检查工作区可达性；(2) 若不可达，以一行
"review skipped — workspace offline" 备注优雅结束，不重试——下一次
触发或 7 天会话内回退会补上——此处"不可达"指探针在那里什么也没
找到：挂载缺失、主机休眠。探针在一条存在的路径上因权限或沙箱错误而
失败是第三种状态，且它不是瞬态的：定时会话自身的沙箱拒绝该工作区，
之后每次触发都以同样方式跳过，什么也不会自愈。其备注要点名责任方
——"review skipped — workspace denied by the session sandbox;
grant C:/Users/Administrator/.zcode in the task definition"
（`references/environments.md`，「访问授权是任务定义的一部分」）——
因为针对策略性拒绝发一条离线备注，会把读者打发去等一台早已开着的
机器；(3) 配置定时评审时，把这条策略固化进定时任务的提示词，让新
会话无需重新发现即可继承。运行中途的权限失败——探针已成功之后——
以同样方式处理：跳过受闸门约束的那一步，把它记录为一项手动跟进，
并仍然产出最终报告——被阻塞的步骤 N 绝不能让步骤 1 到 N-1 的报告
陪葬。以上都不覆盖在步骤 1 之前就停止的运行：一个在第一次调用后
转入空闲的会话不写时间戳、不暂存任何东西、不产出摘要，而调度器把它
记录为 "succeeded"——这是对错误问题的诚实回答，因为调度器报告的是
它是否启动了任务，从不是任务是否完成了它的工作。评审的完成信号是
它自己的工件，即步骤 7 的时间戳；调度器的运行状态只是关于调度器的
证据，调度的消费者要把工件的日期与调度器的最近运行日期互相对照，
而不是单独相信任何一方。

**一台机器上多份观察日志——在集成点统一评审。** 先检查这些日志
是否本应共存：`references/environments.md` 要求每个被观察范围一份
日志，覆盖同一批全局安装技能的两份日志正是它警告过的静默分叉——
应合并它们，而不是联合评审。剩下的是正当情形：日志被刻意分开，因为
观察正文携带不可移植的任务上下文，而它们观察的技能是全局安装、因而
共享的。在那种情形下，按日志逐个运行各工作区的评审会把每个共享技能
暂存多次，每份暂存副本只整合自己那份日志的切片——按构造，这正是
交付章节所要检测的同日多写入者分歧——而 filed 在不同项目里的收敛
观察条目会被当作彼此独立的决策分别上报，因为没有任何一次运行同时
看见它们（步骤 3 的所有权栅栏规则覆盖跨会话分割的积压，不覆盖跨
日志的）。

因此，聚合评审是一次显式发起、针对一组具名工作区根目录的运行——
不是某个工作区级定时任务能发现或启动的东西。后者保持其按日志的
行为，正是这一点阻止两个运行同时清空同一批队列。**具名集合以绝对
路径给出**，在运行的顶部一次性给出：从项目标识枚举出的根路径常以
`-` 开头（Claude Code 就以那种方式编码目录路径），而相对参数中的
前导 `-` 会被 `ls`、`grep` 和 `find` 读作选项——扫描于是返回零个
文件且没有任何报错，与一份干净的日志无从区分。给定根目录：

- **按日志观察什么划定范围，而不是按它们声明什么。** 工作区观察
  同一批已安装技能的日志都在范围内。不要以它们的 `skill:` 列表是否
  重叠设闸：步骤 3 说收敛条目惯常是针对*不同*技能记录的，因此按
  声明目标设闸恰恰跳过了本机制为之存在的那批聚类。先跨所有日志聚类
  （步骤 3 的 Principle 行扫描），再作决定。
- **让每个离开其日志的 id 带上限定。** id 按日志分配，所以 `#5`
  在每份日志里都存在。任何跨日志引用——批准列表、
  `resolution: "by #N"`、步骤 8 摘要、清单条目——都要在编号旁携带
  工作区键。**这个键是标识符：**它派生自一条路径，而路径带着项目的
  名字。当一条跨日志引用要离开本机——一份上游报告、一份共享摘要——
  把工作区中性化重命名（`root`、`p1`、`p2`），并在开头声明一次。
- **每个受影响的技能只暂存一次，并把锚点工作区发布到所有位置。**
  一个参与者是**锚点工作区**：它的 `skill-updates/` 存放暂存副本，
  并为步骤 5 的种子提供 `[workspace folder]`——种子随后完全按单日志
  运行的方式选取自己的**锚点目录**（`[today]/[skill-name]`，或同日
  规则之下带区分标识的目录）。这两个含义是相互独立的轴，始终用全名
  称呼：*锚点工作区* = 哪一份日志的 `skill-updates/` 树，*锚点目录*
  = 其中哪一个带日期的目录。在锚点工作区追加清单条目，并在每一个
  *其他*参与工作区的 `PENDING.md` 里追加一条指针条目——绝不在锚点
  自己的 `PENDING.md` 里，因为锚点已持有清单条目本身，那里的指针是
  一条它自己的对账闸门会重复计数的自引用——**在该清单尚不存在的
  地方创建它**——一个从未暂存过任何东西的参与者没有 `PENDING.md`，
  而一个假定文件已在的追加者什么也不写。清单只从它自己的工作区
  读取，其条目在安装时移除，所以只在一个工作区中被点名的锚点从其他
  工作区不可见，并在第一次安装后消失。
- **簿记保持本地。** 每份日志的工作队列、状态编辑、归档、
  `last-review-date.txt` 与 `activation-tiers.txt` 都从它自己的工作区
  读取并写回它自己的工作区——激活记录尤其是一条关于该工作区配置的
  陈述，所以聚合运行给每个参与者写一份，绝不在锚点工作区写单独一份。
  集成与暂存统一；簿记不统一。

原则是：当多条只追加的队列向共享目标输送编辑时，清空它们的评审必须
在集成点统一，即使队列本身保持分离——而统一需要每个队列有一个身份，
否则合并后的引用不再可解析。

## 审批策略

**交互式（用户在场）：** 始终按技能分组呈现观察条目（编号、标题、
一句话摘要），把需要判断的取舍标记为 "needs your input"，并在应用
之前等待整体批准或选择性批准。分组列表存于评审记录，聊天中最多
携带三个后续步骤并附上指向该记录的链接（步骤 3）；它请求的批准
仍覆盖整个列表。
**先分类，再询问。** 提供给用户的任何*处置*选项（并入、否决、恢复、
路由到技能 X）都必须从条目的正文推导，绝不能从它们的标题和 `skill:`
字段推导——标题级别的摘要恰恰是不读正文也能产出的东西，而它为
错误的拆分发放了许可。先阅读、先分桶，然后附上真实计数呈现路由
决策（"15 → skill A, 25 → skill B, 2 dead"）。要提防的触发条件是
不复存在的目标技能："revive / fold in / decline" 看起来像一个处置
问题，实际是一个分类任务，因为 filed 在一个已死技能名下的语料惯常
拆分到几个活着的技能上。当一个大块问题确实必须先问（积压非常大、
会话预算不足以读完一切）时，在问题里说明这一点，把提议的拆分标记为
暂定，并在内容与之相悖时重新呈现。顺序是
`read → bucket → present counts → ask`，绝不是 `ask → read`。
读正文是必要而非充分的条件：正文本身可能主张一个可核查的前提
（"目标是外部维护的，因此向上游贡献是可能的"），基于它构建的选项
就把该主张未经核实地继承了下来。在呈现该选项**之前**、从本地已有
的材料中解决这类前提——技能安装时来自的检出或副本、一份存好的
基线、文件自己的 source 与 feedback 行（或其 frontmatter 的
`metadata.source`）。本地出处能回答其中大部分，而其成本远低于一个
建立在错误前提上的决策，加上随之而来的重新询问。当前提确实在远端
时（该小节在 upstream HEAD 是否仍然存在、PR 是否仍然开放），评审
不得依赖接通网络：呈现该选项并点名其中那一半为未核实，把远端检查
留给 `references/skill-authoring.md` 的反馈预检，它在用户选择贡献
之后运行。分叉的文件需要在两个层面核查：文件级出处（"此技能为外部
维护"）与小节级出处（"该观察条目所扩展的小节是本地新增"）是两条
独立的陈述——都可以从本地副本回答——而路由到上游还是分叉取决于
第二条。（实测：一个"上游贡献"选项曾被提供并被选择三次，对象是
扩展某个小节的三条观察条目，而该小节查明只存在于本地分叉——该
决策不得不带着修正后的事实重新询问。）被拒绝或被关掉的批准提示
不是批准——也不是跳过询问、直接执行的请求。把它当作受闸门动作的
停止信号：停下，然后用普通聊天文本询问用户想要什么。只有明确的
放行（整体或逐条）才授权应用；作为评审触发短语的 "apply the
observations" 仍让每一次应用受本策略闸门约束，它并不预先批准这些
变更。
**被批准却被工具层拒绝的步骤不会再次尝试。** 用户的批准与宿主的
权限分类器是两道闸门，第二道按自己的规则裁决。当对工作区之外、
用户自己的文件的一个已批准动作——一次删除、一次移入回收站、从
一个指令文件移除一个小节——在工具层被拒绝时，不得以任何形式重试
（SKILL.md「如何记录」中那次唯一的全同重试，针对的是技能自身工作区
的写入）；把该项连同拒绝的原话记为待处理，在收尾摘要中作为带确切
路径的一步交给用户，并继续应用阶段的其余部分。准备工作（锚点、
备份）放进自己独立的调用运行，绝不与携带此类动作的调用同处一个
调用，这样一次拒绝不会把它一起拖垮。

**定时自主（用户不在场）：** 默认应用未上报的观察条目——安全性来自
"暂存加评审"模式（在用户安装之前，任何内容都不上线）。**上报而不
应用**的情形：(1) 观察条目提议一个新技能（命名/范围/类型/许可需要
用户）；(2) 代理（AGENT）本身提议移除既有内容或对其实质重构；
(3) 它自我标注不确定（"not sure if…"、"worth discussing…"）；
(4) 两条观察条目冲突。定时运行仍应应用每一个未上报项——一个什么
都不应用的评审只是一台报告生成器。

标准 (2) 关乎的是谁的判断在驱动变更，而非 diff 的大小。凡观察条目
把移除或重构记录为用户已决定（DECIDED）且携带完整规格——指明什么
替换什么，详细到应用时无需发明任何东西——就应用它，并始终把它
标记为摘要中供用户阅读的第一个 diff。凡规格不完整（"something
like…"、"the old rules should probably go"），适用标准 (3)，它保持
上报。上报规则防的是代理自身的判断，不是变更本身：把用户已经做出
的决策当作问题上交，等于把他们的答案作为问题退还给他们，买不来
任何安全，还耗费一个周期，期间技能保持着明知有错的状态。

**已发布的案例同样被应用，并带上它的仪式。** 对已发布技能的重构
需要发布分支、测试计划与版本升级，这些是无人值守的运行无法独自
决定的——但"上报而不应用"对这层保护是错误的形状，因为暂存不是
发布：在发布运行之前，任何内容都到不了仓库，而发布运行已经对
`under_test` 和它的新鲜度闸门设了闸。因此，对已发布技能的、由用户
决定且规格完整的重构，定时运行**确实会**应用，产物是一份暂存副本，
并且 (a) 版本至少升一个 minor；(b) 在摘要中被标记为第一个 diff，
并带上明确的一行 "published skill — install and the release are
your call"；(c) 携带一条把它命名为重构（restructure）的清单条目，
使发布运行按分支常设规则把它路由到带测试计划的发布分支（步骤 5）；
(d) 该观察条目保持 `open`，并在一条 `reference:` 备注中记录暂存
路径，使下一次评审的存在性检查在副本安装后将其关闭，而不是重新
应用它。保持上报的是该运行做不了的决策——切分支还是从 main 发布，
以及何时——绝不是机械性的工作。（实测：按字面读，旧的但书本会把
维护者本人关于 "priority" 的决策当作问题退还给他，让已发布技能
再保持一个他已决定否弃的形状又一个周期；那次运行还是把它暂存了，
本段把那次的做法定为规则。）

每个聚类只上报一个决策（DECISION），绝不把同一个决策上报两次——
在写上报列表之前先对 OPEN 条目聚类（步骤 3），并在每个决策之下
列出成员观察条目编号。

## 步骤

**步骤 0 —— 建议配置定时评审（仅回退模式）。** 顺序守卫：先运行
步骤 1 的"无观察条目"短路——如果没有 OPEN 观察条目也没有未落地的
原则，就完全跳过步骤 0，只更新时间戳。一个全新的安装绝不能在做过
任何工作之前收到配置提示。否则：检查
`skill-observations/scheduled-review-decline.txt`：若它不到 30 天
且回退没有反复触发，跳过。检查是否注册了定时任务
（`skill-observations/scheduler-registered.txt`，或直接查询平台的
调度器：Unix 上 `crontab -l`；使用 launchd 的 macOS 上
`launchctl list`；PowerShell 里 `Get-ScheduledTask`，或任意 Windows
shell 里的 `schtasks /Query`；Cowork 里应用的 Scheduled tasks
页面）；若找到，先确认它覆盖的正是**本**工作区再跳过：把任务注册时
所针对的工作区（记录在 `scheduler-registered.txt` 里，或从任务定义
中读取）与本会话解析出的 `[workspace folder]` 比较。同一路径 →
再检查其最近一次运行（在调度器报告最近运行的情况下）：一个晚于
`last-review-date.txt` 的最近运行日期，意味着一次触发了却没有完成
任何评审的运行。用一行说明——"fired YYYY-MM-DD, no review
recorded"——把它作为调度器缺陷提出，绝不当作发生过的评审，并且
**不要**跳过：回退保持待命。同一路径且没有这样的运行 → 照旧跳过。
不同路径，或任务的工作区无法确定 → **不**跳过。一个读取另一个
工作区的已注册调度器不是本工作区的覆盖；它是那个分叉在报告自己
健康。用一行说明这一点，点名两条路径与本日志的 open 计数，并路由到
「一台机器上多份观察日志」：覆盖同一批全局安装技能的日志是要合并的
分叉，不是要排期的第二条队列。"No scheduler available" 指平台自己
的调度器被查询过且不存在——Windows 上缺 cron 不属于这种情况；在
那里 Task Scheduler 就是调度器，一个只围绕 cron 措辞的检查会把每个
Windows 安装都标记为无调度器，从而静默地永不提供本评审。提议之前，
先检查可达性（见上文态势）：若平台的调度器运行在触及不到工作区
文件夹的地方（态势 2），不要提议注册——改为推荐"日历提醒加手动
触发"的组合，并跳过本步骤的其余部分。否则提议配置一个。同意 →
通过环境提供的任何调度器注册（见 `references/environments.md` 的
环境表），命名为 `weekly-skill-review`，若
`skill-observations/scheduled-task-draft.md` 存在则使用其中的提示词
草稿，然后先验证注册确实成功（调度器列出了该任务，或平台确认了
创建），**然后**再把今天的日期**连同该任务注册时所针对的绝对工作区
路径**写入 `scheduler-registered.txt`——一个只装日期的标记回答不了
上面的覆盖问题，下一个会话就得去解析任务定义，而不是做一次比较。
若注册失败或无法核实，不要写标记——这个标记会在从未运行任何评审的
情况下永久压制回退。告诉用户注册失败，并让回退保持激活。一个被列出
的任务只是一次注册，不是一个能运行的配置：注册时携带宿主沙箱对
工作区根目录所需的任何允许目录授权，第一次触发自身的报告才是完成
检查，而第一次运行以一条拒绝备注收尾——工作区存在，任务的沙箱
触及不到它——是任务定义上缺失的授权，绝不是下一次触发能补上的
故障（`references/environments.md`，「访问授权是任务定义的一部分」）。
不同意 → 把今天的日期写入 `scheduled-review-decline.txt`（压制
30 天；窗口内回退反复触发会重新浮出该提议）。本环境没有可用的
调度器（按上文定义）→ 静默跳过。

**步骤 1 —— 加载。** 首先，激活回归检查——"激活是否就位？"这个
问题里评审能触及的那一半：评审只在技能已加载时运行，所以它检测
不出从未激活的安装，但它能检测出一个曾经就位、如今不再就位的层级
（一份被重写的 CLAUDE.md、一个被设置同步替换掉的 hooks 文件）。读取
`references/environments.md` 所指名的激活配置——CLAUDE.md 里的
指令块或其等价物，以及宿主提供会话启动钩子时的那个钩子——若先前
某次评审记录为在场的层级如今缺失，在摘要第一行说明并重新建议该
指令块；把找到的层级记录到 `skill-observations/activation-tiers.txt`，
让下一次评审有一个可对照的基线——在跨多份日志的聚合运行中，每个
参与工作区一份这样的文件，描述该工作区自己的配置，绝不在锚点
工作区放单独一份。

同一次扫描还有两个读取动作。**技能前置层级行点名的是批量内容，
还是只点名了探针？** 凡在任一技能就位之前读取的层级——一个偏好块、
一个用户级指令文件、一个会话启动钩子注入的文本——它的行必须点名
完整的第一批：工作区探针**和**会话启动技能加载，合并在同一个批量
调用里（`references/environments.md`，「探针搭载在第一个批量调用
中」）。只点名探针的行要标记；它触发了探针，却把加载留给一个可能
迟到才到位的配置。**定时提示词是否复述了流程？** 在平台公开注册
评审提示词之处（调度器的列表或读取调用）读取它，否则读取
`skill-observations/scheduled-task-draft.md`，并标记每一处复述评审
步骤、暂存路径、状态格式或上报标准的行。提示词只点名技能、模式、
工作区与离线策略，外加"先探针后调用"那一行，以及
`references/environments.md` 对每条定时提示词要求的启动标记——
别无其他。失败形态：存储的提示词每次运行都被读取，却没有人编辑，
于是被复述的步骤落后于本文件，而运行跟着那份副本走。把裁定记入
`activation-tiers.txt`，放在定时任务层级旁边，并让它可举证：逐字
引用提示词的第一行，随后逐条引用每个被标记的行，或者写
`restates: none (read: <n> lines)`。一条什么也不引用的裁定无法被
下一次评审核查，而且读起来与一条凭提示词的意图、而非其文本写下的
裁定毫无分别。对其他每一条调用某个技能的定时提示词，运行同样的
读取。

第三个读取动作也属于同一次扫描：**每次技能加载是否把它的查询放在
了同一个批次里？** 在拿得到会话转录之处，把 `checkpoints.log`
（由 `scripts/skill-load.sh` 写入）里的 `loaded <skill>` 行与 Skill
调用匹配。两类不匹配是可检测的失败，各是一条日志完整性发现：同一
批次里有 `loaded` 行却没有 Skill 调用；有调用却缺少其批次的
`loaded` 行。没有转录时，把每个会话的 `loaded` 行与该会话报告加载的
技能对照，并标记没有对应行的技能。启动行里记录为延迟探针工具的
批次拆分（`references/environments.md`，「延迟的探针工具把探针挪到
第二批」）不算发现。失败形态：这条规则只有在本应携带查询的那个
批次提交之后才会被读到，于是迟到的查询从之后的每个批次看都合规，
而记录是这一不匹配唯一显形的地方。

**在构建工作队列之前，先清空观察收件箱。** 在本次运行能读取到
"无日志会话停放观察条目的用户级存储"之处，读取它的收件箱文件。
对每个条目，一次一条：走正常的写入路径——复述检查、同族检查、
经助手推导 id——并创建观察条目文件；只有在该条目的文件已经在磁盘
上存在之后，才从存储中删除那个条目。被打断的运行因此不丢失任何
东西：每个条目要么还在收件箱里，要么已经是文件，而复述检查会抓住
那条恰好在中断前刚写完文件的条目。绝不删除收件箱文件本身——删除
记忆文件需要用户的明确请求——让它保持空。在该存储对本次运行不可读
之处，在日志完整性之下说明（"inbox not read: <reason>"）：此时不能
认为日志是完整的。失败形态：一个处理步骤从不清空的捕获回退，就是
第二份没人评审的日志。

然后归档在*先前*会话里已解决的观察条目文件——用按原样交付的清扫
（id 片段的清扫块，单独运行；见 SKILL.md 的「写入时归档」），绝不
用临时拼凑的批量移动；在无法避免时，一次性读出全集，并按数量守恒
验证（`observation-log.md`，「归档」）。只读 `observation-log/` 中
每个文件的 frontmatter——不读正文——来构建工作队列；只在步骤 5
中实际处置某条观察条目时，才加载它的正文。正是这种 frontmatter
优先的扫描，让评审在积压增长的同时保持廉价。

从文件本身构建工作队列，而不是从状态过滤。OPEN 集合的定义是：
**`status` 字面就是 `open`，或者该文件根本没有 `status` 字段。**
具体地：

1. 枚举 `observation-log/` 中的每个文件——目录清单就是条目的权威
   列表。
2. 对每个文件，从它的 frontmatter 读取 `status` 字段。缺失、空白，
   或除 `actioned`、`declined`、`superseded`、`parked` 之外的任何
   状态，一律按 OPEN 处理。
3. 绝不要只凭一条 `grep 'status: open'` 推导工作队列。要从文件列表
   里减去已解决的（`actioned` / `declined` / `superseded`）与
   `parked` 文件来推导它。对一个可选字段做 grep，会静默丢掉每一个
   缺少该字段的文件——评审随后自信地报告一份干净的积压，而未经
   分诊的观察条目被跳过了。

**对账守卫：**在继续之前，断言
`count(files in observation-log/) == count(status-classified files)`。
若两个计数不一致，差值就是无状态文件——浮出它们并分诊（按 OPEN），
而不是装作积压干净地继续。**这是时点断言，不是常设保证。**它证明
的是扫描在它运行的那一刻是完整的；日志是多写入者的，而一次长评审
正是其他会话记录日志的窗口，所以这个结果在运行期间会衰减。把步骤 1
的文件列表保存在磁盘上——绝不放进 shell 变量，shell 变量活不过
下一次工具调用，而且在 zsh 下不做分词（`observation-log.md`，「在
zsh 下……」）——这样步骤 6 能在任何东西被标记之前对照它重新扫描：

```bash
d="C:/Users/Administrator/.zcode/skill-observations/observation-log"
l="C:/Users/Administrator/.zcode/skill-observations/review-step1-list.txt"
find "$d" -maxdepth 1 -name '*.md' | sed 's|.*/||' | LC_ALL=C sort > "$l"
```

两个列表文件都会被下一次评审的步骤 1 与步骤 6 覆写，步骤 7 不需要
清理它们；一次针对步骤 1 未能刷新的列表而运行的步骤 6，会表现为
几十条的差值，而不是安静地通过。

**重复 id 检查——流程中没有任何别的东西会去找它。** id 规则说冲突
"留给下一次评审重编号"，而到目前为止没有任何评审步骤去找过，所以
一个重复可以无限期地留在原地。更糟的是，它对评审本身是静默破坏性
的：任何**以 id 为键**合并逐条结果的扫描——把读取扇出给助手时的
常见形状——会把那一对折叠成一条，输掉的那条从它等待已久的评审里
被丢掉，而且没有任何报错。这个冲突曾经浮出过一次，只是因为有人把
合并后的计数与文件计数做了比较。

```bash
d="C:/Users/Administrator/.zcode/skill-observations/observation-log"
find "$d" "$d/archive" -maxdepth 1 -name '*.md' | sed 's|.*/||' \
  | grep -oE '^[0-9]+' | sed 's/^0*\([0-9]\)/\1/' | sort -n | uniq -d
top=$(find "$d" "$d/archive" -maxdepth 1 -name '[0-9]*.md' | sed 's|.*/||' | grep -oE '^[0-9]+' | sort -n | tail -1); floor=$(sed '1!d; s/[^0-9]//g' "$d/archive/.id-floor" 2>/dev/null); [ "$((10#${floor:-0}))" -ge "$((10#${top:-0}))" ] || echo "FLOOR LAGS — .id-floor ${floor:-absent} < highest prefix $top: a writer bypassed the snippet"
```

最后一行在活动集与归档之上断言 `.id-floor >= 最高前缀`。片段或
`scripts/new-observation.sh` 的每次运行都会把 floor 留在它发出的那个
id 上，所以一个落后的 floor 意味着某个写入者没有运行二者之一就
创建了文件——这是绕过行为更早、更便宜的信号，在任何冲突出现之前
就可见（`observation-log.md`，「floor 过期」）。

用 `grep -oE '^[0-9]+'`，不要用 `sed 's/-.*//'`：归档里可能存有
3.0 之前迁移遗留的 `log-YYYY-MM-DD.md` 文件，在第一个连字符处截断
会把每一个都变成 `log`，进而被报告为重复 id。任何做过迁移的安装——
恰恰是最可能存在真实冲突的那批——都会被派去追一个幻影。去除前导
零的处理与 id 片段所用的是同一个，所以 `0091` 和 `91` 会被识别为
同一个数。

任何输出都意味着活动集与归档之间存在重复 id。现在就修，在构建工作
队列之前：把编号保留在**较早**的那个条目上（先按 `date`，再按较低的
`.id-floor` 纪元），把较晚的那条重编号为片段给出的新 id，同时更新
它的文件名和 `id:` 字段，并在它的正文里注明这次重编号，使对旧编号的
引用仍然可追溯。然后重新运行该检查，直到它什么都不再输出。对每一次
冲突，以及对 floor 落后之后的那些文件，把写入会话——每个文件的
`session_context` 与 `date`——记入步骤 8 摘要：这一对能把绕过行为
追溯到一个环境或一条写入路径，修复应该落在那里；而一个光秃秃的
计数，会把责任推给一条每个运行过片段的写入者都遵守了的规则。

**逐条头部一致性——是计数，不是闸门。** 扫描的可疑计数抓得住无法
解析的 YAML；它看不见解析成功却依然错误的头部：一个与文件名前缀
不一致的 `id`、一个不在五个取值之内的 `status`、一个缺失或空白的
`siblings_checked`，或者一个每个消费者都静默忽略的近似字段名
（`skills:`、`proposed_skill:`、`sibling_checked:`）。在重复 id 检查
之后，对活动目录运行它：

```bash
d="C:/Users/Administrator/.zcode/skill-observations/observation-log"
nonconf=$(LC_ALL=C find "$d" -maxdepth 1 -name '*.md' -exec awk '
  FNR==1 { sub(/^\357\273\277/, ""); fm=0; bad=""; idv=""; st=""; sc=""; f=FILENAME; sub(/.*\//,"",f); pre=(match(f,/^[0-9]+/) ? substr(f,1,RLENGTH)+0 : -1) }
  FNR==1 && /^---[[:space:]]*$/ { fm=1; next }
  fm && /^---[[:space:]]*$/ { fm=0
    if (idv !~ /^[1-9][0-9]*$/ || idv+0 != pre) bad=bad " id"
    if (st !~ /^(open|actioned|declined|superseded|parked)$/) bad=bad " status"
    if (sc == "") bad=bad " siblings_checked"
    if (bad != "") print FILENAME ":" bad; nextfile }
  fm && /^id:/ { idv=$2 }
  fm && /^status:/ { st=$2 }
  fm && /^siblings_checked:/ { sc=$0; sub(/^siblings_checked:[[:space:]]*/, "", sc) }
  fm && /^(skills|proposed_skill|proposed_skills|proposes_skills|sibling_checked|siblings_check|target_files|skill_qualifier):/ { bad=bad " near-miss:" $1 }
' {} +)
n_nc=$(printf '%s' "$nonconf" | grep -c .)
if [ "$n_nc" -gt 0 ]; then printf 'NOTE: %s non-conforming headers (id / status / siblings_checked / near-miss field):\n%s\n' "$n_nc" "$nonconf"; fi
```

它只报告；它不阻塞评审。它在真实语料上的误报率没有测量过，所以
第一次在活日志上运行时记录三个数字——命中数、其中真实缺陷的数量、
被归一化的数量——再据此决定它是保持为报告还是成为闸门
（`skill-authoring.md`，「一条被推荐的检查要带上三个实测数字」）。
没有闭合 `---` 的头部不在这里报告；当 `parsed`（已闭合头部）低于
`files` 时，扫描会按名字报告它。修复一处命中的方式，与重复 id 检查
修复一次重编号的方式相同：一个文件里改一个字段，除非出错的正是
id 字段，否则不动文件名。

**并且，凡评审把读取扇出并合并结果之处，以文件名为合并键，而不是
id。**文件名按构造唯一——noclobber 式创建保证了这一点——而 id
恰恰是冲突已经弄得含糊的那个字段。以唯一可能冲突的字段为键的合并，
没有办法察觉自己冲突了。

**搁置条目：排除出队列，不排除出视野。**`status: parked` 的意思是
该观察条目被判定为成立，但被记录在 `parked_until:` 里的外部前置
条件阻塞（SKILL.md，「如何记录」）。它是一项决策，所以不得重新
上报——但它也没有解决，所以它也永不归档，留在 `observation-log/`
里。每次评审都在 frontmatter 已经在手的同时对它做两件事：(a) 把
每条 `parked_until:` 条件对照世界的当前状态重查一遍，凡已满足的，
把该条目置回 `status: open`，清除 `parked_until:`，并把它带进本次
评审的队列；(b) 在步骤 8 摘要里把每条仍然搁置的条目各列一行——
id、标题、解除搁置条件——使搁置的积压保持可见，而不必重新进入
工作队列。以某个载体的状态表述的条件——一个 PR 被合并或被关闭、
一张工单被解决——要在它本应交付的那个结果上复查，也就是目标工件
的文本，因为结果惯常经由别的路径到达（`observation-log.md`，「搁置
条件命名的是结果，绝不是你自己的载体」）；对上游维护技能的一次
刷新，就是对每条搁置于其上的条目做这种检查。

### 暂存工作对账闸门

安装是发生在任何会话之外的手动、逐项行为，因此没有会话观察到它，
安装时刻也没有任何东西触发：一个其移除触发器是"没有任何会话观察到
的事件"的台账，只会长个不停。把清理绑定到台账被读取的时刻——读取
是唯一可靠反复发生的事件，因此做读取的会话拥有它。每次都先把树
对照清单：列出 `skill-updates/` 的顶层条目（`PENDING.md` 之外的
一切），并把每个没有清单条目指名的条目报告在一行里——"N 个暂存
目录没有清单条目：……"。在下面的四路分类之后，在该行中把每个只
持有分类为 (a) 或 (b) 的副本及其 `.skill` 捆绑包的已报告目录——
即保留两份规则会保留的那些已安装副本——标记为 `retained`，这样
未标记的名字就是没有任何东西能解释的那些。枚举目录清单，而不是
匹配日期形状的名字：带区分标识的锚点（`<date>-<slug>`、
`<date>.2`）和交接材料都是合法名字，而索引只显示有人录入过的东西，
所以一个只读索引的检查会把每个未录入项报告为不存在——代价不是
丢失工作，而是同一件工作被一个信息更少的会话重做一遍（实测：一次
清点和一份差异提案被暂存给下一个会话的文档轮，没有写条目；下一个
会话从零重新清点了同样的位置，还漏掉了暂存清点覆盖到的一处）。
然后，对 `skill-updates/PENDING.md` 中的每个条目**以及**
`skill-updates/<date>/` 下的每个技能目录——始终两者都做，绝不仅凭
清单：清单可能缺条目，也可能整个缺失，而一份缺失的清单读起来与
一份空清单一模一样（实测：三个日期文件夹中的八个暂存技能，十天
不可见，因为从未有会话创建过该文件）——对暂存副本与现行技能运行
`diff -rq` 并四路分类——因为现行副本会合理地继续前进，所以光一句
"有差异"不是裁定：

- **(a) 完全相同** → 已安装；移除清单条目。
- **(b) 现行严格更新 / 是暂存副本的超集** → 已并入；移除条目并附注。
- **(c) 暂存副本持有现行缺少的内容，且现行不持有暂存副本缺少的任何
  内容** → 未安装；把它呈报出来，并在本次评审对该技能的任何新暂存
  中，以暂存副本——而非现行——作为基底。同时在摘要中列出
  `resolution:` 指名了该暂存路径的观察条目
  （`find observation-log -name '*.md' -exec grep -l
  "skill-updates/<anchor>/<skill>" {} +`——用 `find`，绝不用裸
  glob，后者在无匹配时被 zsh 当作错误，而且也会漏掉 `archive/`）：
  它们在暂存时被标记为 `actioned`，而它们的工作尚未落地。它们保持
  `actioned`——状态描述的是评审的行为，重新打开会把已经做过的
  工作重新排队——但摘要把它们列在 "actioned, awaiting install"
  之下，而一份到达第二次评审（SECOND review）仍未安装的暂存副本，
  要作为一项决策上报（安装它，或丢弃它并重开其观察条目），而不是
  第三次结转。
- **(d) 双方各持有对方缺少的内容** → 已分歧；动作是合并（MERGE）——
  以现行为基底，把仅暂存副本所有的内容折回——绝不是对任何一侧的
  整体替换。合并之后，断言两个输入里的每个标题都出现在结果中且
  无一重复；该合并副本随后沿用 (c) 的簿记（呈报它、列出其观察条目、
  计数其评审次数）。

**当 `.skill` 捆绑包与暂存目录并列时，对捆绑包分类。** 捆绑包是被
呈现并安装的东西；目录只是它的生产者最后写下的东西。先逐成员按
字节比较二者：不一致本身就是摘要中的一项独立发现——"bundle and
directory differ: <files>; directory edited after packing"——且绝不
算状态 (c)，因为用户安装的正是被呈现的东西。然后把捆绑包的内容
解压到 `skill-updates/` 之外的一个临时路径，对其实际内容运行四路
分类。仅目录持有的内容从未被呈现过：把它作为未交付的工作带入本次
评审对该技能的暂存，并在发现中点名它。

**以安装器 frontmatter 引号归一化的方式比较。** 安装器在某些安装中
把 frontmatter 的 `name:` 行带引号写回，在另一些中不带引号，对某些
技能还会把 `description:` 也重新加上引号，因此一条裸的 `diff -rq`
会把刚安装的副本报告为有差异。分类前对两侧归一化——仅 frontmatter，
仅 `name:` 与 `description:`：去除包围的双引号并解析 `\"` 与 `\\`，
去除包围的单引号并解析 `''`；其余每个文件按字面比较：

```bash
fm=$'1,/^---$/{/^(name|description):[[:space:]]*".*"[[:space:]]*$/{s/:[[:space:]]*"/: /;s/"[[:space:]]*$//;s/\\\\"/"/g;s/\\\\\\\\/\\\\/g;};/^(name|description):[[:space:]]*\'.*\'[[:space:]]*$/{s/:[[:space:]]*\'/: /;s/\'[[:space:]]*$//;s/\'\'/\'/g;};}'
norm() { sed -E "$fm" "$1" > "$2" && [ -s "$2" ]; }
a=$(mktemp) && b=$(mktemp) && norm "$live/SKILL.md" "$a" && norm "$staged/SKILL.md" "$b" && diff "$a" "$b" && diff -rq -x SKILL.md "$live" "$staged"   # bash; exit 0 and silent = (a)
```

归一化失败是闸门错误，绝不是匹配：无法解析表达式的 `sed` 什么也不
写，而两条空流比较相等，所以该命令归一化到临时文件里并拒绝空结果。
若 `norm` 失败，按字面比较 `SKILL.md`，并预期仅引号差异的那几行
不同。

这条命令归本技能所有：任何其他技能在比较已安装副本与暂存副本时，
必须逐字引用它并指名本节是它的所有者，使这一形状不会漂移两次。
被安装器重新折行的多行 description 不被归一化，并会浮出。仅由那
两行上的引号构成的 diff 是状态 (a)，绝不是重新暂存的理由。那两行
上的任何其他变更仍然会浮出；靠肉眼放行已知的 diff，正是会把它藏住
的习惯。校验器的打包步骤产出带引号的 `name:`，所以多数安装回来是
字节相同的，归一化是兜底。

**暂存的状态文件按其记录的哈希对账，而不是按 diff。** 对
`skill-updates/<date>/_target-files/` 下的每个文件（「交付」，「状态
文件以补丁形式暂存」），对现行文件重新计算哈希，并与清单条目在暂存
时记录的字节数和 sha256 比较。哈希未变 → 指示可以写 "apply the
patch — copy is safe"，因为补丁恰好应用于它所基于的那个文件。哈希
已变 → 闸门报告 "staged patch, live file has moved — apply the N
changed lines, do not copy"，其中 N 从补丁计数，并把该条目的指示
改写为上述内容。补丁的每一新增行都已存在于现行，且每一删除行已经
消失 → 已安装；移除条目。安装指示每次重复时都重新推导，绝不逐字
结转：台账里没有任何东西会自行过期，所以一行在暂存时正确的话，
一旦现行文件继续前进，一个字都没改也会变成破坏性的。

**(b) 与 (c) 按差异块判定，绝不按文件。** `diff -rq` 只解决 (a)。
对每条仅存在于暂存副本中的行，问现行是*并入*了它——持有一条包含
它的行，或明显替换了它——还是*缺少*它：每一条此类行都被并入 →
(b)；任何一条真正缺失 → (c)。读起来最自然的文件级判据"任何仅
暂存行即 (c)"，会把每个已并入的副本错判，因为被修改的行会同时出现
在 diff 的两侧——而且它错在有害的方向，因为 (c) 是让暂存副本成为
下一次暂存基底的分支，于是下一次编辑会静默回退现行此后获得的
东西（实测：一份早晨暂存、已安装、又被第二次同日暂存并入的副本，
被按文件级判据判为 (c)；按差异块看，两条仅暂存行都已被现行中的
超集替换）。交付章节下的同日二次暂存正是此事的发生地——那条规则
说第二份副本写在哪里，本条说第一份随后如何分类。一个规定了 N 路
分类的流程，欠读者一个有判别力的判据，而不只是 N 个标签；留给
读者自己发明的话，每个实现者都会分开第一种情形、合并其余。

**(c) 与 (d) 需要另一侧的差集。** 按差异块的判据只读"暂存副本有
而现行没有"的内容；在为情形命名之前，把"现行有而暂存副本没有"
的集合也算出来——第一组非空且第二组为空是 (c)，两组都非空是 (d)。
在每个方向上比较标题集合（对每个文件 `grep '^#'`，每个列表对照
另一个），而不是去读交错的行 diff——后者正是招来捷径的东西。按
"哪一侧领先"排序的类别，只在恰好一侧动过时才穷尽，而带日期的
暂存文件夹按构造就是多写入者的，所以双侧都动过是常态，不是异例。
大小也不能给它们定序：较大的文件是长过了的那一个，这对它丢失了
什么毫无说明。（实测：一份三周前的暂存副本只持有四个小节，而现行
文件只持有另外七个；按当时的写法，(c) 会丢掉现行的七个，而按文件
大小的读法会主张 (b)，那会丢掉暂存的四个。合并保住了全部十一个。）

每次都双向对账：滞留已完成（已安装但仍列着）与缺失已完成（已暂存
但从未安装）以不同的方式失败，只有 diff 能同时看到两者。一次手动
批次的完成是一个主张，不是一个状态；该检查是每技能一次
`diff -rq`，对 20 个技能的批次几秒即完。会话启动协议（步骤 6）在
它宣布暂存更新时，运行同一道闸门。

**报告差异之前，把台账整个读一遍。** 摘录——列表行、标题、某个
模式的命中——是找到条目的合法方式，绝不是对一个条目下裁定的合法
输入。一个手工维护的文件把它的例外记录成刻意不像条目的行文：一次
清理、一次解决、那行写着"没有待办"的说明。于是模式摘录恰恰丢掉
能反驳漂移的内容，保留暗示漂移的内容，而它的信心在它输入最薄弱的
地方最高。（实测：一个会话把清单当作标题和列表项来读，报告一轮
为两个技能暂存、只有一个技能在场，并告诉用户清单需要清理——往下
二十行，以行文形式，记录着移除该副本的那次清理，以及"没有任何
条目处于开放状态"的陈述。）摘录用于搜索，全文用于裁定。

**`release/` 形状的暂存若没有清单条目，是闸门失败，呈报在摘要的
第一行——绝不是一个可被静默重构的副本。** 对近期日期目录的回退
清扫，本是为抓住缺失条目而存在，但抓到它是发现，不是修复：发布
分支的暂存与它的清单条目、它的挂起和它的测试计划一同切出（步骤 5，
常设规则），条目缺席意味着切出动作跳过了它的写入，因此挂起和测试
计划同样可疑。实测发生过两次：一个分支被暂存待装而没有清单条目，
发布注册表的挂起仍指着前一个被放弃的分支——只因本清扫对每个近期
目录做 diff 才被发现，且由一天后的一个交互会话修复，重构没有留下
该机制曾失效的任何痕迹。点名目录，点名缺失的写入，并把该副本按
状态 (c) 处理；若本次运行重构了条目，好让闸门的其余部分得以继续，
第一行要说明这一点，并说明写了什么——摘要不提的修复，正是本条
禁止的静默重构。

同时读取所有激活的横切原则。如果没有 OPEN 观察条目也没有未落地的
原则：报告 "no open observations or outstanding principles"，更新
时间戳，停止。

**步骤 2 —— 清点技能，并按"编辑能否**存续**"而非"能否成功"来
归类每个写入目标。** 列出所有技能（系统提示的 `<available_skills>`
或技能目录），并把每一个放进三类之一：

| 类别 | 判定 | 动作 |
|---|---|---|
| (a) 用户所有，无上游 | 位于用户技能目录；不是 git 检出；不从任何地方刷新 | 正常暂存流程 |
| (b) 可写但易变，或外部维护 | 路径包含插件缓存或版本锁定目录；或该技能经 clone/copy 或 `git pull` 从上游刷新；或**文件自身的内容声明了用户之外的维护者**——指名其他作者的署名块、用户不向其提交的正式仓库、`source:`/`upstream:` frontmatter 字段——无论它安装在哪里、如何到达那里，包括手工复制并手工更新的文件 | 绝不就地编辑——下一次更新会静默丢弃它，且永远不会触发任何权限错误；对声明了上游的，路由是上游报告 |
| (c) 无磁盘文件，或只读 | 内置 / 宿主提供的技能（如 docx、pdf、xlsx、pptx、skill-creator）；拒绝写入的挂载 | 无法编辑 |

指向 (b) 或 (c) 的观察条目不被跳过——目的地必须是既能让编辑存续、
又有东西真正加载的地方。两条路线都提供，让用户选择：一个互补的、
用户所有的 `{skill}-extras` 技能，只持有增量，**外加**用户指令文件
中的一条路由条目（明白陈述：没有路由条目，就永远不会有任何东西
加载这个伴生技能——路由到无处加载之处的修复不是修复）；或者把
内容直接路由进指令文件，后者无条件加载。对声明了上游的 (b)，默认
路线是按 source 与 feedback 行发起上游 issue 或 PR——
`references/skill-authoring.md` 的反馈预检在步骤 5 运行——
`{skill}-extras` 伴生技能只用于上游不会接收的、本安装特有的增量；
就地编辑文件不在选项之列，无论它多么可写。出处是工件的属性，写在
它的前几行里；安装位置是关于本机的事实，对谁维护该文件毫无说明，
所以先读署名块，再看路径（实测：本技能的一份手工安装、手工更新的
副本，与其发布 HEAD 字节相同，字面满足 (a) 的每一条款，一次评审
向它暂存了十条观察条目份量的本地编辑——正确的输出应是上游报告而
没有任何本地编辑）。本技能自身就是常设示例：凡用户不是其维护者的
地方，`task-observer` 属于 (b)。选择伴生路线可能意味着在本次评审中
创建 `{skill}-extras` 技能，约束章节允许它作为"评审中不创建新技能"
的唯一例外。当一次更新因权限失败时，扩充 (c) 列表；当你做出的变更
消失时，扩充 (b) 列表——这条规则在损害发生之后才触发，所以它是
署名读取的兜底，绝不是判据本身。

**步骤 3 —— 交叉核对观察条目。** 把每条 OPEN 观察条目对每一个技能
评估——不只是其 `skill:` 列表点名的技能；原则往往会泛化。构建
"技能 → [相关观察条目]"映射，从 frontmatter 播种：观察条目
`skill:` 列表中的每个条目把它放进那个技能的桶（第一个条目为主），
`proposes_skill:` 中的每个条目把它放到该名字的新技能候选之下，
`target_file:` 中的每个条目把它放到那个文件之下——评审按文件的
所有者对该桶应用（「交付」，「非技能文件按所有者拆分」：评审自己
拥有时直接写入，另一个进程拥有时暂存为补丁），而不是把条目重新
映射到最近的技能上。一条观察条目可以出现在多个桶里。每个桶以技能
的列出名为键，而不是原始字符串：一个恰好匹配唯一已安装
`plugin:name` 的裸名字并入那个桶；一个匹配多个的裸名字，或一个
描述性形式，从正文解析，绝不靠猜；并且每次归一化都列在步骤 8 摘要
的日志完整性之下。在那里同样报告 `skill:` 持有插件限定名
（`plugin:name`）的条目计数，与裸形式计数的对比：一份两种拼法并存
的日志，正是"用任一拼法查询都会静默漏掉另一种"的那种日志。否则
一个技能的两种写法就是两个更小的聚类，家族检查就发现不了两条条目
指向同一个成员。然后，在呈现任何东西之前：

- **路由检查，先于存在性检查。** `skill:` 是由注意到症状的人在
  任务中途写下的，所以它可靠地命名症状，不可靠地命名位置，而写入
  时的检查只问名字能否解析。打开每个目标，确认它执行 Issue 所描述
  的操作。若它不执行，重新路由——路由到执行的技能，或路由到执行
  它的非技能文件（一个指令文件、一个代理定义、一条定时提示词），
  后者成为一个 `target_file:` 桶，其输出是那个文件的一份补丁，由其
  所有者路由（「交付」）——并在正文中注明这次移动（"routed from
  X to Y: X never performs the append"），使 resolution 携带它。装在
  它无法生效之处的修复，关闭了条目，却让缺陷原地站着。

- **存在性检查，在此处、对着真实目标进行——并且对着 Issue，而不
  只是对着建议。** 步骤 5 在写入之前，对暂存副本 grep 每项建议的
  改进；这里也要在呈现任何东西之前，运行同样的"已应用 / 部分应用 /
  未应用"分类。在交互式评审中，用户在本步骤批准，所以步骤 5 永远
  不会再看到一条用户被请求批准两次的条目。对硬换行 Markdown 的
  短语搜索，要在空白归一化之后于块内匹配，绝不逐行
  （`observation-log.md`，「搁置条件命名的是结果，绝不是你自己的
  载体」）。对着观察条目实际指向的文件运行它——它的 `skill:`
  条目、它的 `target_file:` 条目、它指名的代码或登记表——绝不用
  代理目标，比如条目要求的是某个例程声明的登记表时，绝不用那个
  例程自己的 `SKILL.md`。关闭已应用者，并在 resolution 中指明在哪里
  找到。

- **修复拥有该问题的系统。** 在添加一条技能规则之前，检查某个
  代码、配置或 CI 变更能否消除该失败。若能，推荐那个修复：指名
  文件、变更和验证方式。只在需要的期间保留变通指令，并识别出能让
  后续评审移除它的那个修复。实施该修复仍遵循用户的范围与审批策略。

- **按所解决的问题合并新技能候选，而不是按名字。** 针对同一技能
  独立记录的提案不会看起来相似，因为各自以浮现它的任务命名；十一个
  工作名在阅读后坍缩成了四个技能。呈现合并后的聚类及其成员观察
  条目 id。
- **任何新技能聚类在呈现之前先做存在性检查。** 一条 `proposes_skill:`
  或一个 `siblings_checked: none`，是一条范围仅限于写下它的那个会话
  的"不存在"主张。搜索那个会话看不到的范围——其他项目的
  `.claude/skills/` 以及它们渲染自的生成器源——按正文里的问题词，
  而不只是按提议的名字，并对任何找到的技能运行上述存在性检查：
  一条"提议一个已在他处存在的技能"的观察条目，是对那个技能的
  改进，并且可能已经在彼处应用。
- **并入检查。** 凡较晚观察条目的发现是"较早那条的缓解不奏效"时，
  把较早的标记为 `status: superseded`、`resolution: "by #N"`，只把
  较晚的那条带向前。
- **家族传播。** 一条 `skill:` 列表携带多个条目的观察条目，在列出
  的每个技能都被更新或被明确处置之前，不算已处置——部分应用是
  默认的失败方式，而且是静默的，因为观察条目会凭它碰到的第一个
  技能就被标记 `actioned`。把逐技能的处置记入 `resolution:`，并带进
  摘要的家族一致性块。凡存在正当的部分应用（一个会话只拥有所列
  技能的一个子集），`observation-log.md` 中的承载条目模式解决它——
  而承载观察条目作为一等公民进入本队列，绝不因其出身被推迟。同时
  趁 frontmatter 在手检查 `siblings_checked:`：字段缺失或为空的
  条目，是在没做检查的情况下记录的，所以在处置它之前现在就做该
  检查（`observation-log.md` 中的注册表、测试与回退），若范围过窄
  则加宽 `skill:`。统计这些——"N 条观察条目未做同族检查即记录"是
  记录实践的一项健康指标，不是逐条的滋扰。同样只凭 frontmatter
  统计 `assumed` 排除项，并在处置该条目之前把每个这样的同族技能
  打开：一个基于 `assumed` 的排除是一个评审项，不是裁定
  （`observation-log.md`，「记录裁定」）。同一扫描中检查
  `commands_verified:`：一条引用了命令而该字段缺失或为空的正文，
  引用了一条没人运行过的命令——现在运行它，或者在条目被处置或
  引用之前，记录 `NOT RUN` 及原因。
- **对日志本身的保密扫描。** 对每条 OPEN 的 `open-source` 观察条目，
  检查 Issue 与 Improvement 字段里已不再为上下文所需的客户可识别
  细节，并剥除它们。日志是最可能被随手共享的工件，而编写时的清扫
  永远看不到它。

交互式：把完整的决策列表——按技能分组，正如审批策略所要求——存入
评审记录（步骤 8）。聊天中最多展示三个推荐的后续步骤，按影响排序。
对每一项，用平实的语言陈述**问题 → 具体变更 → 验证**；指名变更
属于技能、代理指令，还是工具。链接完整列表，并说明还剩多少决策。
在选择那三个之前，合并重复项并排除已修复项。等待批准：用户可以
批准那三项、一步批准记录中的整个列表，或从中选择一部分；一个短
列表不授权积压的其余部分。自主：对暂存副本应用上述审批策略并继续，
并保存同样的记录。

**在写上报列表之前，先按决策聚类。** 只追加的日志按构造积累收敛
条目：同一底层问题从不同的任务上下文被重新发现，并记录到不同的
技能名下，所以按记录类别分组会把这种重复保留进上报列表，用户被
多次询问同一个问题。把 OPEN 条目按它们所**要求的决策**分组，而不
是按记录到哪个技能；每个聚类上报一个决策，并在其下列出成员观察
条目编号；任何决策与另一条重复的条目做交叉引用，而不是单独上报。
廉价的第一遍：扫 Principle 行——收敛的观察条目即使 Issue 描述着
互不相关的任务，其原则也往往近乎相同。对会话内行为的推论：如果你
对重叠的察觉，强烈到会把"这与 X 是同一件事"作为答案选项提供出来，
那它就是答案——接受它并告诉用户，而不是花一个往返去问。
**跨所有权栅栏：**当积压被拆分在并行会话之间，而你把一条条目推迟
给另一个会话拥有的聚类时，这个推迟在指针双侧存在之前不算完成——
直接把它中继给那个会话，或作为一项交接事项呈报给用户。一条单向的
备注，让条目指向一个可能在没有它的情况下已被解决的决策。

**步骤 4 —— 交叉核对原则，并审计家族漂移。** 标记每一个尚未遵守
每条激活横切原则的技能。`skill-observations/cross-cutting-principles.md`
缺失是异常，不是空：会话启动步骤 1 会创建它，而它是该步骤的产出物
中直到本步骤才被读取的唯一一件，所以它的缺席至今没有任何可观察的
后果——一个运行了却不留痕迹的步骤，与一个被跳过的步骤无从区分
（实测：数月的日常使用、上百条记录的观察条目，该文件从未被创建）。
现在就从 `references/skill-authoring.md` 的模板创建它，在摘要第一行
说明，并把被跳过的步骤作为一条观察条目记录。

**新增或实质性编辑一条原则时，同一动作要携带其起始集裁定。** 当
捆绑包随附私有原则文件的一份公开的、去除出处信息的摘录——本技能
的 `references/starter-principles.md`——该摘录是派生内容，在抽取时
一次性完成的分诊是一个快照：摘录在私有文件的下一次编辑时就开始
漂移，而下游没有任何东西会为那之后新增的条目产出裁定。所以，新增
一条原则、或实质性修改既有原则的那个步骤，在同一动作中对它分类：
**`include verbatim`**、**`include after scrub`**——准确点名要剥除
什么（出处、观察条目编号、客户或环境细节）——或者 **`leave
out`**（个人策略，或特定于某一个环境）。把裁定追加到分诊参考，以
原则编号为键，使分类逐条对应，并以促成它的那次编辑为日期。本段中
的两个写入都归维护者：凡步骤 2 把本技能归入 (b) 的地方，分诊参考
是维护者自己的文件，起始文件是一份本地编辑无法存续的捆绑包文件，
所以裁定只决定下一段中的邀约。凡用户维护本技能的地方，原则及其
裁定直接进入评审所拥有的工作区文件（「交付」，「非技能文件按
所有者拆分」），而起始文件是技能内容：在同一轮中把它的变更暂存进
本技能的捆绑包，而不是作为后续动作：追加脱敏后的条目，升高起始
文件顶部的 `Starter set version:` 行（每个采用者的对账提议都以那个
数字为闸，没升版本等于把新条目发给任何人都不发），并在交付前闸门
对起始文件运行保密扫描。

然后运行**家族漂移审计**：对 `skill-observations/skill-families.md`
中的每个家族，对每个成员 grep 每一条列为共享的规则，并浮出缺口。
它是机械的，几分钟即完，而它是家族机制中唯一能抓住"早于该规则的
漂移"或"由日志之外编写的技能引入的漂移"的部分——注册表会过期，
grep 不会。两条纪律让输出可用：先把每个缺口对照该家族的
`Member-specific` 列再判定是否漂移（缺席有时是正确的），再按该家族
的一致性模型解决它——`synced-duplicates` 意味着编辑每个成员，
`shared-core` 意味着编辑核心并检查指针。凡审计发现某条规则缺失于
需要它的成员，把它记录为一条指名全部成员的观察条目，而不是静默
修复它，使修正对下一次评审可见。若注册表尚不存在，从本次扫描构建
一个：审计的分组**就是**注册表的第一稿。节奏是每月一次而非每次
评审，除非库已经增长，或上次审计之后有新的家族成员被编写——一个
新成员总是值得一次审计（见 `skill-authoring.md`，「新技能」）。

**步骤 5 —— 应用。** 从副本开始，而不是从编辑开始：对每个持有
已批准/未上报项的技能，

**在把观察条目的事实性主张提升进技能之前，先对照现行系统核实。**
观察条目记录的是一个会话看到的东西；技能陈述的是为真的东西。把
前者逐字提升为后者，会把样本洗白成规则，而该规则随后活得比每一次
察觉的机会都久。

实测：一条以定论口吻陈述的条目称，某文档的 `balance` 字段
"is always 0 in this org"，因此不能用于检测未结款项。它差一点被
逐字提升。对现行 API 的一次查询表明该主张为假——`balance` 在
`pending` 状态的文档上被正确填充。原会话只抽样了 `approved` 文档，
在那个状态下，供应商系统无论实际付款如何，都报告完整的
`amountPaid` 和为零的 `balance`。观察条目是诚实的，样本是不具代表
性的，二者之间，这是常态关系。

因此，在关于外部系统的事实主张进入技能之前——一个 schema、一个
枚举、一个字段的行为、一条转换规则、"X 恒为 Y"——重新运行能证伪
它的最小查询，并把样本扩展到原会话恰好看到的那个状态之外。凡评审
时系统不可达，提升该主张时**带上它的出处**（"observed on N
documents, all in `approved` status"），而不是当作事实，使下一个
读者知道什么需要复查。代价是一次查询；替代方案是一条恰在没人抽样
过的情形下出错的规则。条目引用的一条命令也是这一类的主张；它的
`commands_verified:` 子句（`observation-log.md`）说明是否有人运行
过它。

凡一条已批准项的目的地是上游报告——针对他人维护的技能的 issue
或 PR——起草那份报告**就是**对它的应用步骤，所以
`references/skill-authoring.md` 的反馈预检在这里、在草稿写成之前
运行：跨上游 issue 与 pull request 的重复搜索、维护者偏好的渠道、
上游 HEAD 核实；预发送闸门与主张核查（同一文件）对完成的草稿运行。
一个没有调用点的预检会在发送时才运行，那时草稿已被暂存并被列为
未完成项，而那正是发现重复代价最高的时刻。一个空的重复搜索，只有
在阳性对照之后才放行草稿：搜索一个你确定某个既有 issue 包含的
词，若连它也返回空，说明搜索坏了，而不是干净。

**已发布技能的输入比日志多，输出也不止一份暂存副本。** 对任何
发布到公开仓库的技能，在暂存它的前后运行以下四轮；每轮都产出摘要
要携带的东西。

1. **先合并上一周期的发布分支。** 若上一次评审切出了
   `release/vX.Y.Z` 分支并已在本地安装一周，本仓库的第一个动作就
   是合并决策——而且它先于新的暂存，因为本周暂存的一切，都暂存在
   合并结果之上。**仅当分支上的每项变更，要么有一周自然使用的
   记录，要么有本次评审中按声明的通过标准运行的合成检查时，分支
   才合并。**测试周是容器；检查才是证据。干净的一周是关于"该周
   活动恰好触及的变更"的证据，对其余部分是沉默，所以没有投诉证明
   不了任何东西。合并报告列出每项变更及其证据——自然使用过（在
   何处），或检查已运行（夹具与结果）——既无前者也无后者的变更不
   合并；它留在分支上再等一个周期。检查本身来自该分支的测试计划
   观察条目，按流程，它已在本次评审的队列里（见下）。
2. **阅读仓库的开放 issue 与 pull request。** 它们是与观察日志并列
   的评审输入——评审是"纳入一项贡献不额外花费成本"的唯一时点，而
   一个只被监视的频道，是一个会与下一次同步相撞的积压。列出每个
   开放 issue 与 PR，并对每一个分类：**立即纳入**（include now）
   （文档级修复、规格清晰的缺陷修复、与当前规则一致的变更）、
   **测试分支**（test branch）（对片段、流程或激活的行为性变更，
   以及任何改变代理在会话启动时行为的东西），或者**否决，附原因**
   （decline, with the reason）。把立即纳入集应用到暂存副本——
   **按类别并入，而不是按行号。**一份报告列出的是它的作者恰好
   遇到的实例，这是报告者唯一能度量的东西；完备性是类别的属性，
   只对持有整棵树的人可见。编辑之前，把报告描述的类别 grep 整个
   捆绑包，并修复每一处命中：报告给出诊断，树给出范围（并入同一次
   发布的三个报告分别指名一、二、八处；类别实际有四、三、十一处）。
   报告中的完备性主张——"恰好那两处"、"早先修复漏掉的那一处"——
   是报告者的范围，不是发现，而且它被论证得越仔细，就越压制那一次
   能定案的 grep，所以把这个短语当作运行 grep 的提示。把类别和计数
   记入提交和回复（"replaced at 4 sites; the report named 1"）：
   它告诉报告者，报告被当作类别读了，并给下一个人一个与现实匹配的
   搜索词——一个关闭的 issue 之下的部分修复，让其余部分继续存活，
   还抹掉了本可找到它的那个搜索词。凡类别可机械检查，留下一道
   检查——一行闸门、一条 lint 规则——而不只是一个修好的文件，使
   下一个实例在闸门处失败，而不是再次被报告。当评审对一项贡献
   **改写措辞**而不是逐字合并其 diff 时，合并报告把每个被改写的点
   列在原始条目旁边——与移动文件相同的逐点迁移核实，因为一次改写
   就是换了措辞的迁移，而"实质保留了"是一种感觉，不是检查（一次
   这样的改写丢掉了一个限定词，是被贡献者发现的，不是被评审发现
   的）。在暂存清单里记录分类，并对每个立即纳入项记录报告者的
   **GitHub 登录名与数字用户 ID**——发布运行需要二者，来写 GitHub
   能解析的署名尾注（`Co-authored-by: Name
   <ID+login@users.noreply.github.com>`，裸报告用 `Reported-by:`）。
   以提交正文行文形式写的署名，是平台看不见的署名，而这些 id 在
   这里收集廉价，在提交时刻收集尴尬。
3. **重新推导 README 与用户指南中的每一个数字与时长主张。** 行文
   中的计数是没有时间戳的派生内容：写下时为真，随每一周的使用和
   每一次合并的贡献漂移，而流水线里没有任何别的东西复查它们。枚举
   这些主张，各自从其来源重算——已记录观察条目数 = 迄今发出的最高
   id；被观察技能数 = 已安装技能数；贡献者、issue 与 PR = 仓库的
   有史以来（ALL-TIME）总数，不是开放数；使用月数或年数 = 从日志中
   最早一条观察条目的日期（`observation-log/archive/` 中最旧的
   文件）起算，不是从安装日期或仓库首次提交起算；安装数 = 技能
   目录清单报告的数字，随每次发布与其他 README 数字一起刷新，并在
   目录的安装遥测为 opt-out 时表述为下界——并在同一次暂存中更新
   它们。安装行指名的是安装器工具，不是统计其安装数的站点。把新
   数值带进评审摘要，使维护者看到什么变了。任何只有维护者会注意到
   的同类内容（一个 "recommended by" 列表、一个支持平台列表）在
   同一次扫描中检查。
4. **对每项变更分类，并暂存两次。** 进入本周版本的每项变更——社区
   项或观察条目——按与第 2 轮相同的测试，归为 **safe-to-main** 或
   **needs-test**。这产出两件工件而非一件：**main 暂存**（仅安全
   变更）与**发布分支暂存**（安全加需测试），命名为分支将成为的
   版本 `release/vX.Y.Z`，而被本地安装用于测试周的是发布分支暂存。
   二者都是 `skill-updates/` 之下带各自清单条目的暂存副本；评审
   不推送其中任何一个。

**常设规则——变更已发布技能的评审，升它的版本。** 当被暂存的技能
已发布，或已构建并在等待首次推送（无论你的发布流程如何记录那个
状态），评审在暂存的同时升版本：措辞用 patch，新规则或新小节用
minor，重构用 major。凡技能在 frontmatter 携带 `version:`，升版写入
暂存 frontmatter；凡版本只存在于仓库的清单（`plugin.json` 或等价
物），评审把预期的升版记入暂存清单条目（`PENDING.md`），由发布
同步应用。凡已发布技能既不携带 `version:`，也没有任何仓库清单持有
版本，评审在同一次暂存中补上字段和升版——`1.0.0`，或 README 或
发布历史所暗示的版本之上的下一个 minor——绝不把二者推迟给发布
运行，它无法给一个没人设定过的版本升版：失败形态是一道测试
"version unchanged" 的闸，两次都发现该字段缺席，同步停滞，双方
都指望对方去选数字。无论哪种方式，清单条目都要陈述升版。谁改了
内容，谁就拥有升版；发布者只检查它发生了——同步不得改动技能内容，
而一次评审让已发布技能增长一百行却版本号不变，是用版本号的存在
所要守护的唯一承诺，去发布一个变了技能。

**常设规则——分支与它的测试计划、它的挂起，由一条命令一并切出。**
切出发布/测试分支的会话，把其上每项变更分为"经一周使用自然使用过"
或"不太可能自然发生"，并对第二类写一份测试计划——每项变更的夹具、
步骤与通过标准——作为一条 `skill:` 列表指名该分支技能的观察条目，
以 `open` 创建并在同一回合搁置。这样 filed 的计划按流程到达合并
评审，而不靠任何人记住，且上面的合并步骤拥有它所要求的证据。一个
测试期测试的是该期活动恰好触及的东西；对其余的一切，它只是一次
延迟。**同一动作中，切出分支要把挂起写进发布流程的注册表**——
该技能的行获得 `under_test: release/vX.Y.Z`，附日期及其所替换的值
——而第 1 轮的合并在同一动作中清除它；原则就是观察条目状态规则
"在你行动的同一回合设置状态"，应用到另一个状态文件上。挂起阻止
发布周期把分支线作为版本同步到 `main`；若切出时不写它，就没有
任何东西会写，而它的缺席与"未在测试"无从区分。

三次写入，各自被规定为独立的规则，正是该动作只带着它碰巧记得的
写入被执行的原因（实测两次：第一次，一条分支带着测试计划切出而
没有挂起，挂起在下一次运行中从暂存台账和被搁置的观察条目重建，
输出中没有任何该机制失效的痕迹；随后两天，下一条分支带着测试
计划切出，既没有挂起也没有清单条目，注册表仍指着前一个被放弃的
分支，两处都由另一个会话在一天后修复）。按第二次违例规则，补救是
结构性的：**切出动作是一条脚本化命令，它的副作用就是那三次写入**
——带清单条目的暂存锚点、注册表挂起、被搁置的测试计划观察条目
——并且三个目标中任何一个不可写时拒绝运行。脚本本身住在发布
流程里，后者拥有三个目标中的两个；本技能陈述其输出必须满足的
契约，以及让契约有牙齿的读者侧规则。**缺失的挂起字段是一个断言，
不是默认值**：曾经携带过挂起的行，记录它何时被清除、被哪次合并
清除，所以"没有字段"与"没人写字段"可以区分。发布周期**交叉核对
该技能的暂存目录**，寻找比该行的最近清除日期更新的 `release/`
暂存，发现时询问而不是假设。而本次评审的对账闸门（步骤 1）把
没有清单条目的 `release/` 形状暂存，当作摘要第一行的闸门失败，
绝不当作一个可静默重构的副本。

**合并评审是固定的星期几，锚定在安装上，而不是切出上。** 合并
决策在发布会话中做出，该会话在固定的星期几运行；所以合并评审是
紧跟分支线**安装**（INSTALL）之后至少几个工作会话的那个发布
星期几（维护者的实测选择：周一安装 → 同一周的那次会话，四天
之后）——不是"切出日期加七"，那是对错误事件做的算术，落在算术
所说的那个星期几上（实测：一份测试计划、一条清单条目、一行注册
表行和一份摘要全都指名同一个日期，一个周日，被维护者纠正为前一
个发布星期几）。测试计划的 `parked_until:` 显式指名那个星期几的
日期，而该日期的每一份其他副本——清单条目、注册表行、摘要——
都以同样的方式派生，所以它们不会不一致。凡安装落在周内偏晚
（距该星期几不足三天），评审顺延到第二个这样的星期几；切出者在
测试计划观察条目中一次性陈述选了哪一个及原因，其余副本跟随它。

**常设规则——评审对该工件开启冻结。** 当用户开始评审一份暂存
技能、一条发布分支或一份 diff，停止在其上产出新状态。评审期间
发现的缺陷被报告，而不是被应用——"在你正在读的东西里发现了 X；
现在修，还是留到之后？"——因为重新评审的成本是评审者的，所以
选择权是他们的。每个评审周期，一个工件一个版本：如果必须有变，
明确说明前一版本已被取代，并指名要重读什么。优先选择不可变的
评审工件——写成文件的 diff 可按读者的节奏评审，且不会随后续的
工作失效——并首先提供它，而不是把它作为补救。把修正排在评审
之后，绝不排在它前面。（实测：一条发布分支在一个下午被切出、
折叠、合并、两次变基、改版本号、重写提交信息，而维护者正试图
评审它；他收到的每个回答所描述的状态，在他采取行动时已不存在，
那条分支未被使用就被删除——内容幸存，只是因为它被单独暂存进了
工作区。）有人在评审时做的工作不是并行；是对同一对象的争用，
而每一次修订，都让评审者的注意力从头再花一遍。

**播种之前，枚举该技能的每一份暂存副本，无论它在现行中是否存在。**
`find "[workspace folder]/skill-updates" -maxdepth 2
-name "[skill-name]" -type d`（用 `find`，绝不用裸 glob），并对每个
命中与现行做 `diff -rq`——不只是今天的锚点。下面的存在性检查
定义于*现行*文件的暂存副本，所以它对从未上线的草稿结构性失明，
而那正是最易丢失的工作。它咬人的两种方式：一个技能"从零"编写的
同时，一份同名的未安装草稿已携带新文件缺少的规则；一个技能从
现行播种的同时，一份更早的暂存草稿持有现行从未收到过的一整个
小节——安装新副本会把它丢掉。对账闸门状态 (c) 的一个命中，就是
本次暂存的基底，正如闸门所说；状态 (d) 的一个命中先合并到现行
上，合并结果就是基底。

先选锚点：若 `[today]/[skill-name]` 已经存在，应用交付章节下的
同日规则——整合另一位写入者的待定副本，或给安装后的第二轮一个
带区分标识的锚点——并把那条路径放进下文的 `s=`；守卫行拒绝在
既有锚点上播种。

```bash
# Stage the FULL skill directory (SKILL.md + references/, scripts/, assets/),
# not SKILL.md alone. From a read-only mount, mkdir + per-file cp + chmod is
# the only verified sequence for trees (cp -R and cp --no-preserve=mode both
# fail creating files inside copied subdirectories — see skill-authoring.md
# editing rule 6):
live="<absolute path to the live skill directory, no trailing slash>"
live=$(cd "$live" && pwd -P) || exit 1   # a symlinked skills entry: find descends nothing, cp -R copies the link
s="[workspace folder]/skill-updates/[today]/[skill-name]"
[ -e "$s" ] && { echo "anchor exists — apply the same-day rule (Delivery) before seeding"; exit 1; }
# live may be a clone; the staged copy never carries its VCS metadata
find "$live" \( -name .git -o -name .hg -o -name .svn \) -prune -o -type d -print | while IFS= read -r d; do mkdir -p "$s/${d#$live}"; done
find "$live" \( -name .git -o -name .hg -o -name .svn \) -prune -o -type f -print | while IFS= read -r f; do cp    "$f" "$s/${f#$live}"; done
chmod -R u+w "$s"
diff -rq -x .git -x .hg -x .svn "$live" "$s"      # must be identical before any edit
[ ! -L "$s" ] && [ "$(stat -c %i "$live/SKILL.md" 2>/dev/null || stat -f %i "$live/SKILL.md")" != "$(stat -c %i "$s/SKILL.md" 2>/dev/null || stat -f %i "$s/SKILL.md")" ] || { echo "staged path is live under another name — not a copy"; exit 1; }
# then make EVERY edit against the staged path
```

**从**当前**状态播种，而对共享工件来说，当前状态是上游——不是本地
文件。** 那条 `diff` 证明暂存副本从现行出发；它对"现行是否最新"
保持沉默，而且恰在它看起来在守卫的那个状态里平凡通过。"编辑副本，
而不是原件"回答的是你可能损坏什么，不是你在什么之上构建。对任何
有上游的技能——一个它被安装或刷新自的仓库，包括用户自己从多台
机器或多个会话向其提交的仓库——现行目录本身就是一份不宣布自己
落后多远的副本，而一个过时的本地文件看起来与新鲜的一模一样。

所以播种之前，抓取每个即将被编辑文件的上游版本，并与现行 diff：
相同 → 从现行播种并记录该版本号；有分歧 → 先拉上游，从它播种，
并重新检查观察条目是否已在彼处被解决，因为"以不同且更好的方式
修好了它的维护者"是常见情形。正在编辑技能的会话与其他任何并行
写入者无异，所以这就是流程已对共享日志要求的写入时状态检查，
应用到代理自己的工具上。在步骤 8 摘要中指名播种所自的版本号。

同一次抓取还能定两件事。它定**小节级出处**——被编辑的段落是上游
内容还是本地新增——这正是审批策略在上游报告与分叉本地编辑之间
路由所需要的。而**把上游判定为不可达之前，需要一次阳性对照**：
在断定网络是问题之前，先抓取一条已知存在的路径（仓库 README），
因为对猜出来的技能路径的 404，加上对 README 的 200，说明路径假设
错了。没有这次对照，那个看起来诚实的结论是 "upstream unreachable,
seeding from live"，而这是同一个失败，经由一条让人感觉勤奋的
路径到达。

片段里有两个细节是承重的，而且都曾在早期版本中写错。剥前缀时
**不带**尾斜杠——`${d#$live}`，不是 `${d#$live/}`。带斜杠的模式
对每个子目录都剥得正确，却在唯一那条没有尾斜杠可匹配的路径上
失败：顶层目录本身。`mkdir -p` 随后在整个绝对现行路径上、每技能
一次地在暂存目录*内部*重建它。并且在两个 `read` 循环上都保留
`IFS=`——工作区路径惯常含空格，没有它，循环会把它们弄坏。

**若 `diff` 报告了任何东西，不要编辑。** 在拒绝 `unlink` 的挂载上，
`rm -rf` 和 `rmdir` 在多余的路径上都会失败，所以清理需要环境的
删除授权：**对目标目录请求删除授权（`allow_cowork_file_delete`
或等价物），然后删除——绝不改名挪进保留文件夹。**然后重跑 diff。
保留文件夹把一次删除变成用户必须记住的第二个延迟任务，队列无声
增长而没有消费者。在定时或自主运行中，以同样的方式请求授权；若
权限流在那里失败，把文件留在原处，在报告中命名为 "pending
deletion — grant needed"，并且仍然绝不把它们改名挪进保留文件夹。

该序列的存在，是为了让现行路径永不做编辑目标、暂存副本可证明地
从现行出发、且一份更早日期的过时暂存副本不会被误捡。**写任何
东西之前先做存在性检查：**对暂存副本 grep 每条建议改进的实质内容，
并分类为已应用 / 部分应用 / 未应用——`open` 状态不是"工作尚未
完成"的证据，而把一条已应用的观察条目应用到一个此后被精修过的
小节上，是以改进之名让技能回退。分类逐点进行，逐点指名覆盖它的
那一行：只有每个点都有它的行，条目才算已应用，一个没有行的点就
使它部分应用，无论标题如何暗示；一个合并多个条件的点（A 且 B）
按每个条件一个点计数（`observation-log.md`，「在解决、否决、修复
或引用之前先读完整正文」）。同时对照 **Issue** 与建议做分类：
`already-applied` 需要二者——建议的实质在场，**且** Issue 所描述的
失败不再可能发生。凡建议在场而失败仍可能发生，条目就是
`partially-applied`，无论建议要的是什么；对一条关于手动步骤或缺失
自动化的观察条目，测试就是一个问题——这次变更之后，还有人得
手工做这一步吗，如果自动化存在，是什么在调用它？（实测：一个
已经做了该步的脚本存在；观察条目只要求把它写进文档；段落写了，
条目标了 `actioned`，没有任何东西调用那个脚本，它本要清掉的积压
重新堆起来，直到用户问为什么——被编辑技能自己的规则"手工启动的
检查不是检查"，距那处编辑只有几段。）观察条目因它的问题而关闭，
不因它的提案而关闭。把已应用条目标记为 `actioned`，resolution
注明先前某个会话已应用了它们，并放过该小节。`partially-applied`
条目在 `resolution:` 中指名剩余部分（"suggestion applied; issue
still open: <what can still happen>"），并在同一回合把该剩余部分
记录为它自己的一条观察条目——`observation-log.md` 的承载条目
模式——使它在本条归档后留在队列里。当本次运行自己应用剩余部分
时，只添加没有行的那些点，绝不复述已有行的——在场规则的第二份
副本会与第一份漂移——并在 resolution 中指名二者：先前会话应用的
点，与现在新增的点。然后产出更新后的 SKILL.md：把洞见整合进它们
所属的小节（绝不在底部追加观察条目列表）；保留结构、语气与署名；
把新规则放进它们逻辑上所属的位置。遵循
`references/skill-authoring.md` 的编辑规则（现行文件为基底、暂存、
覆写前 diff）。

为技能的读者改写新增内容，而不是照抄观察条目的行文：规则先行，
一句一个意思，每次变更至多一个示例（`references/skill-authoring.md`，
精简内容——示例要保留；裸规则比带上下文的规则更容易被违反）。
对照观察条目复查草稿，使更短的措辞保留每一个必要的行为与验证
步骤。

**伸缩说明——应用阶段很大时扇出。** 当应用阶段跨越约 3 个以上
技能或约 10 条以上观察条目时，把步骤 5 委托给按技能聚类的并行
子代理，而不是在主会话中应用一切。数分区，不数条目：一批编辑
全部落进一个文件时没有分区，就地应用；观察条目计数此时是上下文
预算信号，合并时的检查仍然运行。给每个子代理的任务书：要读的
观察条目 id（文件）、只读挂载路径、暂存路径、播种序列**作为上述
步骤 5 代码块的逐字片段**（绝不用行文描述——它的两种失败模式都
是重构错误）、观察条目相互依赖的整合逻辑（哪条观察条目并入、精化
或折叠进哪条——父会话必须逐聚类显式陈述这一点，否则顺序应用
观察条目的子代理会产出补丁摞补丁，而不是连贯的最终状态）、开源
技能的保密规则、在其第一次写入技能文件之前先在自己的上下文里
阅读 `references/skill-authoring.md` 的指令（父会话的加载不结转）、
**绝不在未加引号的 frontmatter 值里引入 `: `** 的规则（扩展
`description:` 的子代理，是暂存技能的 frontmatter 停止解析的常见
方式——见 `references/skill-authoring.md`，交付前闸门第 4 项）、
任何 Python 检查不得在暂存树留下字节码的规则（那里的一个
`__pycache__/` 是交付前闸门会拒绝的东西，而且在没有删除授权就
无法 unlink 的挂载上尤其如此）：编译检查运行为
`PYTHONPYCACHEPREFIX=<scratch dir outside the staged tree> python3 -m py_compile <file>`
（或经 `python3 -c` 的 `compile()`），因为无论
`PYTHONDONTWRITEBYTECODE` 说什么，`py_compile` 都会写它的 `.pyc`
——那个变量只管导入机制——所以 `PYTHONDONTWRITEBYTECODE=1`
适用于被执行的脚本，而交付清扫保持兜底；一个明确的删除范围——
子代理只能按路径删除自己创建的文件，且只在自己目录之下，绝不对
一个它没有创建的目录运行递归删除；这一轮是内容轮还是重排版轮
——绝不在一次编辑中二者兼有，并附此前（「交付」）拍的暂存目录
快照——以及一条明确的规则：子代理不改变任何观察条目的状态，也
不写观察条目：值得记录的发现放进子代理的最终报告，由父会话写入，
因为从两个视角看着同一个任务的两个写入者，会把一个发现记录两次，
而合并关于同一个事实的两条条目，不是重复 id 检查所做的那种重
编号（跨分片重复，见下文）。状态标记、归档与观察条目写入，保留给
父会话。派发之前，父会话对输出树拍快照（带大小的清单），并逐
聚类记录暂存副本对现行的 `diff -rq` 及其播种时间，把二者放进该
聚类的任务书：一个在第一次编辑前发现不同状态的子代理，不是第一
写入者，要报告该 diff，而不是在它之上构建。快照还使"被另一个
写入者删除的同族工作"可被检测，而不是在合并中无声缺席。每份
任务书都要求最终报告在返回之外，也写入临时区的一个文件，使一次
随中断对话丢失的交回，可以通过读那个文件恢复，而不是通过恢复
代理。中断之后，在再次派发任何东西之前，把暂存树对照派发前的
快照重新列出，并把无法解释的变更当作该聚类的先前运行，绝不当作
干净的种子。凡宿主提供每代理沙箱或工作树，并行写入者使用它们。
**会写入的阶段，从一开始就按写入阶段下达任务书**，任务书中逐字
引用用户对写入的授权——一份任务书覆盖分诊与应用，或为应用阶段
另起一个全新的子代理——绝不用一份后来由父会话一条消息放宽的
只读任务书。失败形态：权限分类器把"代理间对一份禁止写入的任务书
的放宽"读作洗白并拒绝写入，而另一个代理重试的同一编辑，被当作
绕过再次被拒。凡用户的指令是结果层面的（"include everything
that needs no testing"），扇出之前先取得用户对写入的明确放行，
并在每份任务书中引用它。父会话在任何状态簿记之前，对**每一个**
暂存技能运行 `scripts/validate-skill-bundle.py`——子代理的"完成"
是关于它自己编辑的主张，而校验器是唯一看得见那些编辑所产文件的
检查；若在簿记之后运行，一次失败就意味着回退 `actioned` 标记。
原则是：应用阶段跨技能天然可并行，而簿记必须有唯一的所有者——
沿那条接缝切开工作。

**委托出去的对抗性评审，需要其核心主张所依赖的未变更文件。**
当一个修复被送给第二个代理评审时，自然的任务书是被改的文件、
diff 和一份日志。当修复的核心主张是关于它**没有**变更的东西时，
这恰恰是错的：一个关于调用方如何行为、某个默认值是什么、某个
其他文件保证了什么的假设。

实测：一位评审者找不到"该修复假设了其行为的那个调用方"，不得不
把它最重要的那一个发现——核心假设是否成立——作为"无法验证"
返回。次要发现都正常回来了。评审运行了、产出了输出，却在它为之
存在的那一件事上静默失败。

所以从**主张所依赖的东西**构建任务书，而不是从变更触及的东西：
用一行指名修复的支撑性假设，并纳入确认或反驳它所需的每个文件，
无论改没改。要求评审者把"不可核实的核心主张"作为任务书的失败来
报告，而不是作为一条发现——否则"无法验证"被 filed 在次要发现
旁边，读起来像一次完成了的评审。

**编排者拥有一次合并时的校验轮。** 把工作拆给并行工人，同时把
校验面拆散了，而这一拆并不干净：局部检查分得很整齐，全局不变量
完全分不开。任何定义在整个交付物之上的属性，在工作被划分的那一刻
变得不可核实，并且无论每个工人多么严格都保持不可核实——每个
子代理都能交回一批可证明干净的货，而合并后的工件仍然是错的。要
假设工人看不到的一切，恰恰是缺陷所在。所以在交回齐全之后、在
任何东西被标记 actioned 或交付之前，对合并后的结果做全局重验。
至少三项检查：

1. **跨分片的重复与冲突**——两个拿到同一源信号的子代理，会独立
   产出近乎相同的输出，而任何一方的自检都无法触发，因为谁也
   看不见谁。在这里，这包括同一条规则以分歧的措辞落进两个技能的
   小节，以及同一技能的两份暂存副本出现在同一天的文件夹里。
2. **跨分片的词汇与约定一致性**——任务书欠规格之处，每个工人在
   本地、说得通地、各不相同地解决了它。这种不一致在任何单个
   分片内部不可见，在整个集合之上一目了然。
3. **合并总量对计划的符合性**——每条观察条目被路由、计划中的
   每个技能被暂存、计数吻合、没有多技能观察条目只被应用到其
   列出技能的一部分（步骤 3，家族传播）。

4. **刻画，而不只是数值**——校验轮读起来自然是关于数值（计数、
   字段、总量）的规则，而在输出被表述为判断的地方最不成立：一个
   被报告的冲突、缺陷、风险或就绪裁定，没有可对照的单位，而一个
   错误的刻画因被*同意*而被消费，不留痕迹——一个错误的值，在被
   什么东西拿去计算时，倒是倾向于大声失败。任何将作为发现到达
   用户的子代理主张，必须在它离开会话之前，由父代理对照来源做
   抽查，粒度以能使主张可证伪为准——一次 grep 通常就够。结构性
   触发器：你正要写一句话，把问题归因于一个你自己没有读过的
   东西，就在那一刻。要求子代理随主张一起返回证据（文件、行、
   命中的字符串），使检查廉价；一条没有可定位证据的主张，是一条
   要去核实的主张，不是要去转达的。

对任务书的推论：要求每个被委托的代理以一节"任务书未覆盖的决策"
收尾。那一节是任务书缺陷被发现的方式——一个静默解决了歧义的
代理，把一个可修复的规格缺陷变成了不可见的不一致。而当两个独立
的代理标记了同一个歧义时，缺陷是任务书，不是代理：修任务书并
重新下发，而不是去裁决那两份产出。

**步骤 6 —— 重新扫描，再标记 ACTIONED。** 在写入任何状态之前，
重新枚举 `observation-log/`，并把这份清单与步骤 1 构建的文件列表
比较。队列是一个共享、只追加存储的快照，而本流程中每一个下游的
计数与一致性检查，都是对队列而不是对目录计算的——所以一个过时
的队列，产出一份连贯、自信且不完整的摘要，没有可供绊倒的内部
矛盾。新清单中不在步骤 1 列表里的文件，是运行期间到达的：它们是
OPEN，且从未被分诊。对每一条做分类，而不是仅仅计数：(a) 它指向
的技能的、步骤 5 的暂存副本在本运行中仍然开放 → 把它折叠进去并
处置它（这是常见情形——一个刚触碰过某技能的评审，恰好与最可能
正在使用该技能的那些会话运行在同一个窗口里，而这正是漏掉代价
最大的情形，因为下一次评审的基底，随之变成一份没有人重新推导过
出处的暂存副本）；(b) 否则 → 为下一次评审留 OPEN，并列入步骤 8
摘要的 "arrived during this run" 行。绝不让差值静默通过，也绝不从
id 计数器推断它——一个单调递增的 id 浮现出高于扫描最大值的编号，
是一个副作用，不是一个检测机制。该检查是对步骤 1 列表按行求
集合差，两条路径都在本次调用中重新推导，并对新清单加计数守卫：

```bash
d="C:/Users/Administrator/.zcode/skill-observations/observation-log"
l="C:/Users/Administrator/.zcode/skill-observations/review-step1-list.txt"
now="C:/Users/Administrator/.zcode/skill-observations/review-step6-list.txt"
find "$d" -maxdepth 1 -name '*.md' | sed 's|.*/||' | LC_ALL=C sort > "$now"
n_now=$(find "C:/Users/Administrator/.zcode/skill-observations/observation-log" -maxdepth 1 -name '*.md' | wc -l | tr -d ' ')
n_list=$(wc -l < "$now" | tr -d ' ')
[ "$n_now" -eq "$n_list" ] || { echo "RESCAN COMMAND BROKEN — $n_now files, $n_list listed"; exit 1; }
echo "arrived:"; LC_ALL=C comm -13 "$l" "$now"
echo "gone:";    LC_ALL=C comm -23 "$l" "$now"
```

信任它之前先做阳性对照：在步骤 1 的列表写好之后，往该目录的一个
副本里创建一个一次性 `.md`，确认 `comm -13` 点了它的名——一个坏
掉的比较，能在不动任何计数的情况下发明或隐藏一个差值。评审自身
自步骤 1 以来归档的文件，显示在 `gone:` 之下；这是预期内的，只有
无法解释的离开才是一项发现。
同时在新清单上重跑步骤 1 的重复 id 检查：这次重扫与步骤 1 并不
冗余，因为它要抓的冲突，正是运行*期间*产生的那些（实测：步骤 1
发现并重编号了一个冲突；步骤 6 的重扫发现了第二个、新的冲突——
由一个并行交互会话在运行中途写入，用的 id 是目录和 floor 一个
小时前就越过了的——任何更早的步骤都不可能看到它）。把这一步当作
重复工作裁剪掉的运行，删掉的是唯一一道"位于它所检查的写入之后"
的检查。

然后，在每条已应用观察条目的 frontmatter 里设置
`status: actioned`、`resolved: YYYY-MM-DD`（今天），以及
`resolution: "Staged for [skill-name] at skill-updates/<anchor>/[skill-name] (weekly review)"`
——只编辑那个文件里的那几个字段。步骤 5 判为 `partially-applied`
的条目以同样的方式标记，剩余部分在 `resolution:` 中指名，且其承载
观察条目已经写好（步骤 5）：一条已解决的条目，是后续任何步骤都
不会再读的唯一东西，所以剩余部分必须住在队列里，绝不住在已解决
的文件里。resolution 刻意指名暂存路径：此时的 `actioned` 意为
"已应用到一份暂存副本"，而交出一件工件与它被采纳，是两个不同的
事实——前者绝不能关闭后者的状态。暂存路径正是让下一次评审找到
"每一条工作仍坐在未安装状态"的观察条目的东西（见下）。`resolved:`
日期是承重的：归档以它为闸（文件仅当它早于今天才归档），所以一个
没有日期的标记，会破坏跨会话的宽限期。绝不在同一会话内归档——
之后某一天的下一次写入会归档它们。

**步骤 7 —— 时间戳。** 把今天的日期写入
`skill-observations/last-review-date.txt`，然后用
`completed YYYY-MM-DD` 覆写
`skill-observations/review-started.txt`。一次结果未知的时间戳写入
——调用超时、设备桥断开——由本次运行核实，绝不推给用户：步骤 8
摘要与任何通知，把它报告为"未确认——在下一次可达调用时，或由
下一个会话的启动核实"，绝不是一个留给用户检查的文件。在下一次
触及工作区的调用中，用一次对两个文件的读取核实它；若运行先行
结束，会话启动步骤 3 对 `last-review-date.txt` 和
`review-started.txt` 的读取，就是那次核实。

**步骤 8 —— 交付并总结。** 暂存更新后的技能（见下方「交付」）。
把完整记录用下面的模板，存入
`[workspace folder]/skill-observations/reviews/[date]/REVIEW.md`。
在聊天中报告变更了什么及其验证，随后是最多三个剩余的后续步骤，
按步骤 3 的格式。链接该记录，以供完整对账。区分提议的、已暂存的
与已安装的变更；光一个观察条目计数不是结果。记录被保留：没有任何
步骤修剪 `reviews/`，旧的记录归用户删除。

步骤 8 以一行 **"N bundles staged, N bundles presented"** 收尾，
两个数字不一致时，运行不结束。二者都是实测的：staged 数来自本次
运行打包的捆绑包，presented 数来自呈现调用返回的已交付文件列表
（在没有这种调用的环境中，来自聊天中列出的暂存路径）——绝不来自
对"已呈现过"的记忆。差值通过在一次调用中呈现缺失的捆绑包并重新
计数来闭合。模板：

```markdown
## Weekly Skill Review Complete — [date]

Updated skills ([N] observations, [N] principles applied):

**[skill-name]** — [1-sentence change summary]; observations #[N], #[N]

**[workspace file written directly]** — [its diff] (Delivery, "Non-skill
files are split by owner"); or "none"

### Observations Actioned
[numbers and titles]

### Family coherence
[each multi-skill observation: applied to all listed skills, or partially
applied with the outstanding skill named — never left implicit]
[drift audit: gaps found per family, and how each was resolved]
[N observations logged without a sibling check]

### Published skills
[per published skill: release branch merged / held, with each change on
it and its evidence (exercised naturally where, or check run and result);
merge review date = the publishing weekday at least three days after
INSTALL, derived per Step 5 ("The merge review is a fixed weekday");
a user-decided restructure staged: listed FIRST, with the line
"published skill — install and the release are your call";
community items included now, routed to the test branch, or declined
with the reason; README and user-guide counts re-derived, old → new]

### Parked
[one line each: #id — title — unparks when: [condition]; plus any entry
whose condition has been met and was returned to the queue this review]

### Arrived during this run
[from the Step 6 re-scan: #id — title — folded into [skill] / left OPEN
for the next review; or "none" — the line is never omitted]

### Log integrity
[duplicate ids renumbered and any floor lag (Step 1), each with the
writing sessions' session_context and date; `skill:` names normalised for
bucketing (Step 3), old → new; `skill:` entries in qualified and bare
form (Step 3), N / M; inbox entries drained (Step 1), or "inbox
not read: <reason>"; or "none"]

### Skipped (needs manual review)
[items with reasons]

[N] bundles staged, [N] bundles presented
```

**仅交互模式：**等待用户确认后，再进行其他工作。**在定时自主模式
下，不等待**——没有可确认的用户，而这是定时运行必须始终到达的
步骤，因为运行正是在这里暂存它的输出、记录它的摘要。在暂存更新
后的技能、记录摘要并对账 staged/presented 计数之后收尾。一个阻塞
在不可能发生的事件上的步骤，把运行唯一的交付物变成了挂起。

## 约束

- 不修改观察条目文件中 `status`、`parked_until`、`resolved` 与
  `resolution` 这些 frontmatter 字段之外的任何东西——外加审批策略
  指名的那一种情形下的 `reference:`（已发布技能的、由用户决定的
  重构，保持 `open`，并把暂存路径记录在那里）——**有一个例外：更正
  被错误记录的目标。**`skill:` 和 `proposes_skill:` 在写入时被校验，
  而该校验可能给出错误的答案：一个处于过时检出中的会话，或一个
  对照着错误安装做解析的会话，会把一个存在的技能判定为缺席，从而
  把观察条目 filed 到 `proposes_skill:` 之下。实测：七条条目基于
  "该技能不存在"的诚实判断，以 `skill: []` 和
  `proposes_skill: [<name>]` 记录——它存在，存在于该会话的检出落后
  160 个提交的那些提交里。放着不管，它们就坐在一个已存在技能的
  新技能候选之下，之后的每一次评审都以同样的方式重读它们。一个
  确立了"目标确实存在"的评审，可以更正那两个字段，并把更正记录在
  `resolution:` 里。正文中的其他一切不变。
- 评审中不创建新技能——把候选记录下来，让用户经 skill-creator 去
  处置。唯一的例外是针对只读或易变目标的 `{skill}-extras` 伴生技能
  （步骤 2）：它是已批准增量的路由容器，不是候选技能，在用户选择
  那条路线时创建它，就是应用观察条目的一部分。评审对它仍然只
  暂存、绝不安装；而且它仍然需要那条路由条目，否则没有任何东西
  加载它。
- 不确定如何整合某条观察条目 → 跳过它，并在摘要中说明。
- 以与开源同等的严格程度，对待内部观察条目。

## 交付更新后的技能

**为延迟发送而提前起草的消息，陈述着此后已经改变的状态。** 凡
交付消息、提交正文或摘要是现在起草、以后发送的——一次被等待期
闸住的运行、一次自动发送、一次排队的交接——它的*实测*值通常在
发送时从现行输出正确地填入。行文不是。起草时写下、指名某个其他
分支或提交还差什么的段落，会被逐字发送，并以它身旁那些实测数字
的权威被阅读。

实测：一份模板的行计数、字节计数与证据数字在发送时全部正确，
旁边却有一段固定文字，说某个分支仍在等待一次变更，并描述合并时
必须发生什么。到自动运行发送它的时候，那个分支已经落地，该变更
已经存在于交付结果之中。

所以，在为之后发送而起草的任何东西里：**只陈述发送时实测到的
东西，否则什么都不陈述。**关于其他分支、提交、工单或会话状态的
主张，要么来自运行在发送时计算的值，要么删掉。写下时为真的一句话
不是安全的默认——它是消息中没有任何东西会复查的那一部分。

把每个更新后的技能保存到
`[workspace folder]/skill-updates/[date]/[skill-name]/`——完整的
技能目录（SKILL.md 加上在场时的 references/、scripts/、assets/），
绝不仅是一个 SKILL.md——并用环境提供的任何文件呈现能力，把它
呈现出来以供评审与安装（见 `references/environments.md` 的环境表）；
在没有这种能力的地方，在聊天中报告暂存路径与变更摘要，让用户从
那里评审与安装。绝不直接写现行技能，即使技能目录可写——只暂存
是评审环路的一项刻意设计的安全属性（没有用户的签字，任何东西都
不上线），不是文件系统约束，并且它对技能是绝对的，因为技能有一
个安装步骤；非技能文件按所有者拆分（见下）。**每一个**暂存技能
都被打包成 `.skill` 捆绑包，并作为该捆绑包呈现——所有技能一种
交付格式，无论大小或文件数。按工件形状切换的格式，为一件事造出
两种约定，和一条每个消费者都要重新推导的边界；一种格式在单文件
技能上没有成本，并在另一端消灭整类"裸 SKILL.md 静默截断多文件
技能"的失败。交付前闸门（作为呈现前的最后一步运行）：(1) 对暂存
的 SKILL.md 正文 grep `references/`、`scripts/`、`assets/` 路径，
凡被引用的文件缺失于暂存集，交付失败——一个反引号路径，只有在
**非限定**时才算本技能自己的，所以属于其他技能的文件被引用为
`<skill-name>/references/<file>`，并不受影响地通过；那层限定就是
约定，而把一个真正的交叉引用改写到反引号不再以该前缀开头，是为
满足 linter 而伪装引用，不是修缺陷；(2) 呈现的工件是捆绑包——
裸文件链接过不了这道闸——并且每个暂存捆绑包都被呈现（步骤 8 的
staged/presented 计数）；卡片的数量绝不是少呈现的理由，因为一次
调用装得下全部，而每张卡都是用户反正要做的安装决策；(3) 度量
每个暂存技能 frontmatter 的 description（折叠后的值，不是原始的
YAML 块），超过 1024 字符则交付失败，约 900 以上给软警告——对
集合中的每个技能度量，而不只是失败的那一个；(4) `name` 是
kebab-case、与目录匹配，并且 frontmatter 可解析；(5) 捆绑包的
成员路径使用 `/`，按原始字节检查（Windows 打包器写 `\`，归一化的
读取器会掩盖它）；(6) 恰好一个 frontmatter 块——第二个 `---` 块，
或紧跟在第一个之后的游离 `name:`/`description:` 行，是一个每项
字段检查按构造都会放过的重复头部；(7) 捆绑包中任何文本文件里，
代码之外（任意缩进的 fenced 块，包括嵌套在列表项之下的那种，以及
行内跨度），没有编辑残留：一行里或行文中的字面正则反向引用
（`\1`）、合并冲突标记、未解析的 `{{slot}}` 占位符——闸门检查的
是一次交付的形状，而这是唯一的内容断言，因为一次失败的替换，曾
以字面 `\1` 的形态通过了应用、闸门和安装。未解析占位符规则——
且仅那一条规则——对路径含 `template`（大小写不敏感）的文件，或
首行是标记 `<!-- template: slots intentional -->` 的文件豁免：在一
个本来就是给受托撰写者当模板的参考文件里，占位符是交付物，不是
残留。其余每条残留规则、其余每项闸门，仍对该文件运行，所以这个
豁免永远不会变成"跳过没人质疑的检查"的手工 zip。另有一项是具名
的人工阅读，不是断言：对已发布或已排队待发布的技能，对自上一棵
发布树以来新增的每个小节，运行 `references/skill-authoring.md` 的
保密层 9——理由以失败形态表述，示例跨行业。
`scripts/validate-skill-bundle.py` 断言全部七项，并打出一个格式
良好的捆绑包——凡 Python 可用即运行它。它还强制每个技能自己声明
的核心上限（其 frontmatter 的 `core_max_lines:`，或一个
`.core-ceiling` 文件——`references/skill-authoring.md`，精简内容），
并且**打包步骤绝不因上限失败而被绕过**：一个未通过自己声明的
上限的技能，被修剪回上限之下，把内容移入一个参考文件，并重新
校验——或者，凡上限高出修剪后核心的部分超过容差，把上限降到该
计数；没有声明上限的技能不可能失败该检查，只会被报告。为绕开
校验器而手工打捆绑包，正是该闸门要防止的那个失败（实测：三个
技能在"当时还是脚本里的常数"的上限使它们失败时，用 `pack()` 的
镜像被手工打包——其余每项检查都通过了，缺陷在那个常数，而绕过
是对它的错误响应）。凡捆绑包随附私有文件的公开摘录（本技能的
`references/starter-principles.md`），在这里也对那份摘录运行保密
扫描：它是捆绑包中唯一一个内容复制自私有来源的文件，所以编写时
的清扫永远看不到它。压缩之前，清扫构建工件（`__pycache__/`、
`*.pyc`、`.DS_Store`、`.~lock.*`）与版本控制目录（`.git/`、
`.hg/`、`.svn/`），并在之后读回归档清单，查泄漏的工件和路径
分隔符。**打包是对一个暂存技能的最后一次写入。**捆绑包是交付物，
所以打包之后对目录的任何编辑，都会留下两个版本：用户安装的
捆绑包，和下一次评审 diff 的目录。打包之后，捆绑包的成员必须与
暂存目录逐字节相等——`--pack` 校验这一往返，并在不匹配时非零
退出——而那之后的任何编辑，都意味着重新打包、重新检查后再呈现。
从只读挂载播种暂存副本时，先对暂存路径 `chmod -R u+w`——挂载的
只读模式随副本传播，目录如此，文件也如此。不要就地编辑技能的
文件——用户安装之前，任何东西不上线。**保留两份规则：**对任何
技能，`skill-updates/` 下只保留最近两份**已被安装**的暂存副本——
绝不修剪未安装的副本。两行之上那个不变式说，用户安装之前任何
东西不上线；而修剪最初不分青红皂白地数轮次，于是"收到同一技能
三份暂存更新而一份都没装"的用户——暂存不断发生而安装等待时，
这是一个合理的运行——丢掉了最老的那份，连同其中的可评审工作，
毁于一条读起来像整理的规则。先用对账闸门的比较给每份副本分类
（「以安装器 frontmatter 引号归一化的方式比较」——仅在该引号上
有差异的副本是 (a)）：只修剪返回 **(a) 完全相同** 或 **(b) 已并入**
的副本；状态 (c) 或 (d) 的副本是未安装的工作，无论多旧都保留，
并在摘要中指名，使它不会无形地累积。对可修剪的那些，**对目标
目录请求删除授权，然后删除——绝不改名挪进保留文件夹**（自主
运行中权限流失败时，把它们留在原处，并在报告中命名为 "pending
deletion — grant needed"）。该规则的辖域是暂存的技能副本，不是
日期目录：修剪一个目录之前，列出里面还有什么——一个装配脚本、
一个验证脚本、工作笔记——先把不是暂存技能副本的任何东西挪开，
或者留下目录，只修剪副本。一个在最老目录上正确触发的修剪，会
删掉其中的一切，而一个缺失的工具，要等到下一次需要它时才被
注意到，绝不会在删除的那一刻。规则数的是轮次，不是天数（同日的
第二轮是它自己的一份副本）。

**非技能文件按所有者拆分。** 本技能的评审在观察工作区中所拥有的
文件——`cross-cutting-principles.md`、`skill-families.md`、起始集
分诊参考、`activation-tiers.txt`、`checkpoints.log`、
`last-review-date.txt` 与 `skill-updates/PENDING.md`——没有安装
步骤，并且本流程的其他步骤已经在写它们。评审直接写它们：在写入
之前立刻重读该文件，并把它的变更作为对那次读取的补丁来应用，
绝不作为一个更早准备好的副本。步骤 8 摘要连同其 diff 列出每一个
这样的文件。更早一轮留下的一份它们的暂存副本或补丁，由下一次
评审以同样的方式应用，而不是作为安装指示结转。一个由其他进程
拥有并在运行时读取的文件，保持暂存，如下一段所说。失败形态：
暂存一个没有安装步骤的文件，把评审自己的写入变成一次等用户来做
的手工复制，而在有人照做之前，每一次运行都读着没有该变更的那个
文件。

**状态文件以补丁形式暂存，绝不以快照。** 这里说的状态文件，是
另一个进程拥有并在运行时读取的非技能文件——某个例程的注册表或
配置备注、一个指令文件。改变了它的评审，把它作为补丁暂存在
`skill-updates/<date>/_target-files/` 之下：对现行文件的一份统一
diff（`diff -u "$live_file" "$changed" > "<file>.patch"`），或者
带足以定位的上下文的变更行。它的清单条目记录暂存时现行文件的
字节数与 sha256（`wc -c < "$live_file"`；GNU 上 `sha256sum`，
macOS 上 `shasum -a 256`），对账闸门在重复任何安装指示之前复查
它（步骤 1，「暂存的状态文件按其记录哈希对账」）。失败形态：
每次运行都写状态文件，所以快照随下一次运行过期，而它"复制覆盖"
的指示，变成一次"删除自暂存以来写入的一切"的覆写，读起来却像
合规；一份过时的补丁，则退化为一个必须有人去解决的冲突。

**带日期的暂存文件夹是多写入者的。** `skill-updates/<date>/` 是
一个只按日期作键的命名空间，所以手动会话与定时运行都能写进同
一天的文件夹（实测相隔几分钟）。任何生产者都应假设自己不是当天
唯一的写入者：暂存一个技能之前，检查当天的文件夹是否已持有同一
技能的暂存副本——若有，做 diff 并整合，而不是覆写，并在清单中
说明。任何选择"最新暂存版本"的消费者（例如发布流水线的新鲜度
闸门），必须按内容解决，而不是假设存在单一权威生产者——若同一
技能的两份同日副本分歧，把冲突呈报出来，而不是让 mtime 说了算。
清单条目（见下）是出处标记：谁暂存的它、来自哪次运行、应用了
什么。同日检查还有第三种结局：当天的文件夹已持有用户**已安装**
的一份副本——它与现行 diff 干净，并且没有剩余的清单条目，因为
安装移除了它（仍存在的条目意味着另一位写入者的待定副本：如上
整合）。不要把第二轮播种进去：种子会与现行逐字节相同，`diff -rq`
闸门会平凡通过，而新一轮会继承一个自称已安装的清单条目。给第
二轮一个带区分标识的锚点（`<date>-<slug>` 或 `<date>.2`），带它
自己的清单条目，并且当保留两份规则修剪时，数轮次而不是天数。
锚点在步骤 5 播种**之前**选定——片段的 `s=` 行取那条带区分标识的
路径——而不是事后从本段落里发现。（实测：一个技能的第二轮应用，
在第一轮被安装的同一个晚上开始；按日期作键的锚点指向那份已安装
的副本，只有对清单状态的一次手工检查，阻止了在它之上播种。）

**先前的暂存状态是交付物的一部分——任何第二轮之前先拍快照，
并且绝不让重排搭内容的便车。** 暂存树不在版本控制之下，而种子是
流程唯一取的基线，所以对一份暂存副本的第二轮——一次后续的应用
轮、一次密度精简轮、一次用户要求的更正——会覆写评审者的 diff 所
需要的那个状态；对账闸门比较暂存与现行，它回答"这被安装了吗"，
从不回答"这一轮改了什么"。在重写一个暂存技能的任何一轮之前，把
目录复制到它旁边，作为
`<anchor>/<skill-name>.pre-<passname>`，命名得让闸门的目录清扫和
保留两份修剪不会把它误认成一份暂存副本；锚点消失时它跟着消失。
并且把空白轮挡在内容轮之外：一次重排移动每一行，所以普通 diff
报告完全的变动量，真正改动的少数几行在其中不可见（实测：一次
委托的密度精简轮删了约 4% 的词，并把每个文件重排到统一的宽度，
好让它的行数显得诚实——它以 0% 和 1.2% 改动的两个文件，显示为
完全重写，而且不存在任何轮前基线）。内容先行，经评审；重排作为
单独的一步，其 diff 可以整体丢弃；委托其一的任务书要说明它是两
者中的哪一个，并禁止另一个。可评审性是那一对状态的属性，不是
最终工件的属性——一个产出新状态而不保留旧状态的流程，产出的
是替换，不是可评审的变更。

**暂存清单。** 任何在 `skill-updates/` 之下写入的生产者——一次
评审交付、一次会话内应用，或为另一个会话暂存的交接材料（一份
清点、一份差异提案、一份任务书）——都在同一回合，向
`[workspace folder]/skill-updates/PENDING.md` 追加一个条目，文件
缺席时创建它，并且绝不让它以今天开头：创建时，列出
`skill-updates/<date>/` 下每一个与现行不完全相同的既有技能目录，
使清单的第一个状态描述的是它所索引的那棵树，而不是碰巧创建了
它的那一次交付（一个假定文件已在的追加者什么也不写，正如上文的
聚合运行规则已经对参与工作区说过的那样；一个"缺席"与"没有待办"
无从区分的索引，不能成为防止工作被遗忘的机制）。对一次交付，
条目携带技能、日期目录、生产者（哪个会话或哪次定时运行暂存了
它）、被应用的观察条目 id，以及一份逐变更的摘要（观察条目 id →
触及的小节 → 一行理由）。安装的工件永远是 `.skill` 捆绑包，所以
条目绝不区分单文件与多文件技能。对已发布的技能，它还携带步骤 5
的社区项分类（立即纳入 / 测试分支 / 否决附原因）、每个被纳入项的
报告者 GitHub 登录名与数字 id（使发布运行的提交无需回到 API，
就能写署名尾注），以及已发布技能的版本升版（新版本，或版本只
存在于仓库清单时的预期升版）——并且，凡该暂存是已发布技能的、
由用户决定的重构（审批策略），附上 `restructure` 一词，使发布
运行把它路由到带测试计划的发布分支，而不是 `main`。清单正是
会话启动协议读取来宣布 "N staged updates awaiting review" 的
东西，所以暂存工作从不被悄悄遗忘；逐变更的摘要正是让用户能快速
评审整文件 diff 的东西，而这正是提高安装率的东西。条目由暂存
工作对账闸门（步骤 1，镜像于会话启动步骤 6）在暂存副本被证明与
现行相同、或被现行并入时移除，或在保留两份规则修剪该目录时移除
——绝不在"安装时刻"，因为没有会话观察安装；读取清单的那个
会话，拥有它的清理。

清单携带三类条目，仅此三类：出处、安装指示，以及——在跨多份
日志的聚合运行中——指名"共享技能实际被暂存于哪个锚点工作区"的
**跨日志指针**。交接材料取出处条目——它是什么、谁暂存的、给哪个
会话、它的状态——不带安装指示，因为没有东西可装；它是暂存工作，
而闸门的"树对照清单"行，正是在条目缺失时找到它的那个东西。指针
是为一份住在别处的暂存所记的出处，所以它属于这里；它不是跟进
工作。跟进工作正是清单绝不携带的东西。任何被评审认出"下次检查"
的东西——一个要镜像的同族技能、一次要在暂存安装后运行的审计——
在摘要写就之前，被记录为它自己的一条观察条目：以 `status: open`
创建，正如文件格式规则对每个新条目所要求的，并在同一回合搁置——
`status: parked` 加一个指名的 `parked_until:` 条件，与评审对任何
搁置条目所做的，是同样的双字段编辑。这把它放进了下一次评审按
流程读取的队列（步骤 1 重查每条搁置条件；步骤 8 列出每条搁置
条目），并且它在"移除清单条目"的对账与修剪中幸存。在聚合运行中，
那条被搁置的跟进，写到它所关涉的工作的那个日志里——也就是下一
次评审会需要它的那一个——并且仅当跟进是关于共享暂存本身时，
也写到锚点工作区的日志；簿记保持本地，并且凡一个 id 被另一份
日志引用之处，都带上它的工作区键。一条寿命终止于安装的工件中的
备注，携带不了跟进：评审里没有任何东西把清单备注当队列读，而
评审保证会删除的唯一一处，恰是最诱人写下剩余积压的地方。（实测：
两个会话在两天里各把一条跟进写进了清单；第一条只因清单碰巧在
下一次评审之前被读到才被发现，第二条在同一回合被抓住，并重新
filed 为一条搁置观察条目。）闸门保持绝对——对一道人们受诱绕过
的安全闸门，补救是减少制造诱惑的摩擦，不是放松闸门。一种可选
的、基于 git 的暂存介质，在 `references/environments.md` 中描述。
