## 完整分类法

**开源类技能**与具体客户端无关，由方法论驱动。识别标准：方法论跨客户端、跨情境
行得通；不需要任何专有信息；其他从业者会觉得它有价值；它承载的是一个流程，而非
个人偏好。必备要素：frontmatter 中的作者与许可，外加一行页脚（模板见下文）；正文
顶部提供反馈渠道，把方法论反馈引导给创建者；工具无关的语言（用"浏览器访问"这类
能力说法，而非产品名）；内建的强制执行机制（见起飞前检查原则）。当一项技能两种
取向都说得通时，默认按开源类处理——剥离具体信息并泛化。

**内部类技能**包含用户/客户/项目的具体信息、个人偏好，或只有用户本人掌握的背景。
它们自我标识为内部类，不需要署名或许可，可以写得更短、更不正式。它们是工作
文档——保持其与时俱进，不要过度工程化。

## 起飞前检查原则

写在技能里的规则，在创造性心流中不会被可靠地遵循。任何带有显式规则的技能都
需要一个验证步骤：代理在交付之前重读规则，并对照规则检查自己的产出。在创建或
改进任何技能时都要问："它有规则吗？它有执行这些规则的机制吗？"如果没有，
就补上一个。

**内嵌命令同样是起飞前检查项——发布之前必须执行。**散文式规则与命令代码段的
失效方式不同：一条散文式规则在每次运行时都会结合上下文被重新解释，因此歧义可以
在执行时被抓住；内嵌命令则逐字执行、无人值守、永久生效——而一条细微错误的命令在每次重读时
都可能显得正确（`git log -1 --format=%cI --reverse` 返回的是最新（NEWEST）的
提交，因为 `-1` 先于 `--reverse` 生效，而貌似合理的读法是"最早的提交"）。任何
内嵌在技能中的命令，都必须在技能文件保存之前对真实数据执行一次，并检查其输出
是否合理。一条未经验证的代码段是技能中风险最高的行之一：它发布的缺陷，任何
重读都抓不住。

**从干净的 shell 运行那段字面字符串。**用运行某个*等价*命令来验证，验证的是你的
转述，不是工件。把命令从技能文件里复制出来，执行那段一字不差的文本——从一个
单独另起的 shell 执行，而不是在完成工作的那个会话里：一个工作会话会积累环境
变量、解释器标志、安全策略覆盖、PATH 条目和一个最终读者不会拥有的工作目录，
在那里通过的命令，可能第一次在普通终端里真实使用时就失败。在有两个 shell 可
用时，在未用于配置环境的那个 shell 里做起飞前检查。**当被测命令是一道守卫时，
对机制断言，不对结果断言。**负向测试只有当失败出于预期原因时才算通过；当一个
操作上有多道守卫时，"它被拒绝了"这一结果任何一道都能满足。把错误文本或退出码
对应到被测的那道守卫，选择明显越过阈值的输入，并单独测试边界值。**在对任何带
副作用的东西做起飞前检查之前，先确认存在 dry-run 路径**；不存在的话先补一条——
对护栏的测试不得变成护栏本来要防止的那起事故。

**与你一致的验证命令才是不该信任的。**如上所述执行一次代码段抓不住这一类问题：
命令干净地运行，返回一个貌似合理的数字。与强预期相矛盾的检查会被追查；与预期
一致的检查永远不会，于是错误仪器给出的正确答案教会你信任这台仪器。常见的形态是
聚合计数，因为计数不是清单，而为可读性折叠输出的工具会在不声明的情况下少报：
`git status --porcelain --ignored` 对一个被忽略的目录只打印一行，于是对它
`grep -c` 会在其实有五个文件被忽略时报"1"，只有 `--untracked-files=all` 会把它
展开。在发布一个报告数字的验证步骤之前，先确认这个数字的单位是什么；凡枚举成本
不高，就枚举并通读整个集合。

**一份来源清单也是一条内嵌命令。**上面这条规则很容易被读成只针对 shell 代码段，
因为那才是"命令"看起来的样子。并非如此：它约束的是技能指示未来会话不加检查
就去*使用*的一切——而 URL、API 端点、数据库名、文件路径或工具调用恰恰就是这种
东西。一个核心是"查阅这些来源"的技能，发布其来源的方式，与另一个技能发布命令的
方式相同。

在一个这样的技能上观察到：八个来源，个个貌似合理，全部未经尝试就被写了进去。
**四个不可用**——两个即使带上浏览器 user agent 也返回 403，一个返回"Making sure
you're not a bot!"（确认你不是机器人），一个返回没有结果的空单页应用外壳。每一个
在页面上读起来都像正确的，而且在之后每一次重读中都会继续显得正确。

为什么这比一条坏掉的 shell 命令更糟：坏命令会大声失败，会话知道停下。一个不可达
的来源会返回*某种东西*——空结果集、登录页、外壳——而空结果的自然读法是"没有
匹配项"，这本身就成了一条发现。于是技能教未来的会话把一扇被堵住的门报告成不
存在。在技能文件保存之前，对每一个来源用真实数据执行一次；记录哪些被尝试过、
各自返回了什么。

**不可能得出否定结果的验证不是验证。**发布任何检查之前，先问：如果被检查的
东西失败了，它会是什么样子——如果答案是"一个样"，这个检查就是装饰。这个陷阱有
一种典型形状：被检视的工件正是由执行检视的同一个会话产出或改动过的。观察到：
一组 bundle 发布到了远端目标，验证方式却是读取同一个会话写入了修正内容的那个
本地解包目录。即使发布彻底失败，它也会报告"全部正确"。

区分到达与未到达的是一个**判别值（discriminator）**——一个只有远端才能产出的值：
服务器分配的标识符、上游时间戳、远端计算的摘要、本地副本无从伪造的字段。把已
发布的工件与你自己的源做哈希匹配不算判别值，因为两边都是你的。写检查时指名判别
值；如果指不出来，就明说这一步未经证实，而不是写一个永远通过的检查。

## 精简内容

技能只应包含会在执行时改变代理行为的内容。把变更日志、作者栏之外的鸣谢、冗长的
背景故事和维护者说明移到辅助文档中去。但不要删掉示例、反模式或完整案例——裸规则
比带上下文的规则更容易被违反。检验标准：删掉它会改变行为吗？把每个会话都生效的
规则留在技能正文，把偶发场景材料放进按需加载的参考文件（渐进式披露）——每个会话
都会加载的技能是一笔固定开销，应当像固定开销那样接受审计。

**自己声明核心行数上限，并且只允许它下降。**技能通过自报上限加入尺寸棘轮——在
SKILL.md 的 frontmatter 里写 `core_max_lines: N`，或在它旁边放一个 `.core-ceiling`
文件。此后 `validate-skill-bundle.py` 会在核心超限时失败，并指示把内容移入参考
文件，而不是提高那个数字。以核心今天的实测行数作为初始值：要点不在于每个技能都
缩到某个理想尺寸，而在于没有技能会在无人察觉的情况下越过它已经所在的位置。
**上限随裁剪同步下调。**当声明的上限高于核心计数 3 行以上时，验证器同样会失败；
修复方式是在同一次提交中把 `core_max_lines`（或 `.core-ceiling`）降到当前计数，
与裁剪一起完成。每次运行都会报告 `core N / ceiling M / slack S`。失效形态：一道
只阻止增长的检查会把每次裁剪都留成空闲余量，下一次普通的新增内容会在无人决定的
情况下把它花掉。

两者都未声明的技能没有加入这一机制。行数计数和与 500 行目标的差距仍会报告；
但没有任何东西被门禁。这是刻意的，也是对一个真实缺陷的纠正：上限一度是验证器
内部的常量，于是某一个技能的预算让三个没有改动的不相干技能失败了。**一个技能
为整个库提供的工具不得携带该技能自己的常量。**共享脚本中的任何阈值，要么从被检
对象读取，要么就是建议性的——判别特征是：一道门禁在其作者从未看过的输入上失败。

**渐进式披露是默认要求，不是可选项。**加载分三级：frontmatter 元数据始终在上下
文中；SKILL.md 正文在技能触发时加载；捆绑资源只在有东西读取它们时才加载。因此
正文是一笔每次调用都要交的税，参考文件则不是，所以只有在该技能每次触发时都改变
行为的内容才应留在正文。**这一拆分是每一个新建或重大修订技能的目标结构，无论其
大小**——偶发场景材料从第一稿起就进 `references/`，而不是等正文膨胀到读不动才
拆。一条按行数切换的结构规则会让同一个技能有两种形态、一条每个读者和每个工具都
要重新推导的边界；从小开始拆分在小端没有任何成本。约 500 行这个数字只保留一个
角色：作为现有、尚未拆分技能的**改造触发线**——正文超过大约 500 行，是"补做拆分
不再可选"的起点。具体而言：

- **SKILL.md 保留**心智模型、少数每次调用都会改变行为的规则，以及指向参考文件的
  指针清单。
- **`references/` 承接**工具清单、配方、分类法、按变体的细节和长篇坑点目录——
  在某一类场景中才会查阅、而非每次触发都用的内容。
- **每个参考文件超过大约 300 行后要有目录**，让读者可以加载后跳转，而不是整篇
  通读。
- **每个指针都显式写明加载触发条件**——"首次导出前阅读"、"选择工具时阅读"、
  "评审触发时阅读"——因为没有触发条件的指针读起来像可选，然后被跳过。一份不带
  条件的文件名清单不是渐进式披露，而是参考文献目录。

拆分还造就了让大型技能可维护的接缝：单体正文没有天然的编辑边界，每次修改都触及
整个文件，每次编辑都威胁其余部分。对现有大型技能补做拆分是另一件优先级较低的
工作——默认规则立即约束新工作，以及任何重大到正文反正要重写的修订。

**对任何打算发布的技能，渐进式披露都是强制要求，而不只是对大技能的默认。**就绪
检查验证的是它被写来拦截的东西，而结构人人认可、无人编码——于是一个约 1,200 行的
单文件通过了全部保密、许可与署名检查并发布，其结构重构在三轮运行中一直被记为
"长期跟进事项"。要用机械化方式定义"扁平"，让门禁成为一行脚本而不是一个判断：
**没有 `references/` 目录；或者有 `references/` 目录但 `SKILL.md` 从不指向它
（没有提到其中任何文件的指针清单或章节映射）；或者 `SKILL.md` 超过评审设定的
行数预算且没有任何按需加载的内容。**预算由评审决定；现有核心位于 400–750 行
区间，是参照点。一个扁平的技能就是一个在能发布之前必须重构的技能，而重构在活
技能上通过常规的评审—安装路径完成——绝不在 repo 里做，否则安装副本与发布树会
立刻分叉。

**参考文件的形态由其触发条件决定，而不是行数。**核心的尺寸上限不迁移到参考
文件，因为它们的成本是有条件的：核心每个会话都被完整加载，那里的一行对每个
消费者都收税；参考文件只在其场景发生时加载，因此一个很少加载的长文件是便宜的。
规则是：一个参考文件服务一个场景，或一组可靠地共同发生的场景。当指向同一个
文件的不同加载触发条件的数量增长时，就应当拆分——无论其大小——因为每个触发
条件都在为其他场景的内容买单；而一个长的单一场景文件形态是正确的，不得为了
满足尺寸规则而拆分。本技能自身 bundle 的一次测量（行数 / 指名章节的不同加载
触发条件数），复制自验证器的 `reference shape` 行——从那一行刷新，绝不手抄。
验证器只统计指名了章节的指针，因此核心只按文件名引用的文件显示 n/a：

| 文件 | 行数 | 触发条件数 |
|---|---:|---:|
| `weekly-review.md` | 1,992 | 1 |
| `observation-log.md` | 1,714 | **18** |
| `environments.md` | 1,432 | 5 |
| `skill-authoring.md` | 1,400 | n/a |
| `starter-principles.md` | 444 | n/a |
| `signals.md` | 232 | 4 |
| `migration.md` | 226 | n/a |

行数上限会先标记最大的文件——恰恰是最不需要改动的那个，因为一次评审会把它当作
一个单元整体加载——而且它无法把这个文件与"一个会话中十八个不同时刻各自拉入"的
那个文件区分开。所以 `scripts/validate-skill-bundle.py` 每次运行都打印每文件的
触发条件数，刻意**不做门禁**：一次快照无法为阈值提供依据，而这一次快照已经推翻
了即将成文的规则；下一次评审要从趋势来论证。做出拆分后，每个被移动的场景都
需要一次加载观察测试（见下文），并且绝不在一个测试期内做两次结构性拆分——否则
回归无法归因于其中哪一次。

**加载触发条件是单体文件原本没有的新失效点。**拆分只有在场景发生时参考文件确实
被取用，才能兑现它的节省。没被取用时，代理会凭精简的核心即兴应付该场景，行为
退化，而且没有任何报错——内容全都还在，因此任何针对内容的检查都抓不住它。所以
任何拆分的试用标准都必须测试加载，而不只是内容拆分：

1. 每个指针都是一条携带触发条件的指令（"当 Y 时加载 X"），而不是对 X 包含什么
   的描述。
2. 试用期间，每个场景都要在真实会话中被观察到触发，并确认参考文件已加载——
   每个场景一条标准，这样从未触发的场景会显式呈现为未验证，而不是被默认无事。
3. 一次漏加载是阻塞性发现，不是一条备注。修复方式是结构性强制——一道该场景
   不完成就无法走完的清单步骤——而不是更强硬的措辞，依据正是本文件自己的起飞前
   检查原则。

还要加一道运行时兜底：指示代理在注意到某个场景在其参考文件未加载的情况下被
处理时，记录一条观察条目。没有它，负面情形就没有记录通道，试用也无法区分"尚未
观察到"与"没有发生"（见下文"试用设计"，它规定了此类试用必须如何布控，以免命名
触发条件本身变成干预）。

## 配置与流程——三容器规则

一个需要特定于某个人、团队或安装环境的值的技能——一个身份、一个账户名、一份
私有屏蔽清单、一组本地排除项——需要**三个容器，而不是两个**。在只有技能本身和
调用它的提示词可用时，这些具体信息必须落在其中之一：放进技能会阻碍发布与泛化；
放进提示词会让提示词臃肿且漂移。第三个容器化解这一张力：

1. **技能**承载流程，并*读取*配置。
2. **一个私有配置文件**承载具体值。技能写明它预期的位置，并且永不随技能发布。
3. **调用提示词**只承载触发条件。

显式声明优先级：*配置*上配置文件优先，*流程*上技能优先，且配置永远不能放宽
规则。给技能一个首运行回退：配置文件不存在时询问这些值，并主动提出代为写入
文件——正是这几行，让不是作者的人也能使用这个技能。判断一行该进配置文件还是
该进技能的测试：**换一个人运行这个技能，在这里会不会需要不同的值？**在一次
真实转换上测量，抽出的内容比看上去要少——大多数身份行只是一个专有名词，换成
角色名词（"维护者"）读起来完全一样。

**当提示词或配置文件为了保险而复制技能的规则时，用停止条件替换那份副本，而不是
用更短的副本。**以保险为由保留的重复是最少被审计的一类——复制它的理由同时也是
不去质疑它的理由，于是承载最重要规则的副本恰恰最可能悄悄过期（实践中发现：
某规则集的第三份副本仍带着其源文件早已 superseded（取代）的一条约定，且没有任何
东西发现它）。
规则的一份副本会与源失去一致；"没有源就不继续"则不会。"如果技能没有加载，停下
并报告——不要凭这份提示词继续"只有一行，而且没有任何可以漂移的东西。最多只在
两处同时陈述不可逆的不变量，并在提示词里说明它刻意不携带回退副本，免得未来的
编辑者好心再加回去。

## 记录外部工具面

适用于任何记录他人拥有的界面的技能——MCP 服务器的工具、API 的端点、平台的
接口。这类技能的价值在于其论断是实测观察到的（OBSERVED），而不是从厂商自己的
描述推断出来的，而第一版几乎总是在只演练过界面的一部分之后写成。用与已测试
少数同样的口吻去记录未测试的多数，会把厂商文案悄悄提升成貌似实地验证的发现，
而后来者无从分辨哪些论断有证据支撑。删掉未测试项也不是解决办法——它们仍然
需要列出，代理才知道它们存在。

1. **逐项标记，而不是只标例外。**给每个被记录的工具、端点或屏幕一个可见的逐项
   标记，区分"实践中已验证"与"未演练"，并在清单近顶部写明图例，让这个区分不可能
   被错过。只标记未演练项是失败的：一个未标记项读起来像"信息缺失"，而不是
   "有证据"。
2. **未演练项用不同的口吻写。**写厂商怎么说，加上可以安全推断的风险——"文档
   描述了 X"、"假定这会清除当前状态"——绝不写成实测行为。不写完整示例，不写时序
   或配额论断，不替没人运行过的东西写坑点。
3. **把标记做成工作队列。**加一条显式指令：当某个未演练项被实际使用时，代理
   回报它实际做了什么，以便该条目被改写、其标记被提升。没有这条，标记会僵化成
   永久的免责声明，技能永远无法收敛到证据。
4. **修订时提升。**对技能的任何重大编辑，都要对照此后实际演练过什么，重新检查
   这些标记——提升是编辑的一部分，不是另一个项目。

原则：覆盖面较小但言明哪些论断经过测试的文档，比把两者混在一起的文档更有用，
因为读者的决策——直接信任，还是先验证——完全取决于这个区分，而它一旦模糊就
不可恢复。

## 许可

在前言中包含一条许可声明，并附一份含全文的 LICENSE 文件。可选：**CC BY 4.0**
（散文/方法论类技能；署名即可分享与改编——推荐默认）、**MIT**（代码为主，
宽松型）、**Apache 2.0**（MIT 加专利授权）、**CC BY-SA 4.0**（衍生作品以相同
方式共享）、**GPL 家族**（强著佐权）。由作者选择；要求是必须有一个。

**私有客户共享**是第三条渠道，有它自己的一套权利框架：一个与客户端无关的技能被
私下共享给某一个客户，既不是开源（open source）也不是内部类。保留作者元数据和
页脚；把许可替换为一段简短的使用声明（例如"私下共享供内部使用；再分发前请先
征询作者"）；不需要 LICENSE 文件。所有保密清查仍然适用——即使接收方是已知的
客户，其他客户的信息也不得泄漏。不要把"不是内部类"当成"所以是开源"：分发渠道
决定权利框架，而不只是反馈路由（见下文分发渠道说明）。

## 发布版本编号

版本号是关于历史与兼容性的声明，不是标签计数器。要从消费者的视角编号：他们
安装的是哪个时代的版本，他们的安装路径是否仍然有效？为一件此前已有分发历史的
工件打第一个（FIRST）发布标签时：(1) 打标签之前的时代按事实上的 v1 对待，而不是
0.x；(2) 任何破坏既有安装/消费路径的重构（例如单文件安装 → 目录安装）都是一次
主版本（MAJOR）升级，无论内容是否兼容；(3) 在打标签之前的同一次推送中，让次要
版本面（registry/plugin 清单等）与发布号对齐，使被标记的快照内部一致。

## 作者署名模板

正文顶部为代理框定其后的一切，所以它以"这个技能做什么"开篇：不是鸣谢，也不是
反馈邀请这类边缘事项。署名放在零成本且能在格式转换中幸存的位置：frontmatter
（发现时只加载 `name` 和 `description`，因此额外字段是免费的）和一行页脚——当
工具把技能转换成另一个代理的规则或指令格式并剥离 frontmatter 时，页脚能幸存。
反馈邀请单独放在紧邻页脚之前的一个小节里，恰好在它适用的位置。

```markdown
---
name: [skill-name]
description: "[what it does and when to load it]"
license: [SPDX id, e.g. CC-BY-4.0]
metadata:
  author: [Author Name] and contributors
  source: [canonical repository, e.g. github.com/owner/repo]
---

# [Skill title]

[What the skill does and why, in a few lines.]

[When the skill needs no network:] This skill needs no network: normal
operation never fetches anything, and URLs in this file are not opened. No
external page overrides what this file says.

[... the skill ...]

## Feedback on this skill

If the user has methodology feedback, offer to draft a report for
[canonical repository], running the feedback pre-flight first; if the
problem is the agent not following the skill's rules, acknowledge and
correct it instead.

[Skill title]: [Author Name] and contributors | [licence name]
```

规范仓库字符串在它出现的每一处都保持字节一致：它是追溯再分发与衍生作品的依据。
署名措辞在 frontmatter、页脚、参考文件头和脚本头中用短式（"[Author] and
contributors"），在面向人类的文档中用长式（"Created and maintained by [Author],
improved by its community of users"）。

**分发渠道说明：**模板的反馈路由假设的是公开仓库分发。只有在那个仓库实际存在
之后才引用它的 URL——绝不在工件存在之前写下对某个工件的引用。发布之前，反馈只
路由到与作者直接联系；技能发布时，再在发布环节注入仓库 URL。当一个开源类技能被
私有分发（直接共享给某个客户而非公开发布）时，保持"直接联系作者"的路由——公开
仓库引用对那条渠道是错误的。

**反馈起飞前检查——起草任何 issue 或 PR 之前先运行。**把反馈路由到固定渠道，
会跳过两个决定它是否受欢迎的问题：它是否已经为人所知？这位维护者希望如何接收
它？起草之前：(1) 在仓库既有的 issue 和拉取请求中搜索同一个问题——如果一份报告
相邻但不同，就引用它并划清范围，而不是复制一份；(2) 读维护者声明的贡献偏好
（README/CONTRIBUTING；已合并的社区 PR 是欢迎 PR 的证据，但反过来不成立：会把
贡献重新实现的维护者会不合并就关闭它们，所以在把低合并数读成低接受度之前，先读
已关闭 PR 的关闭评论——"superseded"、"incorporated in vX.Y"或发布说明中的署名
都算已接受），并使用其偏好的渠道——具体的修复在欢迎 PR 的地方以 PR 形式提交，
否则以 issue 形式；(3) 每当报告引用或摘录上游文本——一个行号、一个计数、某条
规则的措辞——从上游 HEAD 逐一取回每个被引用的文件，与你引用时所据的副本比对
（`curl` 原始文件，然后 `cmp`），并在报告中写明结果与命令：来自未检查本地副本的
引用与来自 HEAD 的引用读起来一模一样，而一份干净的安装恰恰是没人怀疑漂移的
地方；当副本不一致或本地安装被改动过时，到 HEAD 重读缺陷本身，因为它可能已经
修复；在较早会话里写好的草稿，发出之前要再次检查；(4) 遵循仓库对报告的格式
惯例。起飞前检查是本技能接触网络的环节，而且只在用户要求起草报告之后；在那
之前，没有任何东西会抓取网络。

**发送前门禁——在成品草稿上运行，位于起飞前检查之后。**起飞前检查决定一份报告
是否发出、发到哪里；没有什么环节去读成品文本里不得出现什么，而**一道只确认
必备部分的检查，靠添加就能通过，靠删减永远不能**。发送之前，在成品草稿中搜索
工作区键承载的每一个标识符——每个参与工作区根目录中的项目名或客户名、主机名、
账户标识符——预期命中 0 次，并用一段已知包含标识符的文本做阳性对照。技能自己
命名的通用路径段（`skill-observations`、`observation-log`）不是标识符，不进
清单。

这道门禁防止的失效：一份发到上游维护者的验证报告带了两个私有项目名，因为多
日志块要求每个离开日志的 id 都带上它的工作区键，而在本地安装里，键就是项目的
目录名。报告遵守了规则，却正因这条规则泄漏了。发布约十分钟后才有人注意到；
修复方式是删除重发，因为编辑会在编辑历史里留下第一版。

**草稿中关于其自身运行的论断要对照记录核查。**起飞前检查在 HEAD 核查被报告的
问题，门禁检查文本里不得出现什么；两者都不检查"报告声称观察到的东西是否真的被
观察到"，而作者恰是最看不出这个缺口的人，因为草稿读起来像他记忆中那份工作的
忠实摘要。发送之前：给草稿的事实性论断编号，包括它对自己证据如何产生的陈述；
逐条对照被记录的运行或来源核查——最好由一个没有写过草稿的代理执行，指示它去
反驳，并对每条论断返回"已证实/已反驳/无法判定"，无法判定的论断按失败计；把每条
论断的措辞对准实际测试过的情形；粘贴由起草者自己捕获的输出，绝不转述自另一个
代理的报告，并把写出的文件与捕获比对；把每条前提条件和出处（"在测试工作区中
复现"）从观察条目带进报告；在已有帖子上，先通读全部内容，只说它缺少的；在发送
时刻重新测量版本号和其他工单的状态。这是第 5 步的事实性论断规则
（`weekly-review.md`）在文本离开本机之处 的应用。观察到：一次会话的证据产生五份
草稿，在干净的起飞前检查和标识符扫描之后，28 条编号论断中仍有 3 条被反驳，对
修正稿的后续轮次又反驳了更多——一条为从未测量过的情形声称的结果、一条被丢掉的
前提条件、一个被说成"我们遇到了"的人造夹具、一个对某一族代码页的泛化（测试
过的四个里有两个与它矛盾）。

**将由人工粘贴的草稿，要按它被消费的方式检查。**起飞前检查在草稿存在之前运行，
上面的门禁读草稿里不得出现什么；两者都不把它当作粘贴源来读，而有两个属性会在
传输途中损坏，任何内容检查都看不见。观察到：同一文件里的三份 issue 草稿，各以
以 `**Title:**
<title>` 开头，段落之间以空行硬换行，由人工发布——每个已发布的标题
都以 `** ` 开头，因为标签的右侧星号随值一起被选中；每个正文都丢失了全部空行，
段落渲染成连成一片；起飞前检查通过了，标识符扫描是干净的，发布后一次对空白做
归一化的比较还判定正文完全一致。所以，对任何交付人工发布的报告：(1) **形态**
——每个字段单独放在自己的围栏代码块中，围栏比它内部任何反引号串都长，且不带
info string（从围栏行或由其渲染出的标签开始的选区，会把语言名粘贴成值的第一
行），目标字段写在块上一行（"粘贴到 Title"），绝不作为值所在行上的标签；一段
一行，保留段落之间的空行，因为 issue 正文会把单个换行渲染成换行符；发给另一个
字段的草稿元数据（一个标签、一条标签建议）绝不放进正文块内；(2) **粘贴检查**
——交付之前，按粘贴会得到的方式逐块提取，并与预期的字段值比对；(3) **回读**
——发布之后，取回已发布的标题和正文，与草稿逐行比对（包括空行），绝不通过对
空白归一化的比较：把受测属性归一化掉的比较什么也证明不了，而人工的复制路径
可能丢掉文件上的任何检查都看不见的结构。同样适用于所有交付出去供粘贴的工件——
激活块、钩子条目、交接文档；配置场景在 `environments.md` 中自带回读（"A
delegated setup step is not done until you have observed it"，委派的配置步骤在
被观察到之前不算完成）。

## description 有不止一类读者

已发布技能的 `description` 被三套系统读取，却只为其中一套而写。它是代理匹配的
运行时触发器，用以决定是否加载该技能。它是采集型技能目录所索引的搜索字段，其
排序往往不过是子串匹配。而通过那些目录页，当有人问这样的工具是否存在时，它是
AI 回答所依据文本的一部分。触发器要求"何时加载"的精确；目录搜索要的是受众实际
输入的词。两者相互拉扯，这个取舍在每个技能上答案不同，所以这里只陈述，
不定论。

决定性事实是加载是否仍依赖 description。自带激活层的技能——CLAUDE.md 里的一行、
一个会话启动钩子、一条显式调用约定——已经把加载与 description 匹配解耦，它的
description 可以承载受众词汇。仅依赖 description 匹配的技能则没有：放宽它的
description 换来可发现性，代价是误加载，每次误加载都是在一个并不需要它的会话里
完整读一遍核心。

在 description 可以自由改动的地方设两道守卫。每一个新增词，都必须是作者能辩护
为"对技能所做之事的准确描述"的词——检验标准是准确性，不是搜索量，而堆砌的
description 恰恰会被项目想吸引的那些维护者读到；每一个新增词也消耗发送门禁所
测量的字符预算。此外，目录持有 frontmatter 的过期副本，按它们自己的节奏刷新，
所以一次改动要数周之后才可测量：在改动发布时记录改前状态（搜索的词、结果
位置），到时再比较。失效形态：一个为单一消费者命名的字段，在工件发布之后获得
了其他消费者，而写作流程中没有任何环节从它们的角度读它。

## 保密层级

开源类/内部类的边界是一条保密边界；分层执行，让任何一层都能接住其他层漏掉的
东西：

1. **观察条目级脱敏**——开源类观察条目只承载完全泛化的原则（在 SKILL.md 中
   说明）。
2. **创建前审查**——起草/重新生成开源类技能之前，扫描全部素材中的客户名、URL、
   域名、内部术语、可识别到具体对象的结构；先替换为通用等价物。
3. **成稿后清查**——一次只针对泄漏的独立重读。**先**读示例、用法字符串、默认
   参数和测试夹具（第 8 层说明原因），然后是作者以外的专有名词、域名/URL/项目
   标识符、能缩小客户范围的行业细节、可追溯到真实项目的示例。
4. **结构性原则**——拿不准就删。略更通用胜过略有泄漏。
5. **跨产品再识别清查**——任何公开发布前的最后一遍。单独脱敏过的示例可以组合
   起来识别出客户（枚举计数与一份公开的客户名单吻合；窄行业里的具体数字；与
   真实客户同行业的、伪装薄弱的占位名）。列出每个示例及其字段（行业、地域、
   数字、时间、计数）；追问：拿着作者公开客户名单的读者能否把它们对应上去；
   缓解手段包括模糊化计数、放宽行业范围、使用示意性区间，或合并成复合示例。
   机械化地执行——作者因为知道真实情况，是最不可靠的裁判。
6. **接收方视角检查（共享给客户的工件）**——以上各层只守一个方向：其他方的
   信息向内泄漏。为特定接收方准备的工件还会把作者自己的工作区向外泄漏：对
   内部工作文件（分析工作簿文件名、私有文档）的引用，接收方从未收到过，既造成
   困惑（引用了读者打不开的来源），也是事实错误（例如把它们描述成"已交付"）。
   检查：每个被引用的文件、文档或来源，要么包含在共享内容中，要么确实在接收方
   手中；把对内部工件的引用替换为对它们所来自分析的平实描述。检验："接收方能否
   打开或验证这份文档中的每一个引用？"
7. **跨技能引用扫描（已发布技能）**——在个人库内部写成的技能会积累指向同族
   技能的指针（"见 {other-skill} 的 Hyperlink 标记"）。在库内它们有用；发布之后
   就悬空了——读者无法解析它们，而且它们泄漏了作者内部工具的存在与命名。一个
   已发布的技能要么独立可用，要么声明对某个特定*已发布*开源配套技能的依赖。
   按名称扫描对其他技能的引用；每个命中要么是 (a) 已声明的已发布配套技能——
   保留，最好附仓库链接；要么是 (b) 可内联的——把所需的规则拉进正文；要么是
   (c) 内部工具——改写成能力语言（"子代理所运行的任何演示工具"）。在任何发布
   流程中把它机械化：用已安装但未发布的技能名清单 grep 内容。已发布文档中的
   每个指针都必须在读者的世界里可解析，而不是在作者的世界里。

   写作期推论——同族同步与家族说明。家族机制会合法地把同步说明写进技能文件，
   以防共享核心漂移，而这些说明正是违反本层的预期形态：同步规则与独立规则各自
   被正确遵循，却共同产出一个双方都没有预料到的不可发布技能。在向一个已发布或
   发布候选的开源类技能添加同族同步或家族说明时，从一开始就用能力语言表述家族
   引用（"在其他平台实现此方法论的同族技能"），或泛指私有家族注册表——绝不上
   已安装但未发布技能的名，因为发布流程的独立可用扫描会拦截这些名字，同步本身
   就成了发布阻塞项，唯一的修复是在活技能上改写。当一个维护机制把交叉引用写进
   某个工件时，它必须尊重它所写入工件的发布边界：内部注册表可以点名内部事物；
   公开工件按能力引用它们，不按名字。
8. **示例在构造时即为合成，而非事后擦洗**——示例、用法字符串、默认参数、测试
   夹具和样例载荷是技能中风险最高、受审最少的文本。它们的全部目的就是曾经真实：
   示例之所以从一次能跑通的实际运行中粘贴而来，恰恰是为了它能用，因此活数据在
   这里比在任何别处都更容易在擦洗后幸存。在写作时就写成合成的——一个通用标签
   加一个圆整数，取该参数或载荷实际采用的形态，这仍然能教会读者格式。本层是
   前瞻性的，而且必须如此，因为没有任何基于词项的扫描能支撑它：保密扫描匹配的
   是名字、域名和 handle，而一个**数字**不在其中。这类扫描也无法有效地以某个
   行业或类别名词为键——一个通用类别词几乎在每个文件上都会触发，把它加进绊线
   清单只是用一种失效模式换一种更糟的。因此一次干净的扫描只是关于清单内词项的
   证据，对示例是否携带真实的分配额、计数、日期或样例载荷不说明任何东西。这就
   是"每台仪器都获得同一个守卫"这条内部规则在保密形态下的体现：一台看不见该对象
   的仪器给出的空结果不是"不存在"的证据。所以第 3 层的清查最先读示例而不是最后
   读，而且发布前通读包括对树中每个示例、用法字符串和夹具的人工通读——这是
   唯一一项没有脚本 能替作者完成的检查。
9. **理由以失效形态表述，示例跨行业（已发布或排队待发布的技能）**——一条规则的
   理由以现在时的失效形态（"失效形态：……"）表述，绝不以它来源的那个案例表述：
   不写"曾观察到一次"，不写"在产生这条规则的案例里"，不写客户投诉，不写来自
   单个项目的计数。豁免：关于技能自身日志与流程的计数（观察条目、评审、技能、
   发布）——它们不追溯到任何项目，恰恰是一条规则存在的证据。示例来自至少两个
   不相关的行业，或来自一个中性的通用行业，绝不来自产生该规则的会话所处的
   行业。本层关闭的失效形态：从内部日志写出的技能更新，把日志的项目叙事及其
   客户的行业带进发布文本，每个示例单独都能通过所有词项扫描，而整个集合识别出
   客户。脚本看不见这两类中的任何一类，所以它是交付前门禁（`weekly-review.md`，
   交付）中一次点名的人工通读，覆盖自上个发布树以来新增的每个章节。

## 永恒性——共享技能不得固化当前状态

任何离开作者自身维护循环的技能（已发布，或共享给客户持续使用）都没有更新
节奏——不带日期的现在时论断会悄悄变错，而代理会照着行动。"关于它应当如何的
建议是永恒的；对当前状态的快照不是。"规则：(a) 建议与规则——保留；(b) 带日期的
历史事实（"2026 年 6 月份额约为 50%"）——保留，它们作为历史始终为真；(c) 不带
日期/现在时的当前状态论断（"X 目前被阻塞"、"该站点现在做 Y"）——替换为检查指令
（"行动前先验证 X 的当前状态"）。清查模式：grep "currently"、"right now"、
"as of"、"now"，以及靠近基础设施名词的现在时状态动词。（内部类客户档案豁免：
它们生活在以捕捉当前状态为目的的维护循环里。）

**第一方观察日期：已发布技能优先使用基于验证的措辞。**上面规则 (b)——带日期的
事实保留——适用于第三方发布的事实（厂商变更日志、API 公告、日历日期示例）。
它不延伸到暴露作者何时观察到、验证或复查某事的日期（"截至 2026 年 4 月"、
"2026 年 6 月的一次复查"）：在已发布的工件里，这些是关于作者流程的元数据，
泄漏内部评审节奏，并会被读成陈旧标记。用基于验证的措辞替换——"上次验证时"、
"此后一次复查发现"——外加一条如何对照线上来源重新验证的显式指令；读者需要知道
的是如何复查一条论断，而不是作者上次何时查过。同一规则覆盖已发布仓库上的提交
信息。

**禁令按它所禁止的对象表述：任何公开工件中都不得有带日期的第一方验证论断，
任何日期格式都不行。**各种形态都只是从属于这条定义的例子，绝不是定义本身：
`YYYY-MM-DD`、`DD/MM/YYYY`、`Mon YYYY`、`Month YYYY`、`QN YYYY`、光秃秃的
"as of 2026"，以及句位形态"on <date>"与"run on <date>"。这份清单之所以重要，
是因为这条规则曾被表述成"月份名 + 年的模式"，此后每一次扫描都恰好只 grep 那一
种形态：照着示例运行复查的人已经遵守了字面上的规则，于是没有什么会促使他追问
模式是否覆盖了规则，十二条 ISO 日期论断因此幸存——其中一条就在一个经过评审、
已签发的发布提交里。所以让检查机械化且可审计：任何发布流程都在提交前扫描公开
工件——是扫描，不是提醒——模式集放在脚本里，可以在一处扩展，并且**扫描记录
运行了哪些模式**；一个不声明覆盖范围的绿色结果是无法审计的。随之有两个推论。
由一个枚举形态集合产出的计数是**下界**，绝不是"已纠正"的数字：那次报告"八处
已纠正"的清查，漏掉了三个最宽松的 grep 就能找到的位置。而一道每次运行都通过
的检查，是关于这道检查的证据，不是关于工件的——仪器守卫（`observation-log.md`，
"每台仪器都获得同一个守卫"）对绿色结果与对空结果同样适用。**有一种配对形态豁免
（维护者决定）：**一个被测量的事实可以带"Last verified YYYY-MM-DD · Re-test:
`<one command>`"——日期加一条反引号包裹的重测命令，两者在一起，因为对一个会
漂移的事实，时效是有用的部分，而命令让它不至于沦为一条裸论断。其余一切带日期
的第一方形态仍然禁止，包括不带命令的日期；发布扫描把豁免作为排除项编码进它的
脚本，绝不写成散文。

**内部文档豁免所假设的维护循环只存在于散文里。**分类法允许描述单一安装的内部
类技能，它们可以合法地指名当前状态。未言明的假设是有人会复查那个状态——但状态
漂移时没有任何东西触发，于是"内部类，所以带日期的事实没问题"变成了"内部类，
所以永久错误"。

观察到：一个内部类技能以它所描述系统的硬编码版本号开篇；部署的系统向前走了，
技能的第一段在一天之内就错了。这已经是同一个数字第二次过期，另外五份副本还
躺在记忆文件和交接说明里。第一段是它破坏力最大的地方，因为它先于任何可能与它
矛盾的内容被读到。

所以，内部类技能只有带着**指名的复查**才可以承载当前状态：什么能重新推导出
该值，以及何时推导。"版本 X（每次评审时用 `<command>` 重新推导）"可以接受；
光秃秃的数字不行。不存在复查方式时，不要记录该值——记录如何获得它。

## 编辑技能——永远从活文件开始

1. 活文件是权威来源：在 Claude Code 中是 `~/.claude/skills/{skill}/SKILL.md`；
   在 Cowork 中是挂在 `.claude/skills/{skill}/SKILL.md` 的只读挂载（写入按设计
   以 EROFS 失败）。**那道防护只在 Cowork 里存在。**在 Claude Code 和大多数
   本地文件系统环境中，同样的文件是普通可写文件，没有任何东西阻止写入——防止
   覆盖的唯一屏障是纪律。除非亲眼见过 EROFS，否则一律假设自己处于无防护情形。
   在任何环境中都不要原地编辑技能的文件——仅限暂存是让自主评审保持安全的前提，
   而在没有防护的地方让这一点成立的办法，是让每次编辑都从复制开始（`mkdir -p`
   建暂存目录，`cp` 拷入活文件，`diff -q` 证明一致），让活路径永远不在手中。
   **复制之前先解析活路径**（`readlink -f`，或 `cd` 进去再 `pwd -P`），并证明
   暂存文件是一个不同的文件，而不只是一个相同的文件。当 skills 条目是指向
   某个 checkout 的符号链接时——一种常见的 dotfiles 布局——对条目 `cp -R`
   复制的是链接本身，暂存路径变成活目录的第二个名字，每一次"暂存"编辑都落进
   活技能，而 `diff -rq` 照样通过，因为它比较的是两条路径各自解析到的内容：它
   验证的是副本忠实，从来不是"这是一个副本"。一道恰好在暂存已经悄悄变成原地
   编辑时报告成功的证明步骤，比没有更糟。所以复制之后：暂存路径本身不是链接
   （`[ ! -L "$s" ]`），且它的 `SKILL.md` 与活文件的 inode 不同（GNU 上用
   `stat -c %i`，macOS 上用 `stat -f %i`）——相同就拒绝编辑。清单的安装说明要
   写解析后的真实路径，因为那才是用户必须覆盖的文件。范围与优先级：仅限暂存
   约束一切情境、一切规模的修改。SKILL.md 中的直接应用条款（"Acting on
   Observations"）决定的是小修改*何时*做——现在，而不是下次评审——从来不是
   *在哪里*做；它不授权原地编辑。
2. 永远以对活文件的全新读取作为编辑的基础——绝不用工作区副本、旧草稿或记忆。
3. 覆盖任何暂存/工作区副本之前，先与活文件做 diff；如果有差异，把你的编辑变基
   到活版本上。（观察到的失效：一次基于过期快照构建的更新，悄悄丢掉了同一天
   加进活技能的两个章节；只有合并前的 diff 抓住了它。）
4. 在任何跨副本同步或发布工作之前（线上安装、工作区副本、已发布的仓库/分支），
   枚举该工件的全部副本，并逐副本凭证据确立新鲜度——mtime、内容探针、哈希——
   绝不凭角色（"repo"、"线上版本"）；然后显式选定基底。在交互式会话的多轮工作
   期间，每轮开始前对暂存副本做快照（weekly-review.md，交付——一个无版本的
   暂存树没有其他基线），并在解读任何 diff 之前重新验证基线：对一个假定固定的
   基线出现 diff 收缩，意味着基线吸收了更早的修改（例如用户在会话中途安装了
   暂存更新），而不是编辑消失了。把意外的 diff 统计方向当作基线移动的信号，
   而不是编辑出错的信号。记录下来的测量遵守同一条规则：当一次交接记录了测试
   合并结果（一个冲突计数、一个 diff 统计）时，连同测量时所对照的基底提交或
   安装日期一起记录，并在据其规划之前对当前基底重跑测试合并——把旧结果当作
   指向冲突将聚集之处的指针，而不是一个计数。当一次修改的全部目的就是让某类
   机制变得不必要时，该类中的每个冲突块都以同样方式解决（取修改方），因此分类
   比计数更重要。
5. 把每次更新暂存到
   `[workspace folder]/skill-updates/[date]/[skill-name]/`（同一天的第二轮要使用
   带区分度的锚点——weekly-review.md，交付）——暂存完整技能目录（SKILL.md 加上
   references/、scripts/、assets/，如存在），绝不是只有 SKILL.md——并提交评审与
   安装；用户安装之前没有任何东西上线，而且用户一旦开始审阅该副本，它即被
   冻结——发现的缺陷只报告、不修改，直到评审结束（weekly-review.md，第 5 步
   常设规则，"评审开启对工件的冻结"）。在没有演示/上传工具的场合（例如 Claude
   Code CLI），改为在会话里呈现暂存路径和变更摘要；仅限暂存适用于一切环境——
   它是评审循环的安全属性，不是文件系统约束。对**每一个**技能，把暂存目录打成
   `.skill` bundle 并呈现 bundle，绝不呈现裸的 SKILL.md——无论文件多少都只有
   一种交付格式：把单文件交付约定套到多文件技能上会静默截断它（安装成功、技能
   加载，缺失的部分直到任务中途某次引用加载或脚本调用失败才暴露），而一条按
   文件数切换的约定每次都把这条边界留给使用者重新推导。**交付前门禁——在交付
   那一刻检查，而不只是在起草时。**条目清单就是 `weekly-review.md`"交付更新的
   技能"里的那道门禁；以下是其中编号相同条目的写作细节：(1) 暂存 SKILL.md 正
   文中每个不带限定的 `references/`、`scripts/`、`assets/` 路径都在暂存集中有
   对应文件——以所属技能名限定的路径（`<skill-name>/references/<file>`）是交叉
   引用，按构造豁免，而这正是引用另一个技能文件的约定（weekly-review.md，
   交付）。验证器提取占据整个反引号跨度的路径，也提取处于命令位的路径——在
   内联跨度或围栏块中跟在解释器（`python3`、`bash`、`node`、`uv run` …）之后、
   后面还带参数的路径——而只是作为示例被引用、不带解释器的裸路径不检查；
   (2) 交付工件是 `.skill` bundle——即使所有文件都已暂存，裸文件链接也过不了
   这道门禁；(3) frontmatter 约束——测量 description（折叠后的值，不是原始
   YAML 块），超过 1024 字符即交付失败，超过约 900 给出软警告，让贴边界的
   description 在变成别人的安装错误之前先收紧。触发词覆盖要在压缩中幸存：修复
   方式是收紧措辞，不是删掉触发词。测量交付集中的每个技能，而不只是失败的那
   一个——向触发词丰富的 description 倾斜的压力会把其他技能也推到边界附近，
   只有测量整个集合才能揭示这一点；(4) `name` 是 kebab-case 且与所在目录同名；
   frontmatter 可作为 YAML 解析且两个必需键都在。一个在任何位置含 `: ` 或
   ` #`、或以 YAML 特殊字符（`#`、`*`、`&`、`!`、`|`、`>`、`{`、`[`、`'`、
   `"`）开头或结尾的 `description:`（或 `name:`）值，必须加双引号或改写——值中
   不带引号的 `: ` 会把该行其余部分变成嵌套键，整个块停止解析；不带引号的 ` #`
   更糟：YAML 在那里开始一段注释，块仍能解析，值在空格处静默截断（`see #146`
   和 `{Author, 2021 #123}` 被截断；`page#section` 不会，因为注释需要那个空格）。
   验证器在一个明显有 `name:` 行的 frontmatter 上报告"`name` missing"，那是
   不可解析块的签名，不是缺字段：修引号，不要修名字。observation-log
   frontmatter 的引号规则不通过类比迁移到这里；它写在这里，是因为这里是技能
   frontmatter 被写作的地方；(5) 打包归档的成员路径不含反斜杠——按原始中央
   目录字节读取，因为 CPython 的 `zipfile` 在读取时把 `0x5C` 归一化成 `/`，会把
   畸形归档报告成干净；Windows 的 `Compress-Archive` 对任何带子目录的技能都会
   产生恰好这个缺陷。`scripts/validate-skill-bundle.py` 把这道门禁的机械条目
   实现为断言，并在任何平台上打出格式正确的 bundle；在有 Python 的地方运行它。
   这道门禁对已发布技能的一次人工通读，是上面的保密层级 9——点名的，不是断言
   的。总体而言：消费平台强加的任何硬限制，都应作为"同一步中与上限比较的测量"
   进入这道门禁，而不是作者被指望记住的规则——一条未被断言的指标不只是漏检
   缺陷，它制造"没有缺陷"的信心。把限制写成数字，并标注为消费方的限制。**一条
   被推荐的检查携带三个测得的数字。**在提议一项自动检查或一条新门禁规则时，
   先把每个候选跑过现有语料，并逐规则记录：(a) 在今天语料上的命中数，(b) 其中
   的真缺陷，(c) 去除其余命中所需的归一化。这些没有一个能从想法本身得知——在
   一个语料上测得：一个候选类产生 35 个命中，几乎全是 locale 伪影；两个产生
   0 个命中（免费的锁，今天就能加）；一个产生 7 个，其中 2 个是缺陷，5 个是
   天真规则会永远误报的合法内容。一项被提议的守卫是关于未来的主张，而它最便宜
   的证据已经存在于被审计的工件之中；一条未测过误报率的规则，是在提议让人们
   忽略一项测试。（在起草时读这条规则，不等于在交付时执行了它；把门禁作为
   呈现前的最后一步来运行。）打包卫生：压缩之前，清查暂存树中被会话内检查留下
   的构建产物（`__pycache__/`、`*.pyc`、`.DS_Store`、`.~lock.*`）和克隆种子
   带入的版本控制目录（`.git/`、`.hg/`、`.svn/`），并在压缩后回读归档清单——
   清单能抓两类缺陷，泄漏的产物和错误的路径分隔符，而它只会为你点名的那一类
   被读，所以要显式查两类。
6. 通过从只读挂载复制来生成暂存副本时，立即重置写权限——挂载的只读模式会随
   副本传递，目录和文件都一样，否则后续编辑会以权限错误失败。对单个文件，`cp`
   之后 `chmod u+w`（或 `cp --no-preserve=mode`）可行。对目录树，在本环境中
   `cp --no-preserve=mode` 不可靠：即使顶层文件复制成功，在（`references/`、
   `scripts/`）被复制的子目录内创建文件时，它仍以"Permission denied"失败过。
   目录树唯一经过验证的序列是：先 `mkdir -p` 建目录结构，再逐文件 `cp`，最后
   对暂存路径 `chmod -R u+w`。一条被记录成"与另一方案等价"的变通方案，必须在
   每个失效面上重新验证——对单个文件可行的选项，仍可能在目录树上失败。使用
   `weekly-review.md` 第 5 步中的原样代码段，而不是凭这段描述重建：剥掉活路径
   前缀时**不带**尾部斜杠，让顶层目录映射到暂存根；并在读取循环上保留 `IFS=`，
   以处理含空格的路径。这两点都很容易只凭这段描述做错，而产生的幽灵目录在一个
   拒绝 `unlink` 的挂载上无法删除。
7. 让流程的严格程度匹配修改本身：复杂/开源/设计不确定 → 有 skill-creator 就
   用；需求已在对话中确立的内部类技能 → 直接写，但把重大修改标出来供评审。
8. **在暂存一次重写之前，枚举技能目录之外重述其规则的所有界面。**一条规则的家
   是一个位置；它的到达范围是每一件复述它的工件，而它们住在拥有该技能的目录
   所看不见的目录里，所以无论对技能文件夹的 grep 多么彻底，都会报告干净。要紧
   的界面是那些独立于技能执行的：定时任务提示词首当其冲，其次是 CLAUDE.md 或
   其等价物中的激活片段、保存的快捷方式、交接文档。枚举它们（一份定时任务清单
   每个任务返回一个路径，所以这是一次调用加一次 grep），然后在同一轮里逐个
   更新，或者按上文"配置与流程"把副本替换成停止条件——包括那句说明省略是刻意
   的条款，否则后来的编辑者会好心地把摘要加回去。不对称性正是这一步不可协商的
   原因：过期副本从不大声失败。它继续运行，貌似合理地做着已被 superseded（取
   代）的事，唯一的目击者是用户在几周后注意到，被要求停止的旧行为又出现了。而且
   漂移很快——
   预测它的是源的变化速率，不是副本的年龄（观察到：一条防漂移规则从写下到被
   现场违反只隔四天，发生在一个规则正处于密集重写中的技能里，只因那条提示词
   碰巧为无关的原因被打开才发现）。

   **改名是一次迁移，不是一次编辑。**在技能由账户或应用托管的场合，新名字下的
   技能就是一个新技能。改名之前，在观察日志（活跃与归档）的 `skill:` 字段、
   `skill-families.md`、横切原则、定时任务提示词、同族路径（`../<old-name>/`）、
   复制的脚本头和记忆笔记中 grep 旧名。上传改名后的技能，验证它能加载，在同一
   步里停用旧的，然后更新 grep 找到的每一个界面。删除旧技能由用户决定。
9. **向有序结构插入是拼接，不是替换。**字符串替换编辑的是文本，而一个列表、
   一张表格、一个 `## Contents` 索引、一个 frontmatter 块或一段编号步骤序列是
   结构，锚点相对插入只有在你知道锚点旁边是什么时才安全——而 `replace` 无法
   断言这一点。观察到：一条列表项以"条目 + 空行 + 锚点"的方式被前置到列表后面
   的段落之前，把列表自己的收尾空行推进了列表中间；渲染后一个列表变成两个，
   而且这个缺陷躲过了验证器运行、保密扫描和提交评审，因为一行*未改动*的文本
   相对邻居移动了，而这三次阅读都不看形状。所以：解析成行，用**结构谓词**定位
   插入点（匹配 `^- ` 的最后一行、空行前的最后一行、新键排序所跟随的那个键），
   拼接，再合并。绝不要以相邻段落的文本为锚。在仍然使用替换的场合，先断言邻居
   的形状——锚点上一行是最后一个列表项、你要加的空行尚不存在——不一致就大声
   失败。`scripts/validate-skill-bundle.py` 的 repo 模式门禁能在事后抓住列表这种
   情形；谓词则在事前防止它。

**验证编辑是另一个问题，而且加载器在跟你作对。**上面的规则覆盖"安全地编辑"；
没有任何一条覆盖"事后确认编辑已生效"。三样东西被混为一谈——磁盘上的文件、
加载器注入本会话的副本、一个全新会话将收到的内容——它们可能同时各不相同。

在一次会话中观察到：加载器提供的是某个 `SKILL.md` 的*上一代血统*，缺了整整一节，
并在一条格式标准上陈述了相反的规则；而磁盘上的文件（哈希已验证、45 分钟前刚在
同一个会话中编辑过）承载的是修正后的文本。若从注入副本作答，会在一个规范性
问题上给用户恰好错误的答案。它之所以被发现，只是因为有人拿一句字面引文去 grep
磁盘上的文件。

显而易见的补救同样失败：起一个子代理来模拟"全新会话"并不能打破冻结。子代理的
上下文从冷启动，但它的技能来自**同一份快照**，于是它报告同样的陈旧内容，还多了
一层貌似独立检查的权威。

所以：**通过读取磁盘上的文件来验证编辑**，绝不问已加载的技能它说了什么，也绝不
问子代理。而当问题是*未来*的会话将收到什么时，只有一次真正的新会话能回答——
正在安装的会话在结构上做不到。

## 以机械化方式声明块的作用域

指令文件、技能或共享配置中的一段，往往只适用于一台机器上的一部分工作。通常的
做法是相信代理能从上下文注意到无关性。这会安静地失败，而且朝着造成损害的方向
失败：为一个领域写的建议，被自信地应用到另一个领域。

改为在块的开头写一个**可检测条件**——代理可以检查而不是推断的东西：

> 仅当项目存在带 `react` 依赖的 `package.json` 时适用。在其他一切项目中，
> 完全忽略本节。

在一台服务于两条互不相关业务线的机器上，观察到它在同一次会话中双向生效：工作
目录是文档文件夹时，该节保持沉默；React 项目一打开，它就接管整个工作流。

**显式写出否定分支**，因为被省略的恰恰是那一半。"适用于 X"读起来像完整陈述，
把其余情形留给代理自行决定；"在其他一切情况下完全忽略"才是让这个块可以安全
携带的那句话。没有陈述否定分支的条件是一个偏好，不是一个作用域。

优先选择代理可以低成本、就地测试的条件——某个文件是否存在、一个路径段、一条
声明的依赖——而不是需要判断的条件（"在处理前端任务时"）。

## 验证迁移与重构

两种模式，选错模式正是一个好改动看起来坏了的原因。**逐字迁移**——内容原样
移动——逐行验证，用下面的两级检查。**合并或抽取**——多个重叠来源调和成一个
目的地，措辞被重写，工具或客户名在途中被泛化成能力语言——逐节验证，因为每一行
被移动的行都理所当然地过不了精确匹配，行级 grep 层会在一次完美合并上报告全面
丢失。

对合并或抽取，用**强制的"来源章节 → 目的地"覆盖表（每个迁移者一份）**替换行级
grep 层：每个来源的每个小节标题都有着落——已移动 / 已并入 / 留在配套件中 / 带
理由放弃——旁边记录只有一个来源承载过的内容、刻意留下的通用内容，以及所做的
替换。保留逐文件的词数健全性检查——它便宜，而且能抓住整块遗漏。并且**拆分小节
的迁移者写两侧目的地**：把材料移出某个技能的人，同时为相同小节写该技能的剩余
部分。互补性——两处没有重复、两处之间没有遗漏——事后检查的成本远高于产出时
保证的成本，而把两半拆给两个作者，必然造出一条无人负责的接缝。覆盖表才是合并
被接受所依据的工件；diff 不是。

对逐字迁移，"没有丢失"可以机械化检查——但只能用两级检查：

1. 通过旧基底与新基底的 `diff`，枚举每一行新增/移动的行。
2. 将每条非空行与重构后的文件集做精确匹配：`grep -qF -- "$line" "$file"`——
   `--` 是必需的，否则以 `-` 开头的 markdown 行会被解析成选项，`grep` 报错退出，
   该行被记为丢失（一次运行中，35 条真实丢失旁边有 31 条假丢失）。同样的要求
   适用于所有把文件内容插入到参数位置的嵌入式代码段。
3. 对未命中项，先用行中有辨识度的子串做实质检查，再下丢失结论——大多数未命中
   是容器伪影（标题层级变化、列表转散文的适配、重排行把一个短语拆到多个换行），
   不是真实丢失。
4. 逐文件的词数健全性检查。
5. 在以上任何步骤之前，先归一化行尾。用 `core.autocrlf=true` 做出的 checkout，
   或者一份保留 LF 的下载与一个改写成 CRLF 的克隆并存，会让 `diff -rq` 报告
   每个文本文件都变了、`grep -qF` 把每一行都记为丢失——而同一 bundle 里的两张
   PNG 比较结果却相同，这正是判别特征。用 `diff --strip-trailing-cr` 比较
   （或用 `dos2unix` / `tr -d '\r'` 处理到临时副本），并在 grep 前剥掉每条
   `$line` 的 `\r`；一场唯一差别是行终止符的验证，什么也没有发现。

**内部交叉引用密集的单体：保持章节编号全局，加一张映射表。**当被拆分的文档充满
将横跨新文件集的内部交叉引用（§13.6、§8.3.3b …）时，绝不要按文件重新编号——
重编号会破坏每一条引用，或迫使一次高风险的重写。经过验证的模式（一个约 5k 行
的技能拆成核心 + 8 个参考文件，零内容丢失）：在整个文件集上保持原章节编号全局；
用逐字行区间抽取移动内容，不做任何改写；在核心中加一张"章节映射表"，把 §N
解析到文件；给每个参考文件一行指向映射表的头部。标识符空间是一个接口——让它在
拆分中保持稳定并加一层解析，而不是为了匹配新容器而给内容重编号。推论：映射表的
加载触发条件必须写成强制（"运行 Y 之前先读 X"），而且当超出部分确实是每次调用
都要用的原则性内容时，核心尺寸适度超过约 500 行的指引是可以接受的——把这条
理由写在下一个编辑者会看到的地方。

只有一级，要么漏掉丢失（只查实质），要么狼来了（只查精确）。**检查器也是代码，
而且是流水线中测试最少的代码**——一次写就、一次运行、从未对夹具演练过。按行
匹配来统计记录头（先切分，再锚定），不要用对整文件文本的 `^` 锚定正则，它的
多行标志语义因语言而异，并会静默失败成"1"。在信任任何检查器的结论之前，先校准
它：断言它能在未改动的原始文件上复现一个已知（KNOWN）计数。校准不过的检查器，
今天是假警报，明天是静默通过。此外，把原文的强制机制（检查点、断言、不变量、
强制写入规则、默认值）清点成一份显式清单——压缩会优先摧毁强制机制，因为它读
起来像冗余——并对任何"纯重构"的修改清查净新增行为，它在大规模改写 diff 中藏得
很好。

**把迁移构建成可重复执行的推导，而不是一次性补丁。**在构建时刻的基底上验证过的
迁移，只对那个基底正确。如果交付前有一条并发编辑落在活文件上——恰好落在被移动
的块内——把完成的目标文件直接铺到新的 tip 上，会**静默回滚它，且不报告任何
冲突**，因为交付中没有任何东西与它正落上去的那个 tip 比较。Git 在这里救不了你：
迁移是一组完整文件，不是补丁，没有可以冲突的东西。

观察到：一次把单文件拆成核心加新参考文件的工作，用三种方式构建并验证（对旧基底
的行区间 diff、对新文件的精确匹配、词数检查），全部通过——对照的是一小时前的
基底。其间，被移动块内的一行已经变了。

所以把迁移表达成**可以从活基底的当前状态重新推导**的东西——一个脚本，或精确到
可以重跑的流程——并在交付之前立即重新推导，而不是信任更早的验证。在手工补丁
确实是唯一选项的场合，交付时对被移动区域与活 tip 做 diff，任何差异都停下。要紧
的验证是针对你正落上去的状态的验证，不是针对你出发时状态的验证。

## 试用设计——测量行为是否在无提示下触发

当一项修改处于试用中，而被测量的是代理是否有机地（ORGANICALLY）做某事（因为
工作需要而加载参考文件、未经指示就应用规则）时，把试用的触发条件记录在被测代理
不会读到的位置——一份维护者笔记或评审报告，绝不在任务文件、CLAUDE.md 或交接
提示词里。在试用的定义中加入一条显式作废条款：任何启动文本点名了触发条件、或
直接指示了该行为的会话，一律作废，不计入任何一侧。并刻意为负面情形布控——把
"范围内有实质工作、无有机加载"记录为一条独立的数据点。原则：点名被测内容的
指令是干预，不是描述；启动文本与测量装置必须分居两条通道，否则试用测的是对
提示词的服从。推论：空结果需要主动记录，否则试用无法区分"尚未观察到"与"没有
发生"。

## 新建技能

**在同级旁边构建：把继承的步骤与必要的步骤分开。**家族的新成员继承其同族技能
的形状，而与家族保持一致本身是正当的设计价值——这恰恰是"继承但不必要"的步骤
能活过评审的原因。它读起来不像错的；它读起来像属于这里的。

观察到：一个家族的每个成员都以识别主管机构开篇，因为每个成员的产出都取决于
适用哪套规则。新成员照抄了这一步，并要求先确定机构才能开始任何工作。用户的
纠正只有一行：*别问机构——直接问我每种要几个。* 他们本来就知道数字。一个继承
来的问题，把一行输入变成了两步盘问。

能发现这一点的人，是必须回答该问题的那个人，而到那时它已经发布了。所以把它
变成一个显式的写作步骤：对每个从同族技能复制的步骤，写明**如果去掉这一步，
本技能的产出会损失什么**。答案是"一致性"的步骤是继承的，不是必要的——删掉它，
或者降级成可选分支。

**在为某个库、工具或项目编写技能之前，先检查该项目是否已经自带一个。**"给 X
做个技能"的反射是去读 X 的文档、从零写一个 `SKILL.md`；许多项目现在在仓库里
自带官方代理技能——通常在 `agent-skill/`、`.claude/skills/`、`skills/` 之下，
或在 README 中被点名——在它旁边手工重写是重复劳动，会偏离维护者的版本，并错过
他们的更新。对上游仓库搜一次（上述路径，加上 README 和发布说明里的"skill"一
词）就能定论——这是本技能允许的两次网络使用之一，而且只在用户要求该技能之后。
如果官方技能存在，安装它，并只把本地增量放进配套技能，与对待任何其他上游维护
技能的方式完全一致（weekly-review.md，第 2 步）；如果不存在，自己写，并考虑把
成果回馈上游。另外，在从零编写任何技能之前，先在
`[workspace folder]/skill-updates/*/<skill-name>/` 下查找未安装的草稿（`find`，
如 weekly-review.md 第 5 步）：一份从未上线的暂存副本没有活文件可以 diff，流程
中的其他环节都不会把它浮现出来，而它旁边一份从零写的草稿会丢掉它承载的一切。

有 skill-creator 可用时使用它，把观察条目作为简要书传入。尽早确定类型：
开源类（open-source）→ 剥离并泛化；内部类（internal）→ 自由纳入具体信息；
不确定 → 默认开源类（open-source），让用户之后再补充内部细节。

**先决定这个技能是否加入某个家族；如果加入，动笔之前先读同族技能。**意图 →
访谈 → 起草，对真正全新的技能是对的，对加入现有家族的技能是错的（注册表是
`skill-observations/skill-families.md`；见 `observation-log.md`），因为家族已经
包含答案的大部分，只是不均匀地分布在各个成员之中。凭当前会话的经验起草、只凭
恰好记得的部分去请教同族技能，会产出第三个发散的成员：观察到，一个新技能带上
了两个同族都没有的类别，又漏掉了某个同族已有的两个，让一个家族从两个不一致的
成员变成三个。成本是不对称而且前置的——先读两个同族只要几分钟；事后调和三个
发散的技能，意味着全部重读、逐规则判断每处分歧是否有意为之、在三个地方编辑，
而分歧恰恰因为每个技能单读都自洽而最难被发现。

完整阅读每一个同族技能，对照它们起草，并在交付物中附一份简短的**调和说明**，
而不是当作可选作业：(a) 取自同族技能的内容；(b) 新技能新增、而同族技能也应该
获得的内容——记录为点名那些同族技能的观察条目，绝不悄悄吸收；(c) 刻意省略的
同族内容及原因。这份说明把一个新的家族成员从漂移源变成对漂移的纠正。然后用新
成员更新注册表。

两个推论。当家族的共享材料相当可观时，起草前的通读是询问它是否应抽取成成员
加载的核心技能（`shared-core`）、而不是第三次复述的天然时机——这个问题在第三
份副本存在之前回答成本最低。以及那条远超技能范围的泛化形式：**一个新实例是对
现有集合可得的最好审计。**起草它，迫使共享材料从零重述，而新表述与某个同族不同
的每一处，要么是改进，要么是缺口。每当一个新实例加入一组平行实现时，先读这组
实现——不是因为新实例需要它们的内容，而是因为这是所有实现之间的差异唯一被人
主动思考的时刻。跳过比较，既浪费了这次审计，又制造了发散。

**当抽取真的发生时，按简要书先行。**先写一次拆分规则，再动任何文件——决定一句
话去向的测试（*这句话去掉平台名还能活吗？* → 核心；否则 → 配套件）、保密规则、
泛化替换，以及任何全局编号规则——并把这一份简要书交给每个迁移者，而不是让每个
人从面前的材料里重新发现规则。然后给每个目的地文件指定唯一迁移者，并要求该
迁移者产出其拆分的每一节的**两半**（核心文本与配套件的剩余部分），外加"验证
迁移与重构"中的覆盖表。维护者评审的交付物是调和说明，不是 diff。两个独立迁移者
标出同一个歧义，意味着缺陷在简要书里：修简要书并重新下发，而不是去裁决产出。

**随技能发布的脚本，要用对抗性测试验证，而不是普通运行。**以下每种失效形态都
能通过一次普通运行，只有专门为破坏它而构建的测试才能抓住。

1. 一个改写文件局部的脚本，要么按字节读写，要么保留每一行自己的行尾：文本
   模式 I/O 会重写 CRLF 文件的每一个行尾，而被编辑的值却是对的。用 CRLF、一个
   BOM 和无结尾换行来测试，并断言编辑区域之外字节一致。
2. 一个否定性要求（"绝不打开私有名单文件"）需要一个运行时观察机制、一个断言该
   机制至少记录了某件事的断言，以及一次针对故意破坏版本的、让测试变红的运行。
   否则接错的检查会空洞地通过。
3. 验收夹具与其运行器一起发布（本技能的是
   `scripts/validate-skill-bundle.py --selftest`），否则它会退化成下次改动之后
   没人再跑的一次性产物。
4. 一个会写东西的脚本，首次冒烟运行指向一个一次性目录，并断言默认位置未被
   触碰：一个重新声明全局选项的子命令可能覆盖它，冒烟测试就会写进真实的家
   目录。
5. 变异测试先用测试装置自己的命令证明基线为绿，而且每个测试断言是哪一道守卫
   拒绝了输入，而不只是有东西拒绝了。死于异常或导入错误的变异体要调查，不计为
   被杀；幸存的变异体意味着加固夹具，或删除冗余条件。

## 运行时前提——声明技能运行所需条件

一个驱动自身之外事物的技能——一个 CLI 二进制、一个守护进程、一个 API 密钥、
一个容器运行时——它的"已安装"程度，取决于它驱动的那个东西。技能清单里的存在
只说明文件在那里。它对调用它们能否工作，不说明任何东西。

由此产生的失效具体而昂贵：代理读到一段完整、自信的描述，为它点名的那类任务
选中该技能，却在工作做到一半时才发现缺少前提。它读起来像代理的错误而不是清单
的错误，而它被选来做的那项任务已经完成了一半。在一个被报告的技能资产中，针对
单一安全工具的九个技能与能用的技能并列在清单里，无法区分；那个工具需要
Docker——缺失——还需要一个不在用户订阅范围内的付费 API 密钥。采用者唯一的防线
是 `CLAUDE.md` 里一条手写的、点名全部九个的禁令——一条必须被读到并被遵守的
规则，而不是系统知道的一个事实。

同一份资产说明了为什么这必须是必备要素而不是良好实践：一次审计发现，9 个成员
中 2 个在自己的 `SKILL.md` 里声明了前提，7 个没有。一旦留成可选，家族就会漂移。

**对任何驱动外部工具的技能，这是必备项。**把前提声明为*可检查的事实*，让人类
读者之外的东西也能评估它们：

```yaml
requires:
  - binary: docker          # on PATH
  - env: OPENAI_API_KEY     # set and non-empty
  - service: http://localhost:11434   # reachable
```

三种形态几乎覆盖一切：`PATH` 上的一个二进制、一个已设置的环境变量、一个能应答
的端点。每一种都是一条廉价命令。任何无法归约成这三者之一的东西，写成技能正文里
的散文说明，而不是声明——一条没人能运行的检查比一句诚实的话更糟，因为它看起来
像保证。

**谁来消费它。**Session Start 第 6 步解析 `skill:` 目标并报告解析失败的那些；
有了这个块，它还能报告那些能解析*却无法运行*的。一个死目标和一个已删除的目标
都意味着"观察条目正在一个永远不会据此行动的东西上积累"，而对任何驱动外部工具
的技能来说，死目标是更常见的情形。

**一般原则。**注册表里的存在不是能力。任何供代理从中选择的清单都需要一个存活
维度，因为它否则产生的失效——自信地选中一个列在清单上却无法运行的东西——在
选择时不可见，在使用时昂贵。

## 退役技能——退役前先收割

一段合作关系的结束是一次收割触发器，不只是清理触发器。在让任何与该合作绑定的
运营技能退役之前，把每一节评估为可迁移方法论或客户特定配置。如果可迁移的占比
可观，先（FIRST）抽取一个与客户端无关的技能，之后再让原件退役，并保留客户档案
以备查。有效的抽取模式：平台机制保持具体——真实的接口怪癖、DOM 模式、分层
诊断、一切通过真实运行和真实修正挣来的东西——并把客户的答案（账户 ID、域名、
来源清单、判据）替换成当初引出这些答案的进场问题。得到的技能告诉下一个代理该
问什么，而不是上一个客户碰巧说过什么。原则：运营技能中的方法论与包裹其外的
客户配置，保质期截然不同。把它们一起退役，是在耐久那一半的成本已经沉没的时刻
丢弃它，而且丢失不可见，因为没有任何东西报错。

## 原则传播

当一条观察条目的原则适用于技能的一般情形时，以 `skill: []` 和
`target_file: [skill-observations/cross-cutting-principles.md]` 记录它并呈报；
如果用户批准，把它加入
`[workspace folder]/skill-observations/cross-cutting-principles.md`。那个文件是
任何技能创建或再生成期间的一份强制清单。传播时机由用户选择：立即（现在就更新
所有技能——适用于保密规则之类）或机会式（在每个技能下次更新时应用）。

```markdown
# Cross-Cutting Principles

Principles that apply to all skills. Read as a mandatory checklist during
any skill creation or regeneration.

---

## Active Principles

### 1. [Principle title]
**Added:** [date]
**Applies to:** [all skills | all open-source skills | all skills with rules]
**Requirement:** [what it requires]
**Propagation:** [immediate | opportunistic]
**Status:** [active]
```
