# 观察日志——存储布局、脚本与缘由

核心技能承载每次调用层面的规则：日志在哪里、如何为文件命名与编号、
frontmatter 格式，以及归档规则。本文件完整承载布局、辅助代码段，
以及规则背后的推理。在首次搭建目录时、在归档时、在编号或
frontmatter 看起来不对劲时，以及在改动任何其他工具或技能读取本
日志的方式之前，加载本文件。此外，正如核心技能的指引所示，在处置、
驳回或引用某个观察条目之前、在设置 `parked` 或 `reference:` 之前、
在新增或修改执行触发器或在日志之上编写新仪器之前，以及每当扫描、
清扫或编号探针返回空时，也要加载本文件。

## 布局

```text
skill-observations/
  observation-log/       # the log IS this directory: one file per observation
    0001-short-slug.md
    0002-short-slug.md
    archive/             # resolved observations, moved here after the grace period
      .id-floor          # highest id ever issued; the counter never drops below it
      log-YYYY-MM-DD.md  # legacy monolithic archives from pre-3.0 installs, if any
  cross-cutting-principles.md
  skill-families.md      # declared families: members, shared vs member-specific,
                         #   coherence model (created when the first family is named)
  last-review-date.txt
  reviews/               # one record per review run: reviews/YYYY-MM-DD/REVIEW.md
                         #   (weekly-review.md Step 8; kept, never pruned by a step)
  checkpoints.log        # append-only acknowledgement markers (optional)
```

`observation-log/` 中的每个文件都遵循核心技能（How to Log）中的
frontmatter 格式。没有需要保持同步的中央索引：目录列表就是索引，
frontmatter 就是元数据。无论本技能还是任何其他技能说到"观察日志"，
指的都是这个目录。

### 工作区创建

一条幂等命令，然后一个断言。会话启动步骤 1 指向这里：运行它，
不要照着上面的目录树手工逐项创建。

```bash
d="C:/Users/Administrator/.zcode/skill-observations"   # the pinned path, quoted: it may contain a space; bash, not sh
[ -e "$d/log.md" ] && [ ! -d "$d/observation-log" ] && { echo "LEGACY log.md — run the migration (references/migration.md) before creating anything"; exit 1; }
c=; for x in observation-log observation-log/archive last-review-date.txt cross-cutting-principles.md; do [ -e "$d/$x" ] || c="$c${c:+,}$x"; done   # what this run creates
mkdir -p "$d/observation-log/archive"
[ -e "$d/last-review-date.txt" ] || printf 'never\n' > "$d/last-review-date.txt"   # the literal `never`, never a date: a date means a review actually ran
[ -e "$d/cross-cutting-principles.md" ] || printf '# Cross-Cutting Principles\n\nPrinciples that apply to all skills. Read as a mandatory checklist during\nany skill creation or regeneration.\n\n---\n\n## Active Principles\n' > "$d/cross-cutting-principles.md"
for x in observation-log observation-log/archive last-review-date.txt cross-cutting-principles.md; do
  [ -e "$d/$x" ] || { echo "WORKSPACE SETUP INCOMPLETE: $x"; exit 1; }
done
printf '%s [%s] workspace: created=%s\n' "$(date '+%F %H:%M')" "${PWD##*/}" "${c:-none}" >> "$d/checkpoints.log"   # step 1's trace
```

`mkdir -p` 会创建父目录，所以 `observation-log/` 不需要单独一行；
`[ -e ]` 守卫使这条命令在既有工作区上重复运行也安全，这正是让
步骤 1 无条件运行它、而不必先判断是否需要搭建的原因。旧版守卫
最先运行，因为一旦创建了 `observation-log/`，就会掩盖那个唯一能
识别 3.0 之前安装的条件。原则存根是 `skill-authoring.md` 中模板
（"Principle Propagation"）的头部；两处要一起改。

**步骤 1 会留下痕迹。**最后一行把本次运行创建了什么追加到
`checkpoints.log`——普通会话是 `created=none`，全新安装或修复后的
安装则是产物名称。除此之外，创建是会话启动阶段唯一不被任何东西
记录的动作：当复核发现原则文件缺失时，一个从未运行的步骤 1 和
一个后来被删除的文件看起来一模一样，只有痕迹能把它们区分开。
其他文件在会话启动时按同样条款创建，服务于测试计划而非这条
命令：`starter-principles-reviewed.txt`（起步集核对）和
`skill-families.md`（在第一个家族被命名时创建）。

**allowlist 所指路径上的只读或权限错误是路径缺失，不是日志
不可写。**当这条命令在工作区路径上以 `Read-only file system`
或权限错误失败，而该路径正是 harness 写入白名单所指名的路径时，
最可能的原因是路径尚不存在、沙箱无法创建它（`environments.md`，
"工作区锚定"、"授权只点名路径，不创建路径"）。用一行话把这
一点告诉用户，并把修复方法交给他们——在沙箱之外从钉定根目录
创建 `skill-observations/` 和 `skill-updates/`——而不是换另一个
接口重试，也不是滑落到"日志不可写"或"无文件系统"分支。

**为什么用一条命令而不是它取代的散文清单。**在一次全新的用户
作用域安装上观察到：某个会话创建了 `skill-observations/` 和
`observation-log/` 之后再无其他。下一个会话无从分辨——步骤 1 的
探针是对钉定路径做一次 `ls`，路径解析成功、`observation-log/`
就在那里，而没有任何东西复查它的兄弟产物。只要没人细看，工作区
从外面看一直是搭建完毕的样子。

断言循环才是要紧的那一半，因为四个产物以不同方式失败，而其中
只有一个会自己抱怨：

| 缺失 | 如何暴露 |
|---|---|
| `observation-log/` | 立即，在第一次扫描时 |
| `archive/` | 在第一次写入时，编号代码段读取 `.id-floor` 或向其中 `mv` 时 |
| `cross-cutting-principles.md` | 在第一次复核时 |
| `last-review-date.txt` | 只有当步骤 3 施加自己的重建规则时——否则复核触发器永不点火，且没有任何东西说明这一点 |

这与本技能此前为归档解决的问题同形，解法也相同——写在另一个
动作旁边的散文职责不继承该动作的任何强制力，所以归档清扫被折叠
*进*编号推导代码段（"如果一个步骤必须总是伴随某次工具调用，就
把它放进同一条命令"，Archival on Write）。步骤 1 的创建是这套
推理尚未应用到的最后一个地方。

### 代码段接收含空格的路径，且必须以 bash 运行

**替换进来的路径经常含空格**——至少一种常见安装的默认共享文件夹
名就含空格——因此对它的每一次展开都保持双引号，任何代码段都不得
让它经过词切分（`for f in $(find …)`）：一个在空格处切分自身路径
的清扫会检查零个文件，打印没人读的错误信息，并让它所寄生的那条
命令照样成功。

**本技能中的每个代码段都是 bash，不是 POSIX `sh`**——编号代码段
的 `10#` 算术是 `dash` 和 `ash` 都拒绝的 bash 扩展，所以在 `sh`
之下推导在任何文件存在之前就停止，而改造过的代码段可能失败得比
这更安静。`bash` 代码栅栏只把这一点告知人类读者，对其他任何东西
都不起作用，所以要显式地以 bash 调用这些代码段；某个代码块碰巧
也兼容 POSIX（清扫）只是偶然，不是对其余代码段的承诺。

## frontmatter 字段

| 字段 | 含义 |
|---|---|
| `id` | 整数；与 `NNNN-` 文件名前缀一致——四位、零填充（按代码段和脚本写入的 `printf '%04d'`），这样列表按数值排序，冲突也在列表中可见；`63-` 出现在 `0063-` 旁边，就是一个编号出自代码段之外的什么写入者。永不复用。 |
| `title` | 简短的描述性标题。它是每次复述检查与 frontmatter 扫描匹配所依据的摘要，而且编辑正文不会更新它：当追加的实例拓宽了发现时，要在同一次编辑中重写标题，否则对更宽发现的下一次复述会漏掉它并把它当作新条目归档。 |
| `status` | `open`、`actioned`、`declined`、`superseded`（后续观察条目发现本条的缓解不奏效；`resolution` 指名它）或 `parked`。缺失的状态读作 `open`，绝不读作不存在。 |
| `parked`（状态值） | 已决断，但被外部前置条件阻塞：条目本身健全、不再等待裁决，因此复核把它移出工作队列且永不重新上报。它不是已解决，所以不归档——见下文"归档"。它留在 `observation-log/`，直到其 `parked_until:` 条件满足（把它设回 `open`）或它被真正解决。以自由文本记录一个搁置、同时留着 `status: open` 是行不通的：没有东西按散文分类，所以条目留在队列里，每次复核都被重新提起。 |
| `parked_until` | **只要状态为 `parked` 就必填**，否则留空。一行指名解除搁置的条件（"the X scheduled task is re-enabled"），措辞要让后续复核不必重开原决定就能回答是或否。 |
| `type` | `open-source` 或 `internal`（见核心技能中的 Taxonomy）。 |
| `skill` | **始终是列表**，即使只有一个条目，使任何消费者都不必在字符串与列表之间分支。第一个条目是主条目。可以为空。每个名字都写它的裸形式——所列名字最后一个冒号之后的部分——只在两个已安装技能共用同一裸名时才限定为 `plugin:skill`；限定条目要加引号：`["plugin:skill", other-skill]`（见下文）。裸形式是规范形式，因为它是写入者实践中实际产出的形式（两条规则对比时 40 个条目中 0 个是限定的），而一个技能两种拼法就是两个复核分桶。一切按技能名进行的查找——带技能名槽位的 grep、`scripts/skill-load.sh`——都会把 `plugin:name` 归约为最后一个冒号之后的部分再匹配：裸模式能同时命中两种拼法，而限定模式会漏掉每一个以裸名归档的条目并干净地返回零。 |
| `proposes_skill` | 以工作名列举的新技能候选。与 `skill` 相互独立；任一可为空，也可同时有值。 |
| `target_file` | 路径列表，用于正确归宿不是某个技能的观察条目：一份指令文件、一条记忆笔记、一份代理简报、某个例程读取的登记表。指名修复真正要写入的文件，让复核能直接去那里，而不是把条目重新映射到最近的技能上。在 27 条遗留条目的首次复核中实测：15 条在 `skill:` 里指名了非技能（"browser verification protocol"、"documentation hygiene"），每一条都得先人工解析成路径，复核才能开始。 |
| `siblings_checked` | **必填，永不留空。**记录同族检查已发生及其结论：家族名、评估过的成员、每个成员的判定（已传播/已排除）。每项**排除**都携带其依据——在该同族技能中读过的文件与章节（或行），证明它不适用——或字面记号 `assumed`；纳入不需要依据，因为纳入同族技能是安全的错误。`assumed` 排除是复核事项，不是已定判定。`none` 只用于目标不属于任何家族的情况。缺失或为空＝未经同族检查归档，复核也如此计数。 |
| `area` | 技能或工作流中涉及的部分。 |
| `date` | 归档日期，`YYYY-MM-DD`。 |
| `session_context` | 当时在做什么。 |
| `resolved` | 解决日期；仅在状态为 `actioned`、`declined` 或 `superseded` 时设置。归档以它为门禁。 |
| `resolution` | 做了什么，或为何否决。当修复是一份处方（一条规则、一个检查、一种要使用的表单）时，`actioned` 的 resolution 要指名它如今安身之处——一个文件与章节、一份暂存的技能副本，或一条已登记的积压条目。如果指不出这样的地方，这份处方就只是被描述过、没有被实施：让条目保持 `open`，或者解决已落地的部分、把其余部分装进一条承载观察条目（见下文）。复核自身的 resolution 已经指名暂存副本（`weekly-review.md`，Step 6）；本条规则针对在复核之外设置的 resolution。 |
| `reference` | 可选路径，指向已保存的会话本地证据。 |
| `commands_verified` | 正文引用的每个可执行命令对应一个分句：`run` 加上它返回了什么，或 `NOT RUN` 加上原因；正文未引用命令时写字面 `none`。正文引用了命令而此字段为空，意味着该命令从未运行。见下文"观察条目内部的命令"。 |
| `skill_qualifiers` | 可选映射：技能名 → 该技能中意指的章节或部分。 |
| `migration_note` | 仅出现在从遗留日志转换而来、且转换器拒绝猜测的文件上；复核后清除。 |

**字段名与状态值必须精确。**`skills:`、`proposed_skill:` 和
`sibling_checked:` 没有任何东西读取：携带其中之一的条目不属于任何
技能，与 `skill: []` 无法区分，按目标分桶的复核把它路由到无处可去。
`status: OPEN` 不在五个取值之列——一个碰巧做大小写折叠的读取者
掩盖了缺陷，并不等于为缺陷发放了许可。`id:` 是代码段打印的整数，
绝不是零填充的文件名前缀。一个解析每个表头却一个也不对照本表检查
的扫描，会按时碰到这样的条目并报告干净的计数（观察到：一条未经
模板写入的条目在 `skills:` 之下待了四天，带着 `status: OPEN` 且
没有 `type:`、`siblings_checked:` 或 `area:`，而旁边的扫描报告每个
表头都已解析）。失败产生的是更小的数字，从不报错，这正是只要
某处运行检查，近失名就会被标记而非跳过的原因。

**条目是不带字节顺序标记的 UTF-8。**每个表头读取者都测试第 1 行
是否为 `---`，前面的 BOM 会把表头藏起来：扫描以比 `files` 少一的
`parsed` 跳过该条目，归档清扫也永远不会移动它（`environments.md`，
"Windows 宿主：什么会到达 shell 与文件"）。

### 自由文本值中未加引号的 `: `——在有人察觉之前能漂移多远

核心技能陈述了规则（每个自由文本值都加引号）。这里是规则背后的
测量，因为这种失败异常安静，规模也出人意料。

自由文本值内部一个未加引号的 `: ` 是非法 YAML。frontmatter 仍然
能*提取*——在两条 `---` 之间切片的正则对此很满意——所以会话启动
扫描把文件报告为已解析，日志看起来健康。坏掉的是每一个真正
**解析**的消费者：读 `status` 的复核、数 `skill:` 的钩子、检查表头
的校验器。它们在文件上抛异常，而被抛异常的文件通常被跳过而不是
被报告。

在上次验证时对一份活日志实测：**292 个文件中 27 个不可读**，其中
25 个坏在 `resolution:`——这正是最可能含冒号的字段，因为一条
resolution 天然读作 "Actioned: principle #8 extended…"。这 27 个
每一个都是照当时模板写入的，而模板当时就是不加引号地承载该值。
模板教出了缺陷，每位作者都照办了。

扫描的 `suspect` 计数是早期预警：它在文件数旁边报告形状上看起来
非法的表头——未加引号的 `: `、闭引号之后的文本（两种引号风格都
算）、以反引号、`@` 或 `%` 开头的值、双引号 YAML 字符串未定义的
转义（`\x`、`\u`、`\U` 分别需要 2、4、8 个十六进制位）——对活跃
目录和 `archive/` 各报一份，使逐渐漂入这种状态的日志在会话启动时
自我宣告，而不是在被绊倒的那次复核处才暴露。这个 awk 程序在每个
文件的第一行重置自身状态，所以未终止的表头不会在
`find -exec … {} +` 之下泄漏进下一个文件；它允许冒号后任意数量的
空格、值前的 `&anchor` 或 `!tag`，并且从不把以 `{` 或 `#` 开头的
值当作散文——这正是模板自己的 `reference:` 注释行未被标记的原因。
它是地板而非解析：`[…]` 列表只检查未加引号条目中的冒号，`{…}`
映射完全不检查，普通值后跟 `# comment: x` 仍会计数。它还漏检未
终止引号、冒号后空格处换成制表符、以冒号结尾或以 `: ` 开头的值、
续行上的 `: `、`[a-z_]+` 之外的键，以及带类型标签（`!!int`）下的
空值。重新验证的办法是对每个文件的 frontmatter 跑一次真正的 YAML
解析，而不是重读模板。

排版引号是另一类常见破损，而且更安静。以 „ 或 " 开头的值是纯
标量：引号字符成为文本的一部分，其中的未加引号 `: ` 照样破坏
文件，而编辑器里什么都看不出。以 ASCII `"` 开头、以排版引号结尾
的值永远不闭合。在 ASCII 引号包裹的值内部，以 ASCII `"` 收尾的
„…" 在那个 `"` 处结束，该行其余部分就是闭引号后的文本，扫描会
标记它。用 ASCII 配对引用；值内部的引用用 »…« 或 `\"`。

### 含冒号的列表项不可移植

frontmatter 不指定唯一解析器，所以"合法"的意思是：在本日志的
消费者可能用到的每一个 YAML 解析器下都能加载。两条规则在同一行
上分歧，而模板曾经产出这种行。按 YAML 1.2 的读法，流式上下文中
纯标量里的 `:` 在下一个字符不是空格时属于标量的一部分，所以
`skill: [plugin:name]` 就是它看起来的那个单字符串列表；按旧规则
——libyaml 系解析器（Ruby 的 Psych、Go、`yq`）在某些版本中采用
——`:` 终结纯标量，该行抛出 `found unexpected ':' while scanning
a plain scalar`。两者都是不同规范下的正确实现，所以这个表头本身
既非合法也非非法——它不可移植。在一份 202 文件的日志上实测：
自带扫描报告 8 个可疑表头，PyYAML 一轮 0 个非法，Psych 一轮 127
个非法，而三者对同一语料都没说错。

失败从两侧都不可见：Python 消费者（`migrate-log.py`、
`validate-skill-bundle.py`、大多数钩子）永远看到干净的日志；另一
规则下的消费者看到它大半加载失败。所以规则取交集：**给含冒号的
列表项加引号**——`skill: ["superpowers:test-driven-development",
task-observer]`——或改用块式列表，那里冒号不加引号也合法。两种
形式在两条规则下解析结果相同；代价是每个限定条目两个字符。带
插件作用域的名字不是裸 kebab-case 名字，这正是"列表保持裸名"在
观察到带命名空间的技能之后不再正确的原因。`scripts/migrate-log.py`
已写入加引号形式，所以迁移过的日志是可移植的；照模板手写的条目
才是要检查的。

扫描的 `suspect` 计数用自己的规则看穿这一类：在以 `[` 开头的值
中，它丢弃每个带引号的字符串和任何尾部注释，若剩余部分仍含冒号
则标记。所以 `[plugin:name]` 计数而 `["plugin:name"]` 不计。该规则
有一个被接受的误报，`[a: b]`——两种读法下都是合法 YAML，单条目
映射——模板从不产出它。这个计数被标注为 `suspect (awk, a floor)`，
因为它是一台仪器做的形状检查、是一个下界："8 suspect" 从不意味着
"8 invalid"，而零对另一规则下的解析器什么也不说明。用两个解析器
而非一个重新验证：与已经信任的解析器一致的检查才是该怀疑的检查
（`skill-authoring.md`，"与你一致的验证命令才是不该信任的"）。

### 搁置条件以结果命名，绝不用你自己的载体

`parked_until:` 必须指名一个可能发生的条件——但还有第二个更锋利
的测试，第一个测试会径直放过它。

"PR #N is merged or closed" 等待的是对方不必走的路径。维护者把
改动以带共同作者尾注的自有提交并入、择取（cherry-pick）它、或
重写它；PR 保持打开或因被超越而关闭，而**条目等待的结果已经完全
到达**。条件永不触发。在同一仓库观察到两次，这提示它是向别人
维护的仓库做贡献时的常态，而不是例外。

所以测试不只是*这个条件到底能不能发生*，而是**结果能否在条件不
触发的情况下到达？**对任何依赖另一方过程的事情，答案都是能，所以
要把条件措辞在**目标产物的文本**上——"rule X is present in
`main`'s SKILL.md"——读一下目标就能回答，无论改动走的是哪条路。

同样的道理适用于一切替结果站台的载体：工单被解决、构建变绿、
消息被回复。搁置在你真正需要为真的东西上。

措辞为目标文本的条件用短语搜索来检查，而硬换行的 Markdown 会
破坏面向行的搜索：短语跨了换行，`grep` 报告无匹配。在做了空白
归一化的 Markdown 块内搜索（把段落各行接起、把连续空格折叠），
并在信任"不存在"之前，先用一个已知被换行的命中和一个已知跨块的
非命中各测一次搜索。

对用户并不维护的技能，目标产物是本地安装，不是上游树。上游报告
在被接受、合并或发布时并未解决——这些都不改变正在运行的那份
副本——也没有任何东西观察重新安装。所以条目以从已安装副本读出的
条件保持 `parked`（"the installed `task-observer` carries rule X"，
或指名带有该规则的版本），并在该副本带上修复时被解决。（观察到：
一份落后上游十九天的安装，其四份自发报告已在该窗口内修复并发布，
而读过发布说明的那些会话仍在运行旧文本——其中一个撞上了同一份
发布已修掉的缺陷。）

### 上下文保全——`reference:` 字段

**上下文保全：**如果观察条目依赖会话本地数据（上传件、API 输出），
先把这些上下文保存进工作区，再把 `reference:` 设为其路径——证据
随会话消亡的观察条目是不完整的。指针也必须活过交接：`reference:`
与一切把工作移交给后续会话的指针一样，必须指名一个持久路径——
一个活得比会话和重启更久、且能被本会话之外的其他会话解析的路径。
会话作用域的临时目录两项测试都不合格，而角色名（"the
scratchpad"、"my notes"）根本不是路径。这样的指针不可能在写入时
失败，只会在读取时失败，而那时它的作者已不在场修复——一个新会话
跟不上的指针不是保全。

### 观察条目内部的命令——必须在文件写入之前运行

引用可执行命令的观察条目以第一手观察的权威把它带向前方，而当时
被见证的是体验——命令通常是事后凭记忆重构的。下游没有任何东西
能区分二者。`skill-authoring.md` 中的编写前置检查在技能被编写时
运行，往往在另一台机器、另一天，身边没有命令所指的系统；而在
归档时刻，会话正站在那个系统面前，运行它只花几秒。所以在文件
写入之前，运行正文引用的每一个命令——逐字运行并看它的输出——
做不到时，在正文中把命令标记为未验证。把结果记入
`commands_verified:`，每个命令一个分句，正文未引用命令时写字面
`none`，理由与 `siblings_checked:` 永不留空相同：一条带着未运行
命令的正文，无论"检查过并信任"还是"从未考虑过"，字节上完全相同，
只有这个字段能让缺席可见。（观察到：变成一个技能的三条观察条目
总共带着三条错误命令——一个在所指发行版上不存在的标志、一个写给
包装器而非它所启进程的 `$!`、一个从必须由前序步骤填充的缓存里读
清单——只因那个技能恰好是在能运行它们的地方编写的才被抓住。）

## 低成本扫描

只读 frontmatter——头两条 `---` 行之间的表头块——绝不读正文。这
正是会话启动扫描和复核的工作队列遍历在观察条目数以百计时仍然
便宜的原因。扫描是 `scripts/session-start-scan.sh`，唯一的一份：
SKILL.md 的会话启动协议（步骤 2）运行它，读者在那里复核它。下面
的注释解释它的各个部分。

**为什么这行带时间与来源，而不只是日期。**工作区被刻意共享给
观察同一个全局安装技能的所有项目——这就是锚定规则——所以
`checkpoints.log` 按设计就是多项目、多会话的文件。只带
`YYYY-MM-DD` 的一行无法区分同一天运行的两次会话，而这恰恰是常见
情形，也恰恰是这份文件存在所要裁决的情形：痕迹的全部意义在于
证明*这个*会话运行了协议，而不是技能被加载了、协议被跳过了。
两条同日同文的行只能证明有会话运行过，证明不了是哪一个。时间
区分会话；方括号里的来源（工作目录的最后一段，或 harness 暴露的
任何同样便宜的项目内令牌）区分项目。

最后的追加是会话启动运行自身的痕迹（见"扫描以写入收尾，而不只是
打印"）；复核对同一批 frontmatter 的工作队列遍历可以省略它。内容
打印是 `( cd "$d" && … )` 内对 `*.md` 的一次 `awk`，绝不是
`for f in $(find …)`：未加引号的命令替换会把任何含空格的路径按词
切分，这对文件夹名带空格的每个工作区都是现实危险，而目录内部的
glob 交给 `awk` 的是不会被任何东西切分的裸文件名。它打印每个表头
后跟一条 `---` 行，即早先逐文件循环产出的输出，只是整套文件一个
进程而不是每文件一个；子 shell 内的 `LC_ALL=C` 让 glob 按循环中
`sort` 的方式排序。不要用 `$(ls … | xargs …)` 重建文件列表：那会
重新引入词切分。

**守护读取，而不只是写入。**一个返回空的查询同时在报告两种可能
——数据缺席，或者问题从未被提出——而其中只有一个是发现。给每一
个以防止重复工作为目的的检索配上独立的存在性检查，因为那种失败
是静默的、自我确认的，而且代价恰好是那次检索本要省下的工作：一个
没有产出任何输出的扫描曾被读作"没有相关观察条目"，而日志里躺着
几十条，同一发现随后被重新发现并当作新发现呈报。两个性质使检查
独立而非装饰：文件数来自字面路径而非解析循环所用的变量，断言比较
的是两种手段各自得出的两个数。空输出必须挣得证据的身份。

扫描形态的三个性质是承重的，每一个都来自一份报告。守卫的
`parsed` 计数由它自己的命令得出，绝不靠打印循环内递增的计数器：
一旦循环被管道接走（`done | grep …`），搭在输出流上的计数器立刻
落入子 shell，守卫就会在一屏正确打印的表头正下方报"0 headers
parsed"。文件用 `find` 枚举而非 glob：在 zsh 默认的 `nomatch` 下，
未匹配的 `"$d"/*.md` 会在第一次迭代之前中止整个 `for`，于是全新
安装的空日志在答案本应是"没有观察条目"的地方报了错，而本想兜住
字面 glob 的 `[ -e "$f" ] || continue` 一行在那里是死代码。守卫是
`if` 块而非尾部 `&&` 链：最后一步测试为假的链每次健康扫描都以
退出状态 1 离开块，于是一个上抛退出码的 harness 恰好在负责判断
日志可读性的那一步报告了失败。改造代码段时：把守卫放在它所守护
的流之外，枚举不用 glob，并以一句在一切正常时状态为 0 的语句
收尾。

**跨多次工具调用的代码段必须自行重推导路径。**在大多数 harness
里 shell 状态不跨工具调用保留，前一次调用里定义的变量到下一次就
是空的。用 glob 时，空的路径变量不报错——它展开成 `/*.md` 并匹配
不到任何东西，过滤器静默地变成"什么都不匹配"的过滤器；`find ""`
至少会报错，这正是这些代码段用 `find` 枚举的原因之一。这里的每个
代码段都在使用路径的同一回调用中定义它所用的路径；改造时请保留
这一性质。

**在 zsh 下，未加引号的 `$var` 不按词切分，以 `=` 开头的词会被
当作命令路径展开。**两者在 bash 下都正确运行，所以在那里预检过的
代码段会把它们带出去。装在变量里循环的列表（`for f in $names`）
把整个字符串当成一次循环体，这样构建的成员测试永远为假或永远为
真——而且不动任何计数，因为计数守卫数的是文件而缺陷在名字里。
复合命令里一个裸的 `echo ====` 会以 `=== not found` 中止它，其后
的一切全部丢失。永远不要把列表装进变量：写进工作区下的文件再用
`while IFS= read -r` 读回，或用 `comm` 比较两个这样的文件；任何
以 `=` 开头的词都加引号。

### 为什么会话启动扫描不能满足按技能检查

**这个扫描不能满足按技能检查**（每次加载技能时运行的 grep——
`references/environments.md`，激活块）。范围不同（全部技能对一个
技能），深度不同（frontmatter 对正文），时刻不同（会话启动对技能
规则被应用的那一刻）。两者都回答"我看没看过日志？"，所以运行了
这一个就卸下了心里的义务感，让针对性的那个显得多余，而它的功能
并未被执行——对一百个标题的觉察，撑不过二十次工具调用后对那一
条相关正文的回忆。检索必须发生在决策发生的地方。

### 对非空日志的空扫描是坏命令

**已知非空的日志上一个空扫描，在被证明不是之前就是坏命令**，
绝不是"没有相关观察条目"这个发现。扫描的守卫负责裁决它是两者中
的哪一个，而它独立性的两半都是承重的：文件数来自字面路径而非
解析循环所用的变量，断言比较的是两种手段各自得出的两个数——有
文件存在而零解析则停机。改造扫描时保留这份独立性，并让每条路径
在同一回工具调用内重新推导。推理过程与各条规则所来自的报告见
上文"守护读取，而不只是写入"与"跨多次工具调用的代码段必须自行
重推导路径"。

**部分解析是条目丢失，不是日志变小。**守卫只在零解析时停机。
没有表头的编号文件——零字节，或没有开头 `---` 的文本——改由扫描
的 `LOST ENTRIES` 行指名：它是写入在防截断创建与正文之间被打断
的痕迹（被拒的写入、上下文截断、会话终结），它持有一个任何人都
不得复用的编号。在启动行里逐条报告。若观察条目可以重建——本
会话写的，或 slug 与会话记录说得够多——现在就把正文写进那个
文件；否则给它一个最小表头（前缀里的 `id`、指名 slug 的 `title`、
`status: declined`、`resolved:` 今天、`resolution: "write
interrupted; body lost"`、`siblings_checked: "none — lost entry"`），
让归档清扫关掉它。永远不要删除它：编号保持已发行，地板也已经坐
在它之上。

### 每台仪器都获得同一个守卫

**每台仪器都获得同一个守卫：空结果或零结果，在独立探针证明总体
为空之前，只是关于仪器的主张。**`SCAN COMMAND BROKEN` 和
`ID COMMAND BROKEN` 是一条规则的两个实例，不是两条规则——
frontmatter 扫描、编号推导、状态 grep、钩子里的计数、脚本里的
查询，报告的都与上面扫描的两种可能相同，而其中只有第二种是被
"0"掩盖的缺陷。所以守卫是每台新仪器与生俱来的性质，绝不是第一次
静默失败之后补上的一行：给每条产出数字或列表的命令配一条用不同
手段从字面路径得出的第二个计数，分歧即停机。逐代码段枚举的守卫
按构造对下一个代码段不设防；作为仪器性质陈述的守卫才能覆盖还没
人写出来的那一台。

**一个只能区分"空"与"非空"的守卫抓不住部分读取，而部分读取是
文本形态工具输出的常见失败。**返回目录一部分的列表能通过每个零
检查，产出一个貌似合理却错误的最大值。把列表对同一总体的、以
不同手段取得的第二个计数做断言——编号代码段把它列出的前缀数与
`find` 数出的带前缀文件数相对——而不是对某个哨兵值。已经内嵌于
计算的单调不变量是更弱的检查：地板文件永不高于已*发行*的最高
编号，但编号可以在文件从未创建的情况下被发行（旧代码段在创建
之前写地板，而遗留单体归档持有任何文件名都不携带的编号），所以
低于地板的计算最大值被报告为 NOTE，编号取地板之上，而不是停机。
并且永远不要把可疑读数写回它所来自的持久源；放在那次写入之后的
守卫什么也没保护，而本为阻止计数器回卷而存在的地板反而成了回卷
它的东西。

**四种状态，一个空结果。**运行了且什么都没找到的仪器、运行了且
坏掉的仪器、从未获准运行的仪器和尚未完成的仪器（见下文）返回
同样的东西，而只有第一种是关于世界的事实。第三种没有天然的
破绽：什么都没坏，所以没有 `BROKEN` 守卫点火，拒绝信息又很容易
被概括成"什么都没找到"。凡是命令可能被 shell 之上的策略层拒绝
的地方——见"被拒绝的打印不是空日志"——守卫也覆盖拒绝，并以拒绝
自己的原话报告它。

**守卫按命令是什么划定范围，不按它长什么样。**上面两个指名实例
——`SCAN COMMAND BROKEN`、`ID COMMAND BROKEN`——都是随本技能
发行的读日志代码段，所以这条规则在实践中读起来像是只针对*那几
条*。并不是，而这个缺口恰恰是代价最大的地方：调查中途临时运行的
单行环境探针，其空结果会直接作为事实进操作手册或观察条目正文。

两种观察到的形态，都被记录成了并不存在的发现：

- 交互式 zsh 里的 `ls /usr/bin/*askpass* /usr/lib/ssh/*askpass* …`
  打印了 `no matches found`——一个 glob 错误，不是答案——然后
  "不存在 askpass 助手"被记了下来。
- 对会话无权读取的目录做存在性列举返回了空，缺席被当作系统状态
  报告。

两条命令都不是"日志仪器"，所以都没引来守卫。把守卫应用到**任何
空输出或零输出即将变成主张的命令**：配一条不同手段的第二探针，
或者把结果表述为"探针什么都没返回"而不是"那里什么都没有"。

**当仪器是外部进程时，独立探针要走过同一条代码路径。**对字面
路径，第二计数是对同一目录换个手段再读一次。对从非交互 shell
调用的 CLI，"不同手段"被字面满足于一个兄弟子命令——`--version`
能打印，所以二进制没问题——而这证明不了被测子命令能否向管道
报告：一个只通过交互式终端 UI 渲染的子命令被接管道时什么都不
打印并以 0 退出，无论结果有效、无效还是没有结果，都与真正的空
答案字节相同。所以探针是带已知坏参数的同一子命令。如果它也以
成功退出码返回空，这条路径就是 TTY 门控的（或在此调用方式下因
别的原因静默），仪器回答不了这个问题，正确的输出是把命令交给
交互式终端而不是报告"none found"。观察到：一个列表会话的子命令
接到 `head` 返回零字节且退出 0；`--version` 打印了，被读作"没有
会话"的确认；同一子命令带非法 id 同样返回零字节且退出 0。

**从另一个进程仍在写的文件里读出的数，在该进程已知退出之前只是
暂定值。**这是第四种状态，守卫自身的药方抓不住它：换个手段的第
二计数读的是同一个未完成的源、同样为空，于是两个独立探针以十足
的信心在一个假阴性上一致——总体没问题，解析没问题，只有时机
不对。未完成的文件看不出未完成：`grep`、`awk` 和 `sed` 对终端按
行刷新、对文件或管道按块刷新，所以一个仍在运行、*尚且*什么都没
找到的生产者，与一个跑完了且什么都没找到的生产者字节相同。
harness 为后台命令提供的中途读取便利不是完整性信号。所以对这一
类，守卫不是第二计数，而是存活与退出检查——生产者的退出状态，
或一次进程检查（对其模式的 `pgrep`）——在中途输出被解读之前运行，
绝不是在貌似合理的空结果之后当交叉检查。观察到：对大型工作树的
递归搜索移入后台任务、其输出文件可供中途读取，被两次读作零命中；
它的三个进程十二分钟后仍在运行，什么都没刷新。

**当仪器是本会话编写的代码时，它的输入覆盖按构造就未经验证——
打印它吃进了什么，而不只是它找到了什么。**发行的代码段至少在
它要读的总体上运行过；一次性解析器只在作者启发式碰巧匹配的东西
上运行过。观察到：一次对权威术语表的扫描在调用时从貌似合理的
标题下的要点重新推导，报告"3 terms checked, hits: none"——术语表
自己的机器可读块里有 24 个，而解析器读的是相邻章节的三个顺带
要点。一台只看到八分之一输入的仪器给出的通过不能证明任何事，
它被抓住只因计数小得难以置信。所以会话编写代码的守卫形式是
**任何结果之前的覆盖断言**：打印仪器读到的术语数、行数或文件数，
并对照权威源自身的计数（块的行数、目录的文件数、表的行数）断言
——不匹配就使步骤失败，而不是退化成启发式。计数是守卫；命中是
发现。同一道理适用于绿色结果与空结果："0 hits"只有在仪器已知能
看到语料之后才是关于语料的主张（`skill-authoring.md` 的永恒性
扫描记录运行过哪些模式，正是为了这个原因）。

**有内容的结果同样要守卫，且比零结果更少被质疑，因为它看起来像
证据。**五种形态能通过上面所有空结果检查：对整个总体完全相同的
裁定（每个预期文件都报 `MISSING`，因为一个路径转换步骤在每次
迭代中都失败成空字符串，把后面的 `[ -f ]` 测试变成了常量）；一小
撮貌似合理、其实全是仪器自身误报的发现；对同一总体的两台仪器
分歧，被第三个"还有剩吗？"检查掩盖，而那个检查谁也不验证；一个
看起来完整的响应、其终止元数据却说明被截断；以及从错误命令读来
的退出状态。所以：对总体齐一的裁定是关于仪器的主张，像空结果
一样探它，取一个答案已由其他手段得知的元素。凡检查会变换输入
（解析、路径转换、解码）的，先打印变换后的值再下判断。凡两台
仪器测量一个总体的，断言 `before - fixed = after` 而不是只查最终
状态。呈报一份发现列表之前，把其中一条放回原始上下文打开。把
终止元数据（`finish_reason`、`done_reason`、`truncated`、退出码）
与它所修饰的内容并排读取，因为看起来完整恰恰是截断输出的看家
本领。在命令之后紧接着的语句里捕获退出状态（`cmd; rc=$?`），绝不
在同样运行命令替换的字符串里捕获：在 `echo "$(basename "$d")
exit=$?"` 里 bash 报告的是替换的状态而非命令的，其他 shell 又各
不相同。而对一条新的告警或错误分支，数一数今天真会到达它的输入：
零意味着输入缺失或分支多余，而绿色的单元测试分不清这两者。

**关于外部系统行为方式的主张也是仪器读数，同样要守卫——无论它
产自哪里。**无论它来自被委派代理的报告、本会话写的工具，还是
代理自己的推理，在那个推断之外有什么东西返回它之前，它就是未
验证的。把机制陈述为假说，指名能一锤定音的观察，而当检查花几分
钟、错误却要付出不可逆动作的代价时，在被质疑之前先跑检查，而不
是被质疑之后。观察到：签署提交能否消除托管平台的"unverified"
徽章，决定着是否向公共仓库强制推送；这个答案被两次自信地断言、
没有任何证据，而在用户以一个竞争机制反问之后，两次 API 调用
九十秒内就定了案——竞争机制才是正确原因。把这种情形与普通不
确定区分开的破绽是**重复**：第一次自信的回答是猜测；在隐性怀疑
下不加查证地重复它，就是守卫应当点火的时刻，因为重复感觉像
一致，实为固化。碰巧正确不等于可靠，而用户从外面分不清这两者。

### 被拒绝的打印不是空日志

会话启动扫描在一个脚本里干两件不同的活，而它们的胃口不同。直到
`checkpoints.log` 写入在内的一切只索要关于文件的*事实*：存在多少、
多少有可解析的表头、多少——目录里和 `archive/` 里——看起来是
非法 YAML。尾部的循环索要**内容**——它从文件里读出指令形态的文本
并放进代理的上下文，而这正是积压工作觉察的来源。

后一半受管辖上下文的东西管辖，不只受管辖文件系统的东西管辖。在
带自动内容分类器的权限模式下它可能被直接拒绝——现场报告为
`Instruction Poisoning`，而那条命令几分钟前对空目录运行时毫无
异议。这个性质是该步骤固有的，换措辞不会消失，而且随着日志增长
它变得**更**可能，不是更不可能。

这就是计数和痕迹先运行的原因。三个后果：

- **拒绝不是空日志，绝不报告为空日志。**情形诱发的即兴发挥——
  "扫描没找到东西"——恰恰是日志要防止的那个失败。说打印被拒绝
  了，指名分类器给出的理由，并给出计数。
- **仅计数形式是成文的降级方案**，不是退化的即兴发挥。它仍然满足
  `SCAN COMMAND BROKEN` 守卫，因为 `n` 与 `parsed` 都来自运行了的
  那一半。把脚本顺序反过来，会让守卫自己的输入排到可能被拒绝的
  那一半下游——守卫恰在需要它的时候哑掉。
- **觉察确实减少了，这值得对用户说一行。**会话在上下文中没有
  积压工作的条件下继续；它不等价于一次运行了的扫描。

一般形式归入下面的仪器守卫：*仪器未获准运行*是*运行了且没找到*
与*运行了且坏掉*之外的第三种状态。三者都产出空结果，而只有中间
那个是关于世界的事实。

### 被拒绝的代码段是降级路径，绝不是被跳过的步骤

上面的拒绝只针对打印；审查命令*形态*的 harness 可能拒绝整块。
一个分类而非执行命令的策略层会把多行复合命令——内嵌 `awk` 的
`for`、包着花括号组和管道的命令替换——当作不可验证而拒绝：它
无法对上白名单，于是永远不运行。随后是两种失败形态，而两者事后
都不可见：代理把代码段改写成更隐晦的复合命令，再被拒绝，然后
放弃；或者断定协议在本环境不可用，带着用户的任务继续走，什么
都没激活。被跳过的协议留下的产物，与一无所获的协议留下的产物
一模一样。

**代码段只是步骤的一种实现；步骤本身才是要求。**当 harness 以
不可验证为由拒绝一条命令时，不要把它改写成更聪明的复合命令——
拒绝针对的是形态，更聪明的复合命令还是那个形态。下面这个阶梯只
回应命令*形态*被拒的情形，因为扁平形式恰是策略层能检查的东西。
指名内容或目标的拒绝——上面的打印拒绝、被拒路径——是拒绝：
以它自己的原话报告，不要换个方式去取同一内容。降级到基于绝对
路径的扁平单一用途命令，每次调用一条，由你自己合并：列目录和
归档、用一条 `grep` 抽取 frontmatter 字段、读 `.id-floor`、需要
最大值时手工取。守卫仍然适用——非空的列表加上零个抽取出的编号
是坏读取，不是空日志——`checkpoints.log` 行仍然要写。在会话中
说明运行的是哪种形式，让后续读者能把降级运行与跳过运行区分开。
对写入，扁平形式已经存在：`scripts/new-observation.sh`，以绝对
路径调用，是一条没有 shell 操作符的命令，凡能运行它的地方它是
唯一写入路径。扫描也有同样的扁平形式，`scripts/session-start-scan.sh`
以绝对路径调用，所以它是阶梯的第一级；扁平读取跟在它后面，供它
也被拒绝或无法运行之时。凡随命令发行的强制步骤都拥有一句话，
说明命令不可用时什么仍然强制；对扫描而言这就是那句话。

阶梯，每次调用一条命令，每条都没有形态分类器可能拒绝的 shell
操作符：

```bash
bash "<skill directory>/scripts/session-start-scan.sh" "C:/Users/Administrator/.zcode"
find "C:/Users/Administrator/.zcode/skill-observations/observation-log" -maxdepth 1 -name '*.md' -exec grep -H -E '^(id|title|status|skill|proposes_skill|siblings_checked):' {} +
ls "C:/Users/Administrator/.zcode/skill-observations/observation-log"
ls "C:/Users/Administrator/.zcode/skill-observations/observation-log/archive"
cat "C:/Users/Administrator/.zcode/skill-observations/observation-log/archive/.id-floor"
```

从扁平读取出发人工合并：`files` 是第一份列表中 `.md` 名字的数量，
`parsed` 是 `grep` 打印过 `id:` 行的不同文件数，编号最大值是两份
列表加地板里最大的前缀。然后写 `checkpoints.log` 行，并在会话中
说"降级形式"。如果 `-exec … +` 本身作为复合命令被拒，回退方案是
bash 之下的
`grep -H -E '…' "C:/Users/Administrator/.zcode/skill-observations/observation-log"/*.md`
——这棵树容忍的唯一 glob，且仅在此处，因为它替换的命令被拒绝
过。空日志上那个 `grep` 在空 `ls` 旁边报"No such file"，从未发行
过编号的日志上 `cat` 报同样的：每一对都是预期答案，不是坏读取。
这个阶梯里的 `ls` 是供人工合并计数的读取，不是代码段的输入，所以
被重绑定的 `ls` 会自己显现在列表里。

## 技能家族与同族检查

当多个技能实现同一个想法——同一方法论配不同工具、同一结构配不同
主题、同一伴生模式配不同基础技能——共享部分默认会漂移，因为每个
成员只在用它的那些会话里得到维护，没人看这个集合。真实技能库中
实测：一条纯认识论规则，适用于某五技能家族的每个成员，只在一个
里有；一条自己的文本写着"适用于任何写文件的脚本，不限于这一个"
的规则，四个成员里只有一个有，而其余三个里有两个以同样方式坏掉。
没有人删除过任何东西；只是有些成员长了起来，有些没有。

**为什么检查必须是写入时步骤而不是习惯。**在使用某个成员时获得
的洞见通常适用于其余成员，而常规工作流里没有任何东西过问——于是
`skill:` 塌缩成眼前那一个技能，家族安静地分化。这种分化没有任何
症状，直到有人把两个成员并排读，而那发生在几个月后的漂移审计上。

**最便宜的传播信号是一个短语。**在*单个产物内部*自我声明为通用的
规则——"这适用于任何写文件的脚本，不只是 X"、"对这个家族的每个
伴生技能都成立"——已经告诉你它属于每个同族技能。把那种措辞当作
自动的多技能标志；注意到它零成本，而它抓住的正是去名测试只能
代理的那类情形。

`skill:` 字段本来就是列表，所以多技能观察条目是可表达的。机制
存在；*检查*不存在——而没有规则去填充的列表字段会塌缩成单值。
四个部分，按成本递增：

**1. 声明家族与模式组——**`skill-observations/skill-families.md`。
登记表持有两种分组，混淆它们正是让它要么阻塞发布、要么发行没人
能用的引用的原因：

| 种类 | 定义依据 | 成员可互相引用？ | 共享规则放哪里 |
|---|---|---|---|
| **家族** | 同一工具，或一个核心技能及其伴生技能 | 可以——一个成员的用户有理由加载其他成员 | 在成员内（按一致性模型） |
| **模式组** | 同一形态——每个工具一个伴生技能、每个主题一份卷宗——一个成员的用户没有理由持有另一个 | **绝不**——指名其他成员的同族段落就是缺陷，无论是否发布 | 在横切原则里 |

按"一个成员的用户还会需要什么"分组，而不是按它们长得像什么。
洞见的传播与互相引用是两种不同的关系：模式组在写入时赢得同族
检查（"这句话去掉工具名还能活吗？"的测试恰是这种组的用武之地），
却完全赢不到互相引用。家族两者都赢。

**一个技能可以同时属于多个分组**——典型地同时属于一个按工具的
家族和一个核心/伴生家族——登记表分别记录每个成员身份，而不强迫
唯一归宿。同族检查（第 2 部分）对目标所属的**每个**家族和每个
模式组运行，而不只是它解析到的第一个。

每个条目携带成员名单和承重的第二列：**什么是共享的、什么又是
正当的成员专属。**没有这一列，每条观察条目看起来都哪里都适用，
检查产出噪音而非信号。还要为每个家族记录*一致性模型*，因为它
决定"修复漂移"意味着什么（模式组没有一致性模型——没有共享文本
需要保持同步）：

| 一致性模型 | 含义 | 修复漂移意味着 |
|---|---|---|
| `synced-duplicates` | 每个成员自足（例如独立发布），共享章节保持同步 | 编辑每个成员 |
| `shared-core` | 一个技能持有公共材料；其余作为伴生技能加载它 | 编辑核心一次，检查各指针 |

```markdown
## [group name]
**Kind:** family | pattern group
**Members:** skill-a, skill-b, skill-c
**Coherence model:** synced-duplicates | shared-core   # families only
**Shared:** [the material every member should carry]
**Member-specific:** [what legitimately differs, and why]
```

重复有时是正确的，缺席也并不总是漂移——这正是共享/成员专属拆分
所记录的东西。

**2. 归档时检查**（SKILL.md，"How to Log"）。写观察条目之前，把
目标对登记表解析——对它出现的每个家族和每个模式组，因为成员
身份是复数的。对其中的每个同族技能，要么把它加进 `skill:`，要么
在正文中说明它为何不适用。洞见横跨一个模式组时，去处通常是一条
横切原则，而不是同一段落抄进每个成员。**还没有登记表，或目标
不在其中？**检查仍然必需：在已安装技能名里扫共享前缀、后缀或
主题（`*-extras` 伴生技能、同一方法的按工具实现、按主题的卷宗），
对扫出的任何集合做评估，并提议登记表条目。两个便宜的测试决定
判定：

- 这句话去掉工具名、客户名或主题名还能活吗？能，它就属于每个
  同族技能。
- 规则自己声明了普适性吗（"这适用于更广"、"不限于 X"）？那种
  措辞是最便宜的传播信号，需要一个注意到它的机制——把它当作
  自动的多技能标志，而不是风格上的顺带一提。

**缺席主张继承产生它的那次搜索的范围。**会话能看到的已安装名是
用户作用域加上它运行所在的项目。作用于另一个项目的技能，以及
项目副本由之渲染出来的生成器源（一个工具自有的目录渲染进
`.claude/skills/`），从这里都不可见，所以"没有已安装技能覆盖这个"
在那些范围被搜索之前只是观察者的盲区——而这种失败只朝一个方向
跑：窄的范围永远不会发明一个技能，只会漏掉真实的，而那才是昂贵
的结局（观察到：四条观察条目被归档为某工作流的新技能提案，而
存在于另外两个仓库里的一个既有技能早已覆盖它，其中两个仓库已经
应用）。在写 `proposes_skill:`、`siblings_checked:` 里的 `none`、
或把目标报告为缺失之前，按问题而不只按名字搜索其他范围——提案
以让它浮出水面的任务命名，而已解决它的技能很少同名——并在
`siblings_checked:` 里记录搜索过哪些范围。"没找到"只有连同"你在
哪里找过"才是发现，与"会话启动"步骤 6 对目标所说的完全一样。用
glob 而不是递归 `find` 枚举各范围——对一个满是工作树和依赖树的
项目根，递归 find 要跑好几分钟——并给枚举加守卫：空结果先告诉你
仪器的事，再告诉你技能库的事。

```bash
root="[PROJECTS ROOT]"   # absolute path of the directory holding the user's repositories
[ -d "$root" ] || { echo "SWEEP BROKEN — projects root $root does not exist"; exit 1; }
list=$(for d in "$root"/*/.claude/skills/*/ "$root"/*/*/.claude/skills/*/; do [ -f "$d/SKILL.md" ] && echo "${d%/}"; done)
n=$(printf '%s\n' "$list" | grep -c .); p=$(for d in "$root"/*/ "$root"/*/*/; do [ -d "$d" ] && echo; done | wc -l | tr -d ' ')
echo "project skills: $n (in $p directories under $root, two levels deep)"
printf '%s\n' "$list" | grep "/<skill-name>$"                                            # by name: the bare name, any plugin: prefix dropped
printf '%s\n' "$list" | while IFS= read -r d; do if [ -n "$d" ]; then grep -Il -i -- "<term from the body>" "$d/SKILL.md" || :; fi; done   # by problem; a non-match is not an error
```

在根下两层做 glob，每个项目技能一次 `grep`——以找到的技能数为界，
从不受其下方的树所界。`project skills: 0` 出现在一个持有目录的根
上，只有当那些目录就是你指的仓库时才是关于本机的答案；
`0 directories` 是根错了。把用户运行技能的其他任何工具的等价目录
加进来（它的项目级技能目录，替代 `.claude/skills`）；激活块把根
钉定为 `[PROJECTS ROOT]`，安装时像 `C:/Users/Administrator/.zcode` 一样替换。在
`proposes_skill:` 写入之前运行这次清扫，并把它的根与计数写进
`siblings_checked:`。

**3. 记录判定**于 `siblings_checked:`。这个字段存在，是因为单条目
`skill:` 列表的两种状态——同族技能评估过并被正确排除，与同族技能
从未被考虑——字节相同，下游没有任何东西能区分它们：复核无法给
范围不足的条目插旗，漂移审计无法把决定与疏忽分开。记录判断并不
能让判断更好；它让判断的*缺席*可见，而这是唯一能让任何东西去
执行它的性质。仅凭指令显然是不够的——同一会话里四条观察条目被
范围不足地归档，而它们的作者早先在同一会话里写过传播规则。因为
字段在 frontmatter 里，上面的廉价扫描能报告"N 条观察条目未经同族
检查归档"，一个正文都不用读。在一个已经依赖"写入即执行"的技能
里，一条不写任何东西的新规则是格格不入的那个，应当据此被怀疑。

**记录判定不等于记录其依据。**字段让*仪式*的缺席可见；对*依据*
的缺席它什么也不做，而仪式一旦成为习惯，失败就从漏掉的字段挪进
自信填好的字段。观察到：一个同族技能带着具体裁定被排除——"按
稳定 id 选择条目，所以不适用"——而它自己的文档恰好在讨论中的
缺陷上带一段醒目警告；裁定读起来像查过的，其实是假设，直到后续
会话因无关原因打开那个同族技能才发现。不对称性决定依据放哪：错
纳入的同族技能在下次复核时付出一段冗余段落，有人读它然后删掉；
错排除的同族技能则安静地、永远地离开家族，因为下游没有任何东西
会按否定裁定行动。所以每项排除都指名其立足点——在该同族技能里
读过的文件与章节——或写 `assumed`，而复核在接受一项排除前先打开
`assumed` 的那个同族技能。示例：
`siblings_checked: "list-commands: render, pick, close — render added; pick excluded (pick.md §2, selects by stable id); close excluded (assumed)"`。

**4. 复核时的传播与漂移审计**——见 `weekly-review.md`（Step 3 与
Step 4）。前三个部分只覆盖从今往后的事；机械化审计是唯一能抓住
早于本规则的漂移、或由日志之外编写的技能引入的漂移的东西。登记表
会过时；grep 不会。

## 分配编号

编号是三个值中的最大者加一：`observation-log/` 中最大的数字文件名
前缀、`observation-log/archive/` 中最大的，以及
`observation-log/archive/.id-floor` 里的数。地板文件持有迄今发行
过的最高编号，所以当活跃目录被清空（全部归档）、再没有别的东西
记得区间时，计数器不会从 1 重启。凡发行高于它的编号就更新它。
归档清扫（见下文"归档"）折叠进这同一条命令：每次编号推导先把
陈旧的已解决文件移入 `archive/`，于是归档作为任何写入都跳不过的
一步的副作用发生。

核心技能的"How to Log"一节持有这段代码段的权威副本；下面的副本
是为了在上下文中阅读而复制的，两者一旦不一致，以核心为准：

```bash
d="C:/Users/Administrator/.zcode/skill-observations/observation-log"   # the pinned workspace path, never relative to the cwd; it may contain a space, so keep it quoted; bash, not sh
today=$(date +%F)          # archival rides inside this command (see below):
n_files=$(find "$d" -maxdepth 1 -name '[0-9]*.md' ! -empty | wc -l | tr -d ' ')   # a zero-byte file gives awk no line to count
seen=$(cd "$d" && awk 'FNR==1 {n++; nextfile} END {print n+0}' [0-9]*.md 2>/dev/null)   # files the sweep's glob reaches, counted apart from the sweep
[ "$n_files" -gt 0 ] && [ "${seen:-0}" -eq 0 ] && { echo "ARCHIVAL SWEEP BROKEN — $n_files files present, 0 examined"; exit 1; }
( cd "$d" && LC_ALL=C awk -v today="$today" 'FNR==1 {st=""; r=""; sub(/^\357\273\277/, ""); fm=/^---[[:space:]]*$/; if (!fm) nextfile; next}
    fm && /^---[[:space:]]*$/ {if (st ~ /^(actioned|declined|superseded)$/ && r ~ /^[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]$/ && r < today) print FILENAME; nextfile}
    fm && /^status:/ {st=$2}
    fm && /^resolved:/ {r=$2}' [0-9]*.md 2>/dev/null | while IFS= read -r x; do mv -n "$x" archive/ 2>/dev/null; if [ -e "$x" ]; then echo "NOTE: $x not archived — archive/$x exists or the move failed"; fi; done )   # one awk for the set, one mv per stale resolved file, never over an archived one; bash
floor=$(sed '1!d; s/[^0-9]//g' "$d/archive/.id-floor" 2>/dev/null); floor=$((10#${floor:-0}))   # digits only: a CRLF or padded floor still reads
ids=$(for p in "$d"/[0-9]*.md "$d"/archive/[0-9]*.md; do [ -e "$p" ] && printf '%s\n' "${p##*/}"; done | grep -oE '^[0-9]+')   # globs and builtins: no `ls` a profile alias can rebind
[ "$(printf '%s' "$ids" | grep -c .)" -eq "$(find "$d" "$d/archive" -maxdepth 1 -name '[0-9]*.md' | wc -l)" ] || { echo "ID COMMAND BROKEN — the listing and find disagree on the prefixed files"; exit 1; }
hi=$(printf '%s\n' "$ids" | sort -n | tail -1); hi=$((10#${hi:-0}))   # from the files alone; 10#: a zero-padded prefix is not octal
[ "$hi" -lt "$floor" ] && echo "NOTE: highest file id $hi is below .id-floor $floor — ids issued without a file; the new id goes above the floor"
next_id=$(( (hi > floor ? hi : floor) + 1 ))      # never below the floor, whatever the listing saw
f="$d/$(printf '%04d' "$next_id")-<slug>.md"      # the target path, built from the id just derived
[ -n "$(find "$d" -maxdepth 2 -name "$(printf '%04d' "$next_id")-*.md")" ] && { echo "COLLISION — id $next_id already used; re-derive"; exit 1; }   # guard the id PREFIX across active + archive, not the path
(set -C; : > "$f") || exit 1                        # noclobber: create, never truncate an existing file
printf '%s\n' "$next_id" > "$d/archive/.id-floor"   # AFTER the create: an id check that writes no file never moves the floor
```

代码段把推导出的数留在 `$next_id`、目标路径留在 `$f`；如果你还想
让文件名前缀回显出来，追加 `printf '%04d\n' "$next_id"`。

**`bash scripts/new-observation.sh <slug> [workspace-root]` 就是这段
代码段化作的一条命令。**它以相同顺序执行相同步骤——清扫、编号、
前缀守卫、防截断创建（noclobber）、写地板——外加内联代码段没有的
一步：在前缀守卫之前，它以在 `archive/.id-claims/` 里防截断创建
一个空标记来认领该编号，认领被占就上移一位，所以同一时刻的两次
运行永不共用编号。标记从不删除（不需要删除权限）；一次被中断的
运行留下的标记只留下一个空洞。它把钉定工作区根作为第二参数或从
`TASK_OBSERVER_WORKSPACE` 取得，拒绝相对根、畸形 slug 或缺失的
`observation-log/archive/`（停机并重探；绝不从写入者重建），并把
创建的路径打印到 stdout。凡能运行它的地方，它是唯一写入路径：一
个只作为脚本输出存在过的编号，无法在内存里从早先的读携带到稍后
的写，而这正是本节每条规则试图阻止的漂移。内联代码段保留给无法
调用脚本的 harness。

算术里的 `10#` 前缀是承重的，不是装饰：shell 算术把带前导零的数
读作八进制，所以 `$(( 0105 + 1 ))` 得 70——一个静默错误的编号——
而含 8 或 9 的前缀（例如 `0108`）是非法八进制常量，会让整条推导
报错。`sort -n` 不需要剥零；算术需要。地板只按数字读，所以带
CRLF、填充或空格写入的地板文件仍读出它的数，而不是什么都没有。

`awk`、`sed -n`、`grep -oE`、`sort -n`、`mv` 和 `printf` 都是
POSIX，唯一一个非 POSIX 构造是刻意的：算术里的 `10#` 是 bash
扩展，是不让零填充前缀落入八进制的最短形式——所以用 `bash` 而非
`sh` 运行代码段（`dash` 之下推导在任何文件存在之前就以算术错误
停止）。它在 macOS、Linux 和 Git Bash 上原样运行。清扫的日期比较
是 ISO 日期的 `awk` 字符串比较，按字典序排，所以不需要 `date`
算术。把 shell 命令交给代理的技能拥有那条命令的可移植性：以可
移植形式打头，绝不把它当脚注、等主打失败之后代理才摸到——并且
让一切从文件推导数字的命令在空结果上响亮失败，因为一个向空失败
而非向错误失败的命令可能永远不宣布自己失败过。要在代理 harness
里运行的代码段按配置文件无法重绑定的名字调用核心工具——harness
常从用户配置文件初始化 shell，而名为 `ls` 的别名或函数（`eza`、
`lsd`、带默认标志的包装器）改变了那个词运行的内容，代码段却
毫无异常报告。优先 shell glob 与内建；工具免不了时，用 `find`，
或 `command <name>`。守卫还要测试自己的输入：列表在地板并入之前
先对文件计数断言，因为缓存的计数器绝不能满足一个以证明日志被
读过为目的的检查。每文件起一个进程的代码段对它能读的日志携带
一个未声明的上限：逐文件起进程带大常数线性退化——Linux 上一百
个文件数秒，Windows 上一旦超过两分钟工具超时——所以它从不警告，
它停止完成，而后台运行的扫描与一个缓慢的扫描无法区分，直到
下游什么东西吃掉半个答案。会话启动扫描的计数是批处理的
（`-exec … {} +`），内容打印和归档清扫各是目录 glob 上的一次
`awk`；剩下的唯一逐文件进程是对到龄文件的 `mv`，以到期文件为界
而不以日志为界。把不返回的扫描当坏仪器对待，绝不当作值得等待的
慢扫描——对一条从未完成的命令，BROKEN 守卫无法点火。

### 编号代码段的 shell 可移植性——case 模式为什么要加括号

单趟清扫里已经没有 `case` 语句了，但它取代的那个循环在命令替换
`seen=$( … )` 里放过两个，它们教的规则对任何同样做的代码段成立：
`$( )` 里的 `case` 模式写作 `(pattern)`，不是 `pattern)`。前导括号
不是风格。

Bash 3.2——一台原厂 macOS 安装上的 `/bin/bash` 至今仍是它——在
第一个不平衡的 `)` 处结束命令替换，而不加括号的 case 模式恰好
提供了它。整块然后在**解析**时以 `syntax error near unexpected
token ';;'` 失败并退出 2。它内部的什么都不运行：没有归档清扫、
没有编号、没有文件，而且——最难诊断的部分——`ARCHIVAL SWEEP
BROKEN` 和 `ID COMMAND BROKEN` 都无法点火，因为那些守卫在从未
启动的块内部。守卫报告不了发生在它存在之前的失败。

加括号的模式在每个 POSIX shell、每个 bash 版本里都合法，所以可
移植形式零成本。在每一个把 `case` 放进 `$( )` 的代码段里保持它。

**如果你在移植代码段或写新的：**在 macOS 的 `/bin/bash` 下运行
一次，而不只是在你的会话碰巧用的 shell 下。`bash -n <file>` 就
够——它只解析不执行，所以对一条否则会写日志的代码段也安全。

### 守卫行、清扫的计数与防截断创建（noclobber）

列表守卫区分"日志说零"与"我读不了日志"：一个向空失败而非向错误
失败的命令，否则会在充实的日志里提议编号 1。它把 glob 列出的
编号数与 `find` 在同样两个目录里数出的带前缀文件数相比较，所以
部分列表和空列表都触发，而且它只对列表运行、在地板进入之前——
较早的形式先把地板并进最大值，一个坏到什么都没有的列表就返回
地板并通过。最高文件编号与地板分开保存是同一个理由：新编号是
两者较大者加一，低于地板的文件最大值是 NOTE（发行过编号却没有
文件），不是停机，因为较老的代码段在每次止于地板写入的运行里
都会留下恰好那种状态。地板最后写、在创建之后，所以一次不创建
文件的运行——检查、冲突、创建失败——从不移动它。清扫以自己的
名义携带同一个守卫——一条独立的 `awk` 数清扫 glob 够得着的文件，
该数为零而 `find` 报有文件时整块停机。计数来自它自己的命令，因为
清扫是没有循环计数器可读的单趟 `awk`，而搭在清扫输出上的计数会
分享它的失败。一个从不进入循环体的归档循环什么也不移动并成功
退出，所以没有计数的话"没有到龄待归档"与"循环从未运行"是同一个
输出。防截断创建补上逐文件隔离没覆盖的那一种（下文"为什么这就是
并发问题的全部"）：两个会话选了同一编号*且*同一 slug，解析到同一
条相同路径，第二个写入者会静默替换第一个。所以代码段在
`noclobber` 之下创建文件——正文只在创建成功之后写。

**冲突守卫以编号前缀为键，不以路径为键。**较早的形式测试
`[ -e "$f" ]`——完整路径，含 slug——抓不住实际发生的那种冲突：
两个写入者以*不同* slug 推导出同一个数，产出两条不同路径，两次
创建都成功，两个文件共用一个编号，哪里都没有错误。守卫必须以它
保护的不变量为键；noclobber 保护路径，不变量是唯一的数，而以
路径为键的守卫放过每一个换用不同 slug 的对编号的违反——而那是
全部的违反。所以守卫现在问的是 `observation-log/` 或 `archive/`
里是否存在带该推导前缀的任何文件（`find … -name 'NNNN-*.md'`，
绝不是裸 glob），存在即停机。它在推导陈旧时点火——编号来自本次
写入之前立即运行代码段之外的什么地方。它看不见同一时刻正在运行
的写入者，那个文件还不存在：两者从同一列表推导出同一个正确的数。
脚本用它的编号认领关上这扇窗；内联代码段没有，复核的重复编号
检查接住漏网的。重跑代码段；绝不手工调整数字。

### 每次写入前立即运行代码段

**在每次写入之前立即运行代码段，包括一个会话的第一次也是唯一
一次。**早先出于别的原因读过日志目录——会话启动 frontmatter
扫描、对指名在用技能的观察条目做 grep、一次状态检查——替代不了
它，而这正是跳过显得最合理的那个状态。那些是*相关性*查询；编号
是*最大值*，对前者的回答永远不是关于后者的证据：相关性 grep
返回它最高的**匹配**条目，不是最高条目，而它和 `observation-log/`
的任何普通列表都不读 `archive/` 和 `.id-floor`——那是三个输入中
的两个，是这条命令存在的理由。（观察到：一次最高命中为编号 N 的
相关性 grep 被读作"下一个编号是 N+1"，落在一个已占用的编号上，
而真正的最大值坐在归档里，高出二十。）碰撞真的发生也无害——文件
不同，什么都没丢——但应在发现时修复而不是留给复核注意：用代码段
推导正确编号，把较新的文件 `mv` 到那个前缀，并把它的 `id:`
frontmatter 字段改成一致。两者都是普通的单文件操作；不碰任何
其他条目。

**会话启动扫描打印的编号绝不是写入的输入。**扫描为觉察打印编号
——存在哪些观察条目、它们指向什么——而对一个在写入时刻必须是
最大值的数，觉察是错误的来源。这个失败的签名事后一目了然：一个
新文件编号为"会话启动时可见的最高编号加一"，却是一小时后写的，
而目录和地板当时都已高出十。这在规则已加载且写入会话中规则正确
的情况下已发生两次，这是二次违反条件：补救不是更硬的一句话，
而是一条不可拆分的写入路径——`scripts/new-observation.sh`（上文），
凡脚本可运行处——让"在写入时解析"成为唯一可用写入路径所做的事，
而不是一条关于何时运行代码段的规则。前缀守卫是它办不到的
harness 上的兜底。

### 每个编号在它自己的写入时刻解析

**每次写入，不只是成批的。**这条规则的较早版本开头是"当一个会话
里归档多条观察条目、且可能与一次定期复核或另一个写入者重叠时"
——两个范围条件，而一个看起来什么都不重叠的会话里的单次写入
一个也不满足。被报告的失败恰是那个形状：一条观察条目，同一
shell 调用里运行的代码段打印 `next_id=92`，随后跟着的 heredoc 在
文件名和 `id:` 字段里都带着 `91`。中间一个并行会话写入了 `0091`。
范围条件已删除：在**每一**次写入之前运行代码段，包括一个会话的
第一次也是唯一一次。

**写代码段打印的那个值。**这是规则从未说出的那一步，而失败恰恰
发生在这里——不在推导编号，编号是对的，而在推导它与敲下它之间
的缝隙。代码段打印的数进文件名**和** `id:` 字段，抄写，不是凭对
你以为它会是什么的记忆重敲。两者不一致时，文件是每次后续扫描都
相信的那个。

**绝不预先计算一个区间。**成批追加是 N 场独立的竞赛，不是一场；
预制的连续编号把 N 次独立的最大值检查塌缩成一次陈旧的读取。在
每条条目自己的写入时刻对活目录解析其编号，并在重叠可信时做写后
逐号计数。

**观察条目写入不是独立调用——不要并行化。**harness 常指示代理
在一个块里发出独立的工具调用以降延迟。观察条目写入看起来独立
（不同文件，无共享变量），其实不然：每条的编号依赖前一条留下的
状态，同一块里派发的两次写入读到同一个最大值、铸出同一个数。
这是碰撞的第三个来源，与并行会话、本会话的子代理并列——后者
继承同样的激活指令和同样的日志——而它是唯一完全生活在一个代理
自己回合里的那个，这使它成为再多"别的写入者"方面的谨慎也防不住
的那一个。多条观察条目到期时，一条一条写，每条等上一条写完再写。

### 编号地板陈旧——地板低于最高活跃前缀

只有每个发行者都更新它，`.id-floor` 才是安全网。三值取最大的推导
吸收一个滞后的地板而不产生碰撞，所以滞后在日常使用中不可见——
直到活跃目录被归档清空，那时一个滞后的地板恰是计数器在已发行
编号上重启的前置条件。滞后可检测：**地板 < 最高活跃前缀，意味着
某个发行者跳过了地板写入**，而写下那些文件的无论是什么都没运行
代码段（观察到：三个连续编号发行出来，地板落后三个）。扫描可以
断言它；这个检查只有一行，位置在扫描的计数之后、内容打印之前：

```bash
floor=$(sed '1!d; s/[^0-9]//g' "$d/archive/.id-floor" 2>/dev/null)
top=$(for p in "$d"/[0-9]*.md; do [ -e "$p" ] && printf '%s\n' "${p##*/}"; done | grep -oE '^[0-9]+' | sort -n | tail -1)
[ -n "${floor:-}" ] && [ -n "${top:-}" ] && [ "$((10#$floor))" -lt "$((10#$top))" ] && echo "NOTE: .id-floor ($floor) below highest active id ($top) — an issuer skipped the floor write"
```

`scripts/session-start-scan.sh` 不运行它（那一行在那里是可选的）；
`scripts/new-observation.sh` 在每次写入时运行同一检查，并把它自己
的地板写纠正进去。这里的 NOTE 是某个写入者绕过了代码段的证据——
把那个当作观察条目归档，而不是那个数。

### 返回空的结构探针是停止信号

**在曾有内容的地方返回空的结构探针是停止信号，不是一次创建。**
如果你早先在会话中归档过的目录或文件突然缺失，或者编号检查在
你已知有内容的日志里返回空，停机并重探结构（有 `observation-log/`
吗？有 `log.md.migrated` 吗？）——一个并行会话可能迁移或重组了
存储。绝不让一次追加静默重建缺失的目标：那会把迁移信号变成损坏
（观察到：按文件迁移把 `log.md` 改名之后，一个陈旧会话用一条崭新
的"Observation 1"重建了退役的 `log.md`；见 `migration.md` 关于与
活跃会话共存）。写入者对共享可变状态的模型只新鲜到它最后一次
读取。

**这同样覆盖读取。**对你知道存在的内容返回空的检索——会话启动
扫描、对指名当前技能的观察条目的过滤、对早先发现的一次 grep——
是同一个信号换了衣服，而且是更危险的那一半，因为坏读取不产生
错误，而它的结果（"没有相关的"）是一个合法的可能答案。在据其
行动之前重探（见上文"守护读取，而不只是写入"）。

### 为什么这就是并发问题的全部

因为每条观察条目住在自己的文件里，新观察条目从不触碰另一条条目
的字节，所以它不能截断、覆盖或重编号别人的工作。单文件日志需要
一套先检查-再行动-再验证的编号仪式、有界变更规则、结构不变量
检查和存活检查，因为一次贪婪替换曾把十六条条目从某个 Status 行
覆盖到文件尾，也因为一个并行会话的写回曾静默抹掉几分钟前追加的
条目。每文件隔离之下，这些失败模式一个都不存在。两个并行会话
碰巧选出同一编号的罕见情形里，结果是两个文件共用一个数——无害，
文件各异，什么都没丢，只要 slug 不同；脚本的编号认领为同一时刻
的运行防止它，代码段的前缀守卫在推导陈旧时于写入时刻抓住它，
编号与 slug 都相同就是一条路径，那正是防截断创建所防御的，而复核
的重复编号检查（Step 1，在 Step 6 重跑）给两者漏掉的重新编号并
归档一条元观察条目。

**有界变更纪律活得比单文件日志久。**它为 `log.md` 而写，适用于
代理在任何多条目文本文件里做的每一次删除或替换——交接文档、编号
列表、复核报告、清单。按目标自身的边界定位它（该条目的首行与
下一项的首行），绝不按周围空白或贪婪模式：一个编号列表某一项
周围的 `\n\n`"段落"边界曾一路跑过列表尾、删掉其后每一项，恰是
上述十六条丢失的形状。编辑后重读该区域，把幸存的与原本该幸存的
清点对账。

## 在处置、驳回、修复或引用之前先读完整正文

**在处置、驳回、修复或引用之前先读完整正文。**被跟踪条目的标题
（观察条目、GitHub issue、工单）是索引项，不是内容——它把失败
经过、报告者的上下文、乃至常常连同提议的修复一起压缩掉了。驳回
是没有下游检查点的那条路：已解决或被引用的条目事后有人复核，被
驳回的静默消失。从 issue 正文里收获修复设计——报告者常常附上正确
的解法，这也顺带解决了署名。当并行代理归档了一条看起来与你自己
重复的发现时，对比两个正文，不是标题：关于同一机制的两条条目
可以携带相反的运行结论，而第二条常常是提炼而不是回声。表面的
一致比分歧更有效地压制验证，所以这条规则恰在它显得最不必要的地方
约束力最强。同一道理适用于为对照某产物而读的手工账本或清单——
检索条目用摘录，判断条目用全文（`weekly-review.md`，
"Staged-work reconciliation gate"）。

**不是你做的变更，要逐点解决观察条目，绝不拿标题对标题。**当一次
上游发布、一个同族会话的编辑或一次经合并到达的修复看起来覆盖了
某条观察条目时，列出其正文提出的各点，并对每一点指名覆盖它的那一
行 diff；没有对应行的点保持 open，移入一条承载观察条目（承载模式，
见下文）。一个联合多个条件（A 且 B）的点按每个条件一个点计——
匹配后半的行不覆盖前半。拿修复的标题对观察条目的标题，衡量的
是两个标题的重叠，不是内容的覆盖，而未覆盖的余下部分离开每个
队列，因为条目被标成了已解决。

## 编辑既有观察条目

状态变更与归档恰好触碰一个文件。编辑之前立即重读那个文件（并行
的复核可能已解决它），然后只编辑你要改的 frontmatter 字段
（`status`、`resolved`、`resolution`）。绝不重写你不拥有的文件，
也绝不批量重写整个目录——没有必要，而且它重新引入了这套布局
存在所要移除的多条目危险。

当积压工作分给并行会话时，上面的机械安全拦不住两个会话以不同
方式合理地解决*同一个*文件。分活儿的交接因此必须携带所有权围栏：
按编号的显式在范围内列表、显式的范围外列表，以及每个会话只在自己
的编号上改状态的指令。

**在第一次写入之前立即复查所有权，不是在规划时。**"还有别人在
做这个吗？"从两个来源回答，而两者都诚实、也都在被读到的那一刻
过期：交接或清单状态，以及会话列表。一个**暂停**的会话没有释放
它的任务——它空闲，它读起来空闲，而它随时可以带着自己的决定完好
无损地恢复。

观察到：一次漫长的多步复核中途被暂停，其状态写着"等用户的决定"，
列表显示它没有在运行。第二个会话在规划时查了两样，正确地断定
第一个空闲，并计划接管。在它做第一次写入之前，用户恢复了第一个
会话，后者随即记录了它的决定并完成了大部分工作。假如第二个会话
写了，它会把用户已经做过的决定再问一遍。

所以检查属于第一次写入之前、同一个回合里——与编辑前重读文件是
同一条规则、同一个理由。规划时的空闲证据的保质期恰好等于规划
本身耗时。并且优先检查**结果**——工作是否已落在目标里？——而
不是检查载体，因为暂停会话的状态对它接下来要做什么只字不提。

**用编辑工具改日志文件——绝不 `sed -i`、`perl -pi`，或对文件的
重定向。**不为快速修复或临时反向测试破例；诱惑恰好在有未提交
工作、无可回退的文件上达到峰值。

从 shell 重写文本文件，先让替换经过 shell 的引号处理，到达的未必
是敲下的。双引号替换里一个未转义的 `$` 曾在源文件里落成 NUL 字节，
把文件变成二进制——而**命令退出码是 0**。损害后来偶然暴露，当时
一次 `grep` 回答"Binary file matches"而不是预期的那行。

观察条目正文让这比听上去严重得多。它们满是反引号、`$`、引号和
花括号，因为它们以引用命令和 frontmatter 为生。heredoc 是从 shell
写它们的天然方式，而**未加引号的** heredoc 会执行其中每一段反
引号：文件创建了，表面上看起来对，部分内容已被命令的输出替换。
凡 shell 写入真是唯一路径时，给定界符加引号（`<<'OBS'`）——
`set -C` 防截断创建没有编辑工具的等价物——其余处处优先编辑工具。
编辑工具拒绝写会话中没读过的文件时，先读一下创建刚做出的空文件
再写正文：拒绝以那个状态为键，而它读起来像 harness 故障而不是
创建的后果。加引号的 heredoc 只在 shell 按敲下的原样收到命令时
才是精确的；在 shell 工具改写传输中命令的主机上（`environments.md`，
"Windows 宿主：什么会到达 shell 与文件"），正文走编辑
工具。凡 shell 是唯一路径，用 `printf` 写 frontmatter、用加引号的
heredoc 写正文：给定界符加引号会关闭一切替换，正文带不了变量，
编号和日期放进它上面的 `printf` 里——

```bash
printf -- '---\nid: %s\ntitle: "%s"\nstatus: open\ndate: %s\n' "$next_id" "$title" "$(date +%F)" > "$f"   # …the remaining fields, then the closing ---
cat >> "$f" <<'OBS'
**Issue:** … `find -exec` … $(date) … written literally, none of it run
OBS
```

同一规则覆盖 `echo -e` 和任何 `"$(cat <<…)"` 形式。退出码 0 不是
证据：未加引号的形式创建文件，产出带可解析表头的合法 Markdown，
扫描报告它健康，而损害在正文里，直到复核打开它之前没人读。

如果 shell 写入还是发生了，**在同一回合里、在做任何别的事之前
验证文件**：`file "$f"`，或一次不回答"Binary file matches"的
`grep -c ''`，外加正文重读——读出来比你写的短，或解释的位置出现
命令输出的，就是 heredoc 失败。稍后检查等于永不检查。

**一条被否决的条目记录一个裁定；没有前提，裁定无法被重新审视。**
`declined` 意味着有人判定某个替代方案不可行，而那个判定是一个
可能错的事实主张——错了的话，它就永远静默否决更好的方案，因为
每个后续读者都发现决定已经做出。

观察到：一条条目记录某个辅助脚本被否决，理由是它"会在一个非致命
包装器里死硬退出并泄漏它启动的会话"。貌似有理、具体、且从条目
本身完全不可证伪——没有文件、没有行、没有命令。后续会话读了
那个辅助脚本的源码：它恰在那样的包装器下用的是库的"返回而非
退出"形式，所以所述失败不可能发生。前提干脆是假的。辅助脚本被
采纳，两条调用路径都改进了。在那两个会话之间，那条条目把自己的
工作做得完美——它被读了、信了、奉行了。

所以被否决条目上的 `resolution:` 携带**证据，而不只是裁定**：查了
什么（文件、行、命令、输出），以及要否决为错需要什么为真。而重读
被否决条目，使你有义务先核实其前提仍然成立再依赖它——`declined`
是唯一一个其正确性下游永远不测的状态。

## `parked` 状态——已决断，非待定

**`parked` 意味着已决断，不是待定。**当观察条目健全、但在外部前置
条件满足之前无法行动时使用它——产出它的定时任务被停用、它描述的
工具停用中、一个依赖尚未落地。搁置条目在工作队列*之外*：复核不得
重新上报它，而决定属于 `status:`，不属于 `status: open` 旁边的
一段自由文本笔记（没有东西按散文分类的笔记让条目留在队列里，每次
复核都被重新提起）。它也不是已解决，所以永不归档——归档需要已
解决状态加 `resolved:` 日期。它无限期留在 `observation-log/`，直到
其 `parked_until:` 条件满足——设回 `open` 并入队——或它被真正
解决。凡状态为 `parked`，`parked_until:` 必填：一行陈述条件，措辞
让后续会话真能回答它是否发生——并且在搁置前检查它到底能不能发生：
问谁或什么必须行动才能满足条件，那一方是否有理由做恰好相反的事
（有时恰是条目等着观察的那件事的预期效果）。如果条件不可能发生，
条目就不是在等待：以今天可得的替代证据关掉它，或把它搁置在一个
真能触发的触发器上——措辞在目标中的结果上，绝不在载体的状态上
（上文"搁置条件以结果命名，绝不用你自己的载体"）。

## 多技能观察条目的部分处置——承载模式

`status:` 按观察条目计，而 `skill:` 是列表，所以生命周期字段比它
所跟踪的工作更粗。当一个会话合理地只对所列技能的一个子集行动——
一个发布会话拥有一个技能，而并行复核拥有其余——两种直白做法都是
错的：留着 `open`，另一个会话可能重复应用已完成的部分；标成
`actioned`，未完成的部分静默离开此后每一次复核队列。沿着工作的
接缝拆开记录：

1. **部分工作进行期间**，在正文中记下主张："部分 X 正由会话 Y
   应用——不要重复应用。"主张保护进行中的部分不被并行会话触碰。
2. **完成时**，把观察条目标为 `actioned`，`resolution:` 指名究竟
   应用了哪些部分。
3. **同一回合里**，归档一条承载观察条目，持有剩余部分：其
   `skill:` 列表只列未完成的技能，正文声明它承载原始条目未应用的
   余下部分（引用原始条目的编号），并带上未完成部分所需的实质
   内容——绝不只是一根指针，因为原始条目即将归档。
4. **复核把承载条目当一等公民。**承载条目像任何其他 open 观察条目
   一样进入工作队列；其出身不使它延迟或降级。

原则：当记录的生命周期字段比它所跟踪的工作更粗时，每次状态迁移
都对某个消费者说一句谎——沿工作的接缝拆分记录，而不是给状态过载
语义。

## 当工作区处于版本控制之下

把工作区文件夹纳入版本控制是好做法——它给出技能所关心的回滚——
而它增加了一个看起来不像变更面的变更面。`git checkout --
<path>`、`git stash`、`git reset --hard`、带着本地修改的分支切换、
丢掉一个 hunk 的 rebase，以及最重要的 `git clean -fd`，对观察条目
文件的毁灭与任何编辑一样彻底；最新的文件暴露最多，因为一条刚写
下的观察条目在被提交之前是*未跟踪*文件，而 `git clean` 存在的
目的恰是删除那些。这些命令被当成整理家务反射性地运行（"把树弄
干净到能切分支"），而一份持续写入的日志几乎总是把树弄脏的东西。

规则：在任何可能丢弃工作树状态的 git 操作之前，把 `observation-log/`
复制到仓库之外，事后确认本会话写的每个文件仍然存在，不在则从
副本重建。**优先提交待定的观察条目而不是回退它们**——当树里的
脏东西就是日志时，提交永远是弄干净的更便宜方式。把任何脏树守卫
的作用域排除 `skill-observations/`，而不是教会会话去清空它，并且
绝不在该目录处于作用域内时运行 `git clean`。

**在两份安装之间同步的日志，是没有共享读取的多写入者日志。**
编号代码段在本安装看得见的文件上取最大值；另一份安装已铸出、尚未
推送的编号不是没读到，而是不存在，于是双方各自从自己的最大值
铸造，两侧每个守卫都诚实地通过（观察到：两台机器写了一周日志后
一次推送里十四个冲突编号，其中九个对裸列表不可见，因为一边写
`63-`、另一边写 `0063-`——复核的重复编号检查剥掉填充找到它们）。
而 `.id-floor` 是一个记录按写入者计的事实的文件，所以它合并成
两个正确值之间的冲突：向上解决，绝不选边。两份安装通过一个仓库
共享日志的，把写入通过它串行化——每次写之前 pull，写之后 push
——并把下次复核发现的碰撞当作漏掉一次 pull 的预期代价，按 Step 1
所说重新编号；文件的所有权不是条件。

## 归档

归档在结构上绑定到编号推导（上文"分配编号"）：计算下一个编号的同
一条命令先把已解决的文件从 `observation-log/` 移到
`observation-log/archive/`，所以每次写入都作为它跳不过的一步的
副作用触发清扫。规则的散文形式——"每次写入，先归档"——实践中欠
触发：作为前言附在另一个动作上的职责，不继承那个动作的任何强制
力，所以如果一个步骤必须总是伴随某次工具调用，它属于同一条命令
内部，而不是在散文里待在旁边。定期复核在其 Step 1 独立归档，作为
对归档安静的那几周的兜底。"已解决"由文件自己的 frontmatter 判定：
`status: actioned`、`declined` 或 `superseded`，**且** `resolved:`
日期早于今天。今天解决的文件留到下一天，无论哪个会话解决了它们
——宽限期活在文件里，从不在会话内存里，所以它对并行会话和后续
会话都成立。已解决却没有可读 `resolved:` 日期的文件，把今天的
日期写进那个字段，而不是被归档；内嵌清扫刻意跳过这种文件（其
日期检查失败即关闭），所以那一字段修复是对该文件单独一次、小心
的编辑。

**`parked` 豁免于归档——刻意如此。**它是唯一一个意味着"已决断"
而不意味着"已解决"的状态，所以它不满足门禁的两半：不在已解决
集合里，也不携带 `resolved:` 日期。不要从"它已离开工作队列"推断
它该归档，也不要为把它收拾掉而盖上 `resolved:` 日期——搁置条目
必须留在 `observation-log/`，复核才能复查其 `parked_until:` 条件
（`weekly-review.md`，Step 1）。它只在真正被处置、否决或并入之后
归档。

归档是一组普通的 `mv`，一次一个文件。移动一个已解决文件，影响
不了任何其他观察条目。安全的形式就是随发行的清扫——一趟 `awk`
扫过目录的 `*.md` 名，指名陈旧的已解决文件，它后面的循环只移动
刚交给它的名字；移走的文件落进 `archive/`，glob 绝不下探到那里。
不写观察条目也要归档时（复核的 Step 1），单独运行那段清扫块，从
`today=` 直到 `mv` 循环。没有闭合 `---` 的表头绝不归档：这一趟在
闭合行上做决定，而那样的文件没有闭合行。不要即兴批量移动；实在
免不了时，两条规则：

**一次读完集合。**要么像清扫那样由单次枚举驱动全部移动，要么在
第一个 `mv` 之前把完整候选清单写进文件或变量。绝不在移动进行中
第二次读目录——对其文件的 `grep`、单独一次 glob 展开、一次列表
——那个读取者是否撞上移动者已移走的文件，取决于哪一阶段领先，
而它的"No such file or directory"错误与数据丢失同形。（观察到：
一条读取阶段与移动阶段并发运行的流水线产出几十个这样的错误；
没有文件丢失，而事后区分这两者花的代价比先写清单大。）

**按守恒验证批量移动**，而不是按存在性探针：一次移动不改变
`observation-log/` 加 `archive/` 的总数。带多个参数的 `ls` 聚合
退出码——任一参数缺失就以非零退出，而移动之后活跃副本按设计
就是缺失的——所以用一条 `ls` 测"每个文件在活跃或归档中存在"，
会把每个文件都报成缺失。确需存在性探针时，每条路径一次调用。

```bash
d="C:/Users/Administrator/.zcode/skill-observations/observation-log"
total() { echo $(( $(find "$d" -maxdepth 1 -name '[0-9]*.md' | wc -l) + $(find "$d/archive" -maxdepth 1 -name '[0-9]*.md' | wc -l) )); }
before=$(total)
# ... the moves ...
after=$(total)
if [ "$before" -ne "$after" ]; then echo "ARCHIVAL CONSERVATION BROKEN: $before -> $after"; exit 1; fi
```

读集合与改集合，属于一次枚举或两个严格排序的步骤，绝不属于两个
并发的步骤；而批量操作之后的检查要落在一个不变量上，因为带聚合
退出码的探针，对没人问过它的问题回答"缺失"。可移植地把
`resolved:` 日期与今天比较（ISO 日期按字典序排）：

```bash
older_than_today() {   # $1 = a YYYY-MM-DD date
  today=$(date +%F)
  [ "$(printf '%s\n%s\n' "$1" "$today" | sort | head -1)" = "$1" ] \
    && [ "$1" != "$today" ]
}
```

归档是平的：解决日期住在每个文件里，所以不需要带日期的归档文件
名。来自 3.0 之前安装的遗留 `log-YYYY-MM-DD.md` 文件原样坐在按
文件归档旁边；它们不被转换（见 `migration.md`）也不被扫描。

## 引用观察条目

按 frontmatter 里的 `id` 字段引用观察条目，它与文件名的 `NNNN-`
前缀一致。绝不把 `grep -n` 的行号当 id 引用——搜索工具的行号是
位置元数据，不是标识符。廉价的合理性检查：被引用的编号应落在
`observation-log/`、其 `archive/` 与 `.id-floor` 实际存在的编号
区间内；远在区间外的数（最高编号 #766 时引用 #1365）几乎必然是
被误读成 id 的行号。编号来自记录自身的标识符字段，绝不来自找到
它的工具的位置元数据。

## 为什么检查点是写入而不是提问

核心技能要求每逢第三个完成的 todo 条目、每逢一次交付事件就向磁盘
写入——一个观察条目文件，或没有积累时 `checkpoints.log` 里一行
确认。原因是"记得问一问有什么值得归档"不是强制：更软的"完成条目
时检查一下"式指引被反复证明会在认知负担沉重的分析工作中丢失——
恰是观察条目积累最多的时候。一次具体的写入迫使心理检查浮出为
一条被记录的动作，并防止技能已加载、却直到用户开口什么都没写这
一常见失败。把冲写挂在你本来就在做的工具调用上（呈报文件、渲染
幻灯、完成一批 todo），意味着写入作为你反正要做的工作的副作用
发生，而不取决于一次单独的记忆行动。计数不必精确；大约每三次
完成一次是规则。

**声称的写入不是写入。**上面每条规则都落在写入上；报告它的总结
需要自己的规则，因为一句收尾能以真写入的恰好形式指名编号与标题、
卸下心里的义务感、却在磁盘上什么也不留。那比遗忘更糟：遗忘的
写入留下下一个检查点能抓住的缺口，被叙述的写入读起来像已通过的
检查点，而一个编造的编号日后可能与真实编号撞上、在审计中变得
与它无法区分（观察到：一份收尾总结指名了两个没有任何创建打印过
的编号；缺口在下一次真实写入的编号代码段报告的文件数比所称编号
暗示的少时才暴露）。所以呈报自查落在叙述上：总结指名的每个编号
都是代码段或 `scripts/new-observation.sh` 在本会话工具记录里打印
过的，而总结由同一回合内对 `observation-log/` 的一次列表渲染而来，
绝不是凭写过它的记忆。

### 扫描以写入收尾，而不只是打印

加载本技能与执行本协议是两件事，而只有加载在会话转录里留下产物
——这卸下了心里的义务感，所以一个加载了却什么都没运行的会话，
从外面看与两件都做了的一模一样。追加的 `checkpoints.log` 行是
协议自身的痕迹，理由与检查点规则是写入相同：一个价值在于在特定
时刻发生的步骤，需要在工具记录里有自己的条目。（工作区给每次
写入计价的地方——"How to Log" 下的例外——把这一行折进会话的
第一次写入。）

### 检查点配对仍然留下的两个缺口——以及两者背后的规则

**这个配对仍然留下两个缺口——两者都在什么都没归档的完整工作日里
观察到过。**

1. *一个会话可以完全不含 todo 条目。*第三次完成检查点绑定在一个
   工具上；完全由直接工具调用和 shell 命令驱动的工作永远踩不到它。
   它只在碰巧用 todo 的会话里武装起来，所以它不是永远在场的
   安全网。会话没有它们运行时，交付冲写是仅剩的强制，必须刻意
   施加。
2. *"这是重大交付吗？"是自评，而自评正是在负载下失效的东西。*
   优先选工具记录里一目了然的触发器，而不是需要临场判断的。冲写
   点是一个**性质，不是命令清单**：把一个工作单元向人类宣告完成
   的任何动作。部署、发布、publish、push 都算——但完成通知、最终
   报告、状态文件置为"done"也算。每一个都是一次具体的工具调用，
   是和完成的 todo 一样硬的触发器，并且在洞见积累之处可靠地标志
   一个工作单元的结束。命令清单不能充当定义：它继承推导它的那些
   会话的形状，在任何通过其他工具宣告完成的会话里静默失效——
   没有部署、没有版本控制，不等于没有完成。

两者背后的规则：执行触发器必须挂在工具记录中客观可见的事件上，
绝不挂在代理注意到某个时刻合格上。可见是必要条件而非充分条件：
触发器的模式是对未来工具记录的一个主张，所以在它算作已武装之前，
把项目实际产出的字面事件串当阳性对照跑一遍，再从真实工具记录里
取一个已知的非事件当阴性对照——绝不用编造的例子，那采样的是
作者对输入的想象，正是产生缺口的那个模型。把两个结果记在触发器
旁边。（观察到：一个提醒钩子的六个模式来自部署脚本内部做的事，
从未匹配过项目实际敲下运行它的那条命令，自安装起对它自己的目标
一直失效；同一天它却对一条只读命令点了火，只因其测试串碰巧含
一个信号词。）而绑定在单一工具上的计数器，在每个不用它的会话里
静默失效——这类触发器永远需要第二条独立路径。触发器也不得抢走
后续层已拥有的交付决定（"收件人就在眼前，不必发了"）：点火，让
拥有它的层去抑制——被抑制的发送在工具记录里留下痕迹，没发的
什么也不留。
