# 原型业务实体建模 (Prototype Domain Modeling)

## 概述

从**静态 HTML / 低代码原型**逆向提取业务实体模型,帮产品经理理清业务逻辑关系。原型里没有代码级的 class/struct,业务对象以四种形态藏着:

- **页面 = 业务域**
- **表格列 / 表单字段 = 实体属性**
- **badge class = 状态枚举(权威源)**
- **按钮文案 = 操作**

**核心洞察:状态和枚举的真相源是 CSS badge class,不是 `data-*` 属性。** `data-*` 是脚本为筛选而派生的,常缺失或滞后(动态新增的行往往只有 class、没有 data-status)。只 grep `data-status` 会漏状态。

## 何时用

- PM 拿到一堆原型 `.html`,想理清"有哪些业务对象、什么关系、各自什么状态、能做什么操作"。
- 需要从原型反推领域模型 / 状态机 / 单据流转,产出能驱动 PRD 与评审的业务逻辑文档。

**不适用**:代码里已有真实实体定义(Go struct / TS interface / ORM model)——那是正向建模,用 `domain-modeling` 技能。本技能专攻"对象只活在 HTML 里"的原型。

## 四步提取流程

1. **建图(定边界)**:先读导航/路由/总览页(`nav.js`、`index.html`),列出全部页面,区分**实质页 vs 占位页**。占位页常对应未实现期次(2/3 期),只提取"设计意图",不当作已实现实体。这一步决定详略。

2. **批量提取(别逐行读)**:原型页常 2000+ 行,逐行读浪费上下文。用 Grep 抓结构信号:
   - `<th>` / `<label>` / `.field-label` → 实体属性
   - `<button>` / 行操作 `<a>` 文案 → 操作
   - 所有 `*-tag` / `*-badge` / `*-status` / `*-pill` 的 **class 名** → 状态/分类枚举(**权威源**)
   - `data-status` / 其它 `data-*` → 辅助(派生,非权威)
   - tab / 筛选项 → 分类与状态维度

3. **精读核心 + 全部弹窗**:精读信息密度最高的几个核心页正文 + **每一个 modal / drawer**(弹窗 = 操作表单,承载操作语义和字段)。

4. **交叉验证状态机**:同一状态常分散在工作台 tab、历史列表 tab、配置页超时逻辑、挂起弹窗提示等 4–5 处,拼合后才完整。

## 五条关键约定(防漏防错)

这是 baseline 最容易踩的坑,**逐条遵守**:

1. **badge class 是状态真相源,`data-*` 是派生**。提取状态优先扫所有徽章 class;新增/动态行可能只有 class 没有 `data-status`。只看 `data-status` 会漏状态。

2. **两套状态词汇并存 → 产出映射表**。原型常见"运行态工作台"和"历史列表"用两套状态词(如 `accept/wait` vs `ongoing/closed`)。它们是**同一状态的不同叫法**,不是不同状态。必须产出"状态词汇映射表"统一,否则 PM 会误判状态机更复杂。

3. **占位实体必须标注期次**。占位页(2/3 期)的实体属性从占位卡 `.ph-features` 列表 / 占位描述提取,但产出里**必须显式标注"规划意图,原型未实现"**,不能与 1 期已实现实体混为一谈。

4. **区分演示数据与真实概念**。原型常为演示硬编码维度(如脚本按行轮转注入"企业/品牌/渠道"归属文本)。警惕"看起来像核心架构、实则为演示塞的假维度"。拿不准时标注"疑似演示用"。

5. **提取数据源标注**。很多原型页脚注/注释标注了后端表名(如 `来源:customer_chat_sessions`)。收集"原型概念 → 后端表"映射,帮 PM 判断概念能否落地。无标注则跳过。

## 必须产出

图一律用 **Mermaid**(可渲染、可编辑),不要只用 ASCII。完整模板见 `output-template.md`。最小必产:

- **业务域地图**:页面 → 实体,每个实体标期次。
- **实体清单表**:实体 / 核心属性 / 状态 / 操作 / 承载页 / 数据源 / 期次。
- **关系图**:Mermaid `erDiagram`。
- **状态机**:每个有状态实体一张 Mermaid `stateDiagram-v2`。
- **状态词汇映射表**(若存在两套词汇)。
- **枚举字典**:所有 badge → 业务含义。
- **操作 / CRUD 矩阵**。
- **业务逻辑缺口清单(强制)**:列出所有"原型未明示、需 PM 拍板"的业务逻辑分歧。**这是 PM 最有价值的产出**,务必单独成节。

## 产出形态:单视角 vs 双视角

模型只给 PM 看 → **单视角**(上述必产即可)。同时给**开发和业务** → **双视角**,一份文档四大块,**业务优先**:

1. **业务背景**:归属结构 + 演示数据警示(读正文前的前置说明)。
2. **实体总览**(单一真相源):实体清单 + 关系图 + 状态机 + 状态词表 —— 不带视角的客观事实,两版共用。
3. **业务视角**(放前):流程 / 业务规则 / 角色边界 / 单据流转 / 业务缺口(B)。
4. **开发视角**(放后):DDD 类型 / 聚合边界 / 状态机触发 action / 数据源映射 / 枚举常量 / 技术缺口(T)。

要点(实战验证):
- **状态机等核心只画一次放"实体总览"**,两视角各补独有维度,不重复——避免同一张图在文档里出现两次。
- **业务缺口(B)↔ 技术缺口(T)做对应映射**(如 B 留言是否进 MVP ↔ T 留言无表)。PM 拍板业务口径,开发缺口随之明确;评审会上业务与技术对着同一张表说话。
- **章节命名对业务读者友好**:避开"层 / 骨架 / 模型"等技术词,用"业务背景 / 实体总览"这类人话(PM 反馈"全局骨架 / 共享层"看不懂)。
- **业务视角默认排在开发视角前**(PM 是主读者)。
- **产出前先对齐三个取舍**:开发版深度(领域模型+数据源 / +字段级 / +接口契约)、业务版受众(PM评审 / 业务方 / 客服运营)、文件组织(一份双章节 / 两份独立)。

## 常见错误

| 错误 | 后果 | 正确 |
|------|------|------|
| 只 grep `data-status` | 漏掉只在 badge class 里的状态 | 以 badge class 为权威 |
| 两套状态词当两套状态 | 状态机臃肿失真 | 产出映射表统一 |
| 占位页实体当已实现 | PM 误判功能范围 | 标注期次 + "未实现" |
| 演示假维度当真实架构 | 误导业务建模 | 标注"疑似演示用" |
| 逐行读 2000 行大页 | 烧上下文、慢 | Grep 结构信号 + 精读核心区 |
| 只给模型、不给缺口 | PM 拿不到决策点 | 强制“业务逻辑缺口”清单 |
| 章节名用“层/骨架”等技术词 | 业务读者看不懂 | 用“业务背景/实体总览”等人话 |
| 双视角时状态机画两遍 | 文档冗余 | 核心图只画一次放实体总览,两视角补独有维度 |

## 范例

本技能首次应用产出(可作为参考):`prototype-cs/doc-pm/业务实体模型_V2.0.md`(商城客服系统原型,**业务/开发双视角** —— 业务背景 + 实体总览(真相源)+ 业务视角「流程/规则/角色/单据/业务缺口 B」+ 开发视角「类型/聚合/action/数据源/技术缺口 T」,19 实体,**B↔T 缺口对应**)。
